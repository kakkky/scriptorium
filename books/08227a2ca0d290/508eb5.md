# ミドルウェアについて
複数のエンドポイントにおいて同じ処理を行いたい時や、アクセスログなど透過的に付け加えたい処理などを実装する際に有用なのが、ミドルウェアパターンです。

ミドルウェアを実装する例として、以下のようなものがあります。
- 認証・認可（JWTトークンの検証）
- ロギング（アクセスログの記録）
- CORS設定（クロスオリジンリクエストの管理）
- リクエストバリデーション（リクエストデータのチェック）
- リクエスト・レスポンスのトレース（パフォーマンス測定やデバッグ）

これらのようなミドルウェアは、ハンドラーによる処理の前・後に実行されます。

![](https://storage.googleapis.com/zenn-user-upload/8c1100acc79f-20250201.png)

図からも分かるようにハンドラーと同じく、インターフェースアダプター層におけるプレゼンテーションにミドルウェアの実装を配置することにしました。ハンドラーとミドルウェアは密接に関わるものだからです。

さらに、ミドルウェアがリクエストとレスポンスの流れを制御し、「外側」と「内側」の橋渡しを行うものだとするとハンドラーとそう大きな違いはないと筆者は考えました。

そのため、`app/adapter/presentation/middleware/`として、ミドルウェアを定義していくことにします。



## `net/http`におけるミドルウェア定義
他のwebフレームワークには多様なミドルウェアが用意されていることがありますが
、`net/http`パッケージには、ミドルウェアが用意されていません。

そのため、欲しいミドルウェアの機能は自身で実装していく必要があります。
golangにおけるミドルウェアパターンは、以下のようなシグネチャを満たすように書いていくのが一般的です。
```go
func(h http.Handler)http.Handler
```
**ミドルウェアを適用させたいハンドラ(`h`)をラップした新たなハンドラを返す**といった構造になっています。

ポイントは、`http.Handler`インターフェースを満たすようにミドルウェアを実装していることです。
これによって、**ミドルウェアを入れ子にすると複数のミドルウェアをハンドラに適用する**ことができます。
また`http.Handler`を返すため、**`Handle`メソッドでルーティングにそのまま登録する**ことができます。この辺についてはまだ分かりにくいと思いますが、実装の中で実感していただければと思います。

https://tutuz-tech.hatenablog.com/entry/2020/03/23/220326

### ミドルウェアパターンの実装例
先にあげた`func(h http.Handler)http.Handler`のシグネチャを満たすためにはどういったふうに書けばいいかというと、以下のようになることが多いです。
```go
func middleware(h http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {

        // ミドルウェアで実行したい処理

        h.ServeHTTP(w, r)  // 引数にとったハンドラの処理を実行

        // ミドルウェアで実行したい処理
        
	})
}
```
`http.Handler`を返すために、`http.HandlerFunc`を返しています。

前章のおさらいとなりますが、`http.HandlerFunc`は関数型であり、`func(w http.ResponseWriter, r *http.Request)`といった無名関数（クロージャといいます）をキャストすることで`http.Handler`インターフェースを満たすようにするのでした。`http.HandlerFunc`関数型には`ServeHTTP()`メソッドが定義されているからそれが可能なのでしたね。

ミドルウェアは、引数として受け取ったハンドラー`h`を内部で実行します(`h.ServeHTTP(w, r) `)。それ以外の関数内に書いた処理は全てミドルウェアの処理内容となります。
そのため、ハンドラー実行の前でも後でも、または両方でも記述することが可能です。

このようなミドルウェアは、以下のようにしてルーティングに登録することができます。
```go
// 何らかのハンドラーにミドルウェアを適用させてルーティングに登録する
mux.Handle("GET /",middleware(handler))
```
`middleware()`は`http.Handler`インターフェースを返すので、`Handle`メソッドによってルーティングにそのまま登録できるのですね。

このようなミドルウェアパターンは、とてもシンプルで扱いやすいことがわかります。

### 追加情報を利用したミドルウェアパターンの実装例
少し発展したミドルウェアパターンも今回実装するので、ここで取り上げておきます。

先に示したパターン(`func(h http.Handler)http.Handler`)だと、「ミドルウェア内で外部の設定情報や依存コンポーネントを使いたい」といった場合に対応しにくいという問題があります。このままだと、`http.Handler`を引数にとることになっているからです。

そこで、**「返り値にミドルウェアパターンを返す」関数を記述する**ことで、引数に任意の値を取れるようにします。
```go
func middleware(xxx XXX) func(h http.Handler) http.Handler {
	return func(h http.Handler) http.Handler {
		return http.HandlerFunc(func(rw http.ResponseWriter, r *http.Request) {

                    // Xxx型のxxxを利用した何らかの処理
			
                    h.ServeHTTP(rw, r) //ハンドラの処理を実行
		}
            )
	}
}
```
コードに書いてあるままの説明になってしまいますが、`func(h http.Handler) http.Handler`を返すようになっています。

このようなパターンだと、以下のようにルーティングに登録します。
```go
mux.Handle("GET /",middleware(xxx)(handler))
```
ぱっと見でわかりにくいですが、`middleware(xxx)`の返り値が`func(h http.Handler) http.Handler`の関数そのものと考えてみてください。書き方を変えれば、以下のようになります。
```go
m := middleware(xxx)
mux.Handle("GET /",m(handler))
```
変数`m`には、`middleware(xxx)`の返り値である`func(h http.Handler) http.Handler`の関数そのものが格納されています。

このパターンは、書籍にて紹介されていました。
https://www.c-r.com/book/detail/1462

### ロガーミドルウェア

#### 実装
::::details ロガーミドルウェアのコード
```go:app/adapter/presentation/middleware/logger.go
package middleware

import (
	"bytes"
	"encoding/json"
	"fmt"
	"io"
	"net/http"
	"time"
)

// HTTP リクエストとレスポンスをログに記録するミドルウェア
func Logger(h http.Handler) http.Handler {
	return http.HandlerFunc(func(rw http.ResponseWriter, r *http.Request) {
		// リクエストの処理
		requestLog(r)

		// レスポンス用ラッパーを作成
		buf := &bytes.Buffer{} //レスポンスボディを書き込むためのバッファ
		rww := newResponseWrapper(rw, buf)

		// ハンドラ呼び出し
		// ラッパーをResponseWriterとして渡し、バッファにもレスポンスを書き込むようにする
		h.ServeHTTP(rww, r)

		// レスポンスの処理
		responseLog(rww, buf)
	})
}

// リクエスト情報を取得しログに出力
func requestLog(r *http.Request) {
	reqBody, _ := io.ReadAll(r.Body)
	defer r.Body.Close()

	var formattedReqBody bytes.Buffer
	json.Indent(&formattedReqBody, reqBody, "", "    ")

	// リクエストボディをログに記録
	fmt.Printf(
		"=====================================================================================================\n"+
			"[REQUEST]\n"+
			"Timestamp       : %s\n"+
			"Method          : %s\n"+
			"Path            : %s\n"+
			"Authorization   :%s\n"+
			"Body            :\n%s"+
			"\n-----------------------------------------------------------------------------------------------------\n",
		time.Now().Format(time.RFC3339),
		r.Method,
		r.URL.Path,
		r.Header.Get("Authorization"),
		formattedReqBody.String(),
	)

	// リクエストボディを再代入
	// リクエストボディはストリームなので再代入する必要がある
	r.Body = io.NopCloser(bytes.NewBuffer(reqBody))
}

// レスポンス情報を整形しログに出力
func responseLog(rww *rwWrapper, buf *bytes.Buffer) {
	var formattedRespBody bytes.Buffer
	json.Indent(&formattedRespBody, buf.Bytes(), "", "    ")
	status := rww.statusCode

	fmt.Printf(
		"[RESPONSE]\n"+
			"Timestamp       : %s\n"+
			"Status          : %d\n"+
			"Body            :\n%s"+
			"=====================================================================================================\n",
		time.Now().Format(time.RFC3339),
		status,
		formattedRespBody.String(),
	)
}

// レスポンスのログ記録用にレスポンスをラップ
type rwWrapper struct {
	rw          http.ResponseWriter
	multiWriter io.Writer
	statusCode  int
}

func newResponseWrapper(rw http.ResponseWriter, buf io.Writer) *rwWrapper {
	return &rwWrapper{
		rw:          rw,
		multiWriter: io.MultiWriter(rw, buf),
	}
}

// http.ResponseWriterインターフェースを満たすためのメソッド
func (rww *rwWrapper) Header() http.Header {
	return rww.rw.Header()
}
func (rww *rwWrapper) Write(b []byte) (int, error) {
	return rww.multiWriter.Write(b)
}
func (rww *rwWrapper) WriteHeader(statusCode int) {
	rww.statusCode = statusCode
	rww.rw.WriteHeader(statusCode)
}
```
::::

少し複雑なので、ポイントごとに記述を追っていきます。
- ミドルウェアパターンを満たす`Logger()`関数
- リクエスト情報をログに書き出す`requestLog()`関数
- レスポンス情報をログに書き出す`responseLog()`関数

#### `Logger()`関数
ミドルウェアの本体です。ミドルウェアパターンのシグネチャを満たしていることがわかります。

内部的な処理としては、

- リクエスト情報をロギング→ハンドラーの処理を実行→レスポンス情報をロギング

といった流れになっており、プライベート関数を呼び出しています。

ハンドラー処理を実行した後は、`http.ResponseWriter`型の変数`rww`にレスポンス情報が含まれています。その`rww`を参照することで、レスポンス情報を取得し、ロギングするようにしているのです。
前章を振り返りますが、ハンドラー内で呼び出しているプレゼンター関数は、以下のように、`http.ResponseWriter`型の変数（`rw`）にヘッダーやステータスコード、JSONを付加していました。
```go
func respondJsonSuccess[T any](rw http.ResponseWriter, statusCode int, respBody T) {
	rw.Header().Set("Content-Type", "application/json;charset=utf-8")
	rw.WriteHeader(statusCode)
	jsonResp := SuccessResponse[T]{
		Status: statusCode,
		Data:   respBody,
	}
	if err := json.NewEncoder(rw).Encode(jsonResp); err != nil {
		RespondInternalServerError(rw, err.Error())
	}
}
```

#### `requestLog()`関数
リクエスト情報を含む`*http.Request`型の変数`r`を読み取って`fmt.Printf()`関数によって標準出力にログを書き込むようにしているといったところが大まかな処理内容です。

しかし、ここで注目すべきは**リクエストボディは一度しか読み取れない**ということです。`*http.Request`型のリクエストボディはストリームなデータ構造のようです。
以下の記事では、そのような構造がコードベースで解説されています。
https://rarejob-tech-dept.hatenablog.com/entry/2021/11/15/100650
::::message
上の記事を参考に、リクエストボディが一度しか読み込めない構造を取っているワケは以下のように説明できそうです。

リクエストボディの読み取りは、`sawEOF`というフラグによって制御されているようです。
ボディを最後まで読み取れた時点でフラグが`true`になり、もう一度読み取ろうとしても`sawEOF`フラグが`true`の場合は`EOF`エラーが返るようになっています。

こうしている理由は、**リクエストボディを最後まで読み取らなかった場合に、TCPコネクションを再利用しないようにするため**です。
リクエストボディを中途半端に読み取ったとして、「同じTCP接続を使い回して」後続のリクエストボディを読み取った場合、バッファに前回のリクエストボディが残っているかもしれません。そうなると、正しくリクエストボディを読み取れなくなる可能性が生じます。

その問題を回避するために、

(リクエストボディがCloseされているにも関わらず)`sawEOF`フラグが`false`の場合、つまりリクエストボディを中途半端に読み取ってしまっている場合には、TCP接続を切断して、次回は新たなTCP接続でやり取りするようにするのです。
::::

リクエストボディを読み取る`io.ReadAll(r.Body)`が一度しか行えないとなると、後続のハンドラー内の処理でリクエストボディを読み取ることが出来ません。
そうなると、ハンドラー内に記述していたJSON→構造体のデコード処理が期待通りに動かなくなってしまいます。
```go
json.NewDecoder(r.Body).Decode(&params)
```
`(dec *json.Decoder) Decode`は内部でリクエストボディを読み取っているからです。

このような問題を解決するため、以下のようにしています。
```go
func requestLog(r *http.Request) {
    // リクエストボディを読み取る
	reqBody, _ := io.ReadAll(r.Body)

    // 省略

	// リクエストボディをログに記録
	fmt.Printf( // 省略)

	// リクエストボディを再代入
	// リクエストボディはストリームなので再代入する必要がある
	r.Body = io.NopCloser(bytes.NewBuffer(reqBody))
}
```
一度読み取ったリクエストボディを、新たな`io.ReadCloser`型として`r.Body`に再設定することで、後続のハンドラーでもリクエストボディを読み取れるようにしています。
これを可能にしているのは、以下の部分です。
```go
r.Body = io.NopCloser(bytes.NewBuffer(reqBody))
```
`[]byte`型の`reqBody`は、はじめに読み取ったリクエストボディです。`reqBody`を、`bytes.NewBuffer()`関数によって`*bytes.Buffer`型でラップし、`io.Reader`インターフェースを満たすようにします。
`[]byte`型の変数を`io.Reader`インターフェースに適用させる際に、この関数はよく使用されます。
```go
func bytes.NewBuffer(buf []byte) *bytes.Buffer
```
```go
type Buffer struct {
	buf      []byte   // バイトスライスを格納している(ラップしている)
	// 省略
}
```

そして、`r.Body`は`io.ReadCloser`インターフェースを満たす必要があります。
```go
type ReadCloser interface {
    Reader
    Closer
}
```
リクエストボディは、読み取った後に`Close`する必要があるからです。

そこで、`io.Reader`を`io.ReadCloser`にして返す`io.NopCloser()`関数を使用します。
```go
func io.NopCloser(r io.Reader) io.ReadCloser
```

少し複雑ですが、`r.Body = io.NopCloser(bytes.NewBuffer(reqBody))`によって再設定された`r.Body`の実態は、`[]byte`型である`reqBody`をラップした新たな`io.ReadCloser`です。

そのため、後続のハンドラーにおいて、リクエストボディを読み取る際には、`sawEOF`フラグによる判定はそもそも存在せず、エラーが起きないのです。

`sawEOF`フラグなどを使用していたのは、`r.Body`にDIされていた`io.ReadCloser`の具体実装である`*http.body`型の実装です(`(b *body) Read()`メソッド)。

再代入したのは、`*http.body`型とは異なる、`io.ReadCloser`となっています。
厳密に言えば、`io.nopCloser`型です。`r.Body.Read()`が呼ばれた時には、`io.nopCloser`によってラップされている`*bytes.Buffer`型に定義された`Read()`メソッドが呼び出されるということになります。

#### `responseLog()`関数
関数内を見る前に、`Logger()`関数内にある次の記述についてまずは解説していきます。
```go
// レスポンス用ラッパーを作成
buf := &bytes.Buffer{} //レスポンスボディを書き込むためのバッファ
rww := newResponseWrapper(rw, buf)
```
レスポンス情報をロギングするには、レスポンス情報を読み取る必要があります。これは、`reqestLog()`の場合も同じでした。

しかし、`http.ResponseWriter`インターフェースには読み取りに関するメソッドが定義されていません。
```go
type ResponseWriter interface {
    Header() Header
    Write([]byte) (int, error)
    WriteHeader(statusCode int)
}
```
そこで、`http.ResponseWriter`をラップして、レスポンス情報にアクセスできるようにします。
```go
rww := newResponseWrapper(rw, buf)
```
`newResponseWrapper()`関数の内容を見てみます。
```go
// レスポンスのログ記録用にレスポンスをラップ
type rwWrapper struct {
	rw          http.ResponseWriter
	multiWriter io.Writer
	statusCode  int
}

func newResponseWrapper(rw http.ResponseWriter, buf io.Writer) *rwWrapper {
	return &rwWrapper{
		rw:          rw,
		multiWriter: io.MultiWriter(rw, buf),
	}
}
```
ポイントは、`multiWriter`フィールドです。

関数内では、`multiWriter: io.MultiWriter(rw, buf)`としています。
```go
func MultiWriter(writers ...Writer) Writer
```
この`MultiWriter()`関数は、書き込み先を複数指定できるようにするものです。
以下のように`newResponseWriter()`関数を呼び出している場合、
```go
buf := &bytes.Buffer{}
rww := newResponseWrapper(rw, buf)
```
`*byte.Buffer`型の`buf`変数にもレスポンスボディが書き込まれるようになるということです。

つまり、`http.ResponseWriter`と同じくレスポンスボディが書き込まれる`buf`変数を読み取ることで、レスポンス情報にアクセスできるようになります。

レスポンス情報の取得についての解決策がわかったところで、`responseLog()`関数の中身を見てみましょう。
```go
func responseLog(rww *rwWrapper, buf *bytes.Buffer) {
	var formattedRespBody bytes.Buffer
	json.Indent(&formattedRespBody, buf.Bytes(), "", "    ")
	status := rww.statusCode

	fmt.Printf( // 省略 )
}
```
第二引数に`*bytes.Buffer`型の`buf`を受け取っています。これには、レスポンスボディが書き込まれています。
以下では、`buf.Bytes()`によってレスポンスボディ（バイトスライス）を取得し、整形したJSONを`formattedRespBody`に格納しています。
```go
var formattedRespBody bytes.Buffer
json.Indent(&formattedRespBody, buf.Bytes(), "", "    ")
```
また、ステータスコードについては、`rwWrapper`構造体の`statusCode`フィールドにて管理しています。
ステータスコードは、`WriteHeader()`メソッドにて扱われるため、内部で`statusCode`フィールドに代入することでそれを保持できるようにし、取得できるようにしています。
```go
// http.ResponseWriterインターフェースを満たすためのメソッド
func (rww *rwWrapper) WriteHeader(statusCode int) {
	rww.statusCode = statusCode
	rww.rw.WriteHeader(statusCode)
}
// 省略
```

単にリクエスト情報・レスポンス情報を取得してロギングするだけと考えると単純そうですが、意外と一筋縄ではいかない部分がありました。

### 認可制御ミドルウェア
認可制御のビジネスロジック自体は、10章にてユースケースに実装しました。そのため、ユースケース処理を呼び出すように実装を行うという点において、ハンドラーに近い実装となります。

ハンドラーの処理の前に認可処理を行い、不正なリクエストだった場合はミドルウェアの段階でそれを弾きます。

また、ミドルウェアを適用しないハンドラは、無条件にアクセスを通すように出来ます。

::::details 認可制御ミドルウェアのコード
```go:app/adapter/presentation/middleware/authorization.go
package middleware

import (
	"context"
	"errors"
	"net/http"
	"strings"

	"github.com/kakkky/app/adapter/presentation/presenter"
	"github.com/kakkky/app/application/usecase/auth"
)

type userIDKey struct{}

func Authorication(authorizationUsecase *auth.AuthorizationUsecase) func(h http.Handler) http.Handler {
	return func(h http.Handler) http.Handler {
		return http.HandlerFunc(func(rw http.ResponseWriter, r *http.Request) {
			jwtToken, err := getJwtToken(r)
			if err != nil {
				presenter.RespondUnAuthorized(rw, err.Error())
				return
			}
			input := auth.AuthorizationInputDTO{JwtToken: jwtToken}
			output, err := authorizationUsecase.Run(r.Context(), input)
			if err != nil {
				presenter.RespondUnAuthorized(rw, err.Error())
				return
			}
			userID := output.UserID
			// コンテキストにuserIDを含める
			ctx := context.WithValue(r.Context(), userIDKey{}, userID)
			// 後続の処理（ハンドラ）を実行する
			h.ServeHTTP(rw, r.WithContext(ctx))
		})
	}
}

func getJwtToken(r *http.Request) (string, error) {
	authorizationHeader := r.Header.Get("Authorization")
	if authorizationHeader == "" {
		return "", errors.New("authorization Header is missing")
	}
	// スペースを区切りとして最大２つに分割
	parts := strings.SplitN(authorizationHeader, " ", 2)
	if len(parts) != 2 || parts[0] != "Bearer" {
		return "", errors.New("invalid Authorization header format")
	}
	return parts[1], nil
}

// コンテキストに設定したユーザーIDを取得する
// ハンドラーで使用する
func GetUserID(context context.Context) string {
	return context.Value(userIDKey{}).(string)
}
```
::::

認可ユースケース`*auth.AuthorizationUsecase`に依存するため、引数に受け取るようにしています。これは、先述した**ミドルウェアパターンを返り値として返すパターン**ですね。

処理の流れは以下のようになっています。

1. リクエストヘッダからJWTトークンを取得
2. 認可処理（ユースケース）を呼び出す
3. ユーザーIDをコンテキストに含める
4. リクエストスコープのコンテキストに、(3)で作成したコンテキストを含めてハンドラーを呼び出す

順を追って見ていきましょう。

#### `getJwtToken()`関数
リクエストヘッダー（`Authorization`ヘッダ）からJWTトークンを抽出する関数です。
まず、把握しておくべきは、クライアントからは、JWTトークンを以下のように含めてリクエストが送られてくるということです。
```
Authorization   : Bearer トークン
```
このように、`Authorization`ヘッダに、`Bearer`スキームを設定します。
この`Bearer`認証は、トークンを使用した認証認可に使用されることが想定されているようです。
https://qiita.com/h_tyokinuhata/items/ab8e0337085997be04b1#bearer%E8%AA%8D%E8%A8%BC

関数内部では、このトークンを抽出するためのロジックを書いています。
`authorizationHeader`変数には、`Authorization`をキーとして得られた値が入ります。つまり、`Bearer トークン`の部分が得られます。
```go
authorizationHeader := r.Header.Get("Authorization")
authorizationHeader // "Bearer トークン"
```
そして、以下でスペースを区切りにして分割したものを`parts`変数にスライスとして格納します。
```go
parts := strings.SplitN(authorizationHeader, " ", 2)
parts // []string{"Bearer","トークン"}
```
最後に、`pars[1]`、つまりトークン部分のみを関数の最終的な返り値としています。

#### `Authorication()`関数
ミドルウェアの本体です。

`getJwtToken()`でトークンを抽出したその後からの処理を見ていきます。

まずは、認可ユースケース処理を呼び出しています。
```go
input := auth.AuthorizationInputDTO{JwtToken: jwtToken}
output, err := authorizationUsecase.Run(r.Context(), input)
```

認可制御をPASSした場合、ユーザーIDを返す、というのがユースケース処理の内容でした。

後続のハンドラー処理では、そのユーザーIDを元にユーザーを判別したいです。
そこで、**リクエストスコープのコンテキスト**にIDを含めることで、後続のハンドラーでそれを参照できるようにしていきます。
::::message
#### `context.Context`
golangには`context`パッケージが用されており、`context.Context`型を通して、「情報を透過的に伝播させる」ことが可能になります。

`*http.Request`にも、`context.Context`型のフィールドが含まれています。
```go
type Request {
  // ctx はクライアントまたはサーバーのコンテキストです。
  // これは、Request 全体を Clone または WithContext を使用してコピーすることでのみ変更されるべきです。
  ctx context.Context
}
```
これを、本書では「リクエストスコープのコンテキスト」と呼んでいます。
「リクエストスコープのコンテキスト」を取得するには、`Context()`メソッドを使用します。
::::
`context.Context`型には、キー・バリューで情報を埋め込みます。
```go
// コンテキストにuserIDを含める
ctx := context.WithValue(r.Context(), userIDKey{}, userID)
```
キーには、`userIDKey{}`のように空の構造体を設定しています。
```go
type userIDKey struct{}
```
非公開の独自型`userIDKey{}`をキーとしてコンテキストに含まれた値を取得するのに、以下のような関数を用意しています。
```go
// コンテキストに設定したユーザーIDを取得する
// ハンドラーで使用する
func GetUserID(context context.Context) string {
	return context.Value(userIDKey{}).(string)
}
```
::::message
#### コンテキストに与えるキーの衝突を防ぐ
コンテキストは、アプリケーションのロジック内を透過的に扱えるものであると考えれば、異なるパッケージ間でキーが競合し、衝突してしまう可能性があります。

そこで、**キーにはプリミティブな値（文字列など）を用いず、独自型で表現する**ことが推奨されています。
そうすると、異なるパッケージ間(例えば`package A`と`package B`)で、同じ型名`ctxKey{}`を使用したとしても、`A.ctxKey{}`と`B.ctxKey{}`といったように異なる型として扱えるようになり、衝突しません。

- [よくわかるcontextの使い方(Zenn)](https://zenn.dev/hsaki/books/golang-context/viewer/appliedvalue#context%E3%81%AB%E4%B8%8E%E3%81%88%E3%82%8Bkey%E3%81%AE%E8%A8%AD%E5%AE%9A)
::::


このように、伝播したい情報（ユーザーID）を含めたコンテキスト(`ctx`変数)を用意しました。

それを、リクエストスコープのコンテキストに含めることで、後続のハンドラーにてユーザーIDを参照できるようにします。
```go
// 後続の処理（ハンドラ）を実行する
h.ServeHTTP(rw, r.WithContext(ctx))
```
`WithContext()`メソッドによって、指定した`context.Context`を関連付けた新しい`*http.Request`を作成しています。
```go
func (r *http.Request) WithContext(ctx context.Context) *http.Request
```
厳密には、`ctx`フィールドのみを差し替えた`*http.Request`のコピーを返しているようです。

これにより、後続のハンドラーで`r.Context()`を使って埋め込んだ情報を取得できるようになります。

ハンドラーでは、以下のように記述していましたね（これでエラーが解消されると思います）。
```go

	// contextからuserIdを取得

	// 省略
}
```

### 複数のミドルウェアを束ねる
さて、ロガー・認可制御の二つのミドルウェアを実装できました。

ミドルウェアは以下のようにしてハンドラーに適用させるのでした。
```go
// 何らかのハンドラーにミドルウェアを適用させてルーティングに登録する
mux.Handle("GET /",middleware(handler))
```
一つのミドルウェアを適用させるだけならこれでも問題なさそうですが、ミドルウェアが複数に増えた時、以下のように書かなければならず、可読性が下がります。
```go
mux.Handle("/", middlewareA(middlewareB(middlewareC(handler))))
```

これを解決するために、複数のミドルウェアを扱いやすくするためのロジックを用意しましょう。
これは、ルーティングの際に使用するため、実装するディレクトリは`presentation/middleware`ではなく、`app/infrastructure/router`とします。

`composeMiddleware()`関数としてロジックを実装していきます。

::::details composeMiddleware() のコード
```go:app/infrastructure/router/middlewares.go
package router

import "net/http"


// 適用させたい順で、ミドルウェアを引数に入れる
// composeMiddlewares(M1,M2,M3)とした場合、M1(M2(M3()))といったようにラップされたミドルウェアを返す
func composeMiddlewares(middlewares ...func(http.Handler) http.Handler) func(http.Handler) http.Handler {
	return func(h http.Handler) http.Handler {
		for i := range middlewares {
			h = middlewares[len(middlewares)-(i+1)](h)
		}
		return h
	}
}
```
テストコード
```go:app/infrastructure/router/middlewares_test.go
package router

import (
	"net/http"
	"net/http/httptest"
	"testing"
)

func TestComposeMiddlewares(t *testing.T) {
	middleware1 := func(h http.Handler) http.Handler {
		return http.HandlerFunc(func(rw http.ResponseWriter, r *http.Request) {
			rw.Header().Set("Middleware", "1")
			h.ServeHTTP(rw, r)
		})
	}
	middleware2 := func(h http.Handler) http.Handler {
		return http.HandlerFunc(func(rw http.ResponseWriter, r *http.Request) {
			rw.Header().Set("Middleware", "2")
			h.ServeHTTP(rw, r)
		})
	}
	handler := http.HandlerFunc(func(rw http.ResponseWriter, r *http.Request) {})

	sut := composeMiddlewares(middleware1, middleware2)(handler)
	r := httptest.NewRequest(http.MethodGet, "/", nil)
	rw := httptest.NewRecorder()
	sut.ServeHTTP(rw, r)
	// 最終的なMiddrewareヘッダーは2である。
	// リクエスト処理は、Middleware1→Middleware2と行われる
	if got := rw.Header().Get("Middleware"); got != "2" {
		t.Errorf("expected header Middleware to be '2', got '%s'", got)
	}
}
```
::::
可変長にミドルウェアを受け取れるようにしており、引数にとった最後のミドルウェアから順にハンドラー`h`に適用させていきます。

ただ、ミドルウェアの実行順序には注意が必要です。
実装は次章になりますが、認可制御ミドルウェアとロガーミドルウェアをハンドラーに適用した際の挙動を見ていきましょう。

ルーティングでは、以下のようなコードになります。
適用されているミドルウェアがとても見やすいですね。
```go
mux.Handle("GET /users", composeMiddlewares(logger, authorization)(getUsersHandler))
```
この場合、ミドルウェアは以下のように適用されています。
```go
logger(authorization(getUsersHandler))
```
実行順序としては、
1. ロガーミドルウェアがリクエストログを書き込む(`requestLog()`)
2. 認可制御ミドルウェアが処理を実行
3. ハンドラーの処理を実行(`getUsersHandler`の`ServeHTTP()`)
4. ロガーミドルウェアがレスポンスログを書き込む（`responseLog()`）

といったふうになります。
図解で表すと以下のようになります。

![](https://storage.googleapis.com/zenn-user-upload/986808c1c633-20250202.png)

ロガーミドルウェアは、ハンドラの処理(`ServeHTTP()`)の前後に処理を挟んでいました。
そのため、最初に`requestLog()`が実行されます。

その次には、`ServeHTTP()`が実行されるわけですが、`logger()`の引数には`authorization(getUsersHandler)`をとっています。ということは、`ServeHTTP()`によって、次は認可制御ミドルウェアの処理に移るということになるわけです。

認可制御ミドルウェアでは、ハンドラーの処理(`ServeHTTP()`)の前にロジックを記述していましたね。そのため、認可制御のロジックの後で、ハンドラーの処理に移るのです。

ハンドラーの処理が完了すれば、処理はロガーミドルウェアに戻ってきます。`ServeHTTP()`の後に記述しているロジック(`responseLog()`)が実行され、終了します。


# 番外編: CORSミドルウェアを実装する
フロントエンドからこのバックエンドAPIを叩く場合、**CORS(Cross-Origin Resource Sharing)** の設定を行う必要があります。

今回は、フロントエンドからAPIを叩かないため、CORSミドルウェアの実装は番外編としました。
ですので、実装する必要はありませんし、このハンズオンでは以降登場しません。

::::message
GitHubのリポジトリにおいているソースコードではミドルウェアを登録している記述があります。
::::

```go:app/adapter/presentation/middleware/cors.go
package middleware

import (
	"net/http"

	"github.com/kakkky/app/adapter/presentation/presenter"
)

func Cors(h http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		// 開発環境ようなので全てのリクエストを通すようにする
		w.Header().Set("Access-Control-Allow-Origin", "*") // 本番環境でこのようにするのは禁止
		w.Header().Set("Access-Control-Allow-Headers", "Content-Type, X-Requested-With, Origin, X-Csrftoken, Accept, Authorization")
		w.Header().Set("Access-Control-Allow-Methods", "POST, GET, PATCH, DELETE, OPTIONS")
		h.ServeHTTP(w, r)
	})
}
```
