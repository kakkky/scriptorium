# ユースケースの責務
実装に入る前に、ユースケースの持つ責務について理解しておきましょう。

クリーンアーキテクチャにおいては、円の「内側」にあることを第二章では説明しました。
アプリケーション固有のビジネスルール、ロジックを含む場所であり、アプリケーションが持つ「機能」を実現します。

ユースケースは、円のもう一つ外側に位置するインターフェースアダプター層の中でも特に**ハンドラー**から依存されます。

機能を実現するために、ハンドラーからデータを受け取り、ドメイン層に定義されたロジックを操作します。また、処理結果などをハンドラーに返す処理も担います。
つまり、

データを受け取って、ロジックを実行し、またそのデータを返すという、
**円の内側↔︎インタフェースアダプター層間のI/O処理の役割**があると言えます。

どのように実装すればいいかを具体的に理解するために、次に具体例を用いて考えてみます。


# ユースケースの実装方針
## 例：ユーザー登録ユースケース

### コンポーネントのインターフェースに依存させる

これらの機能を実現するには、さまざまなコンポーネントが必要になります。
![](https://storage.googleapis.com/zenn-user-upload/dc2c27f8948d-20250106.png)

エンティティ、ドメインサービス、リポジトリを操作する必要があるのですね。
エンティティは、ユースケースの内側にあるものであり、直接の依存が許されています。

そして「DBに保存する」ためには、ユーザー登録ユースケースは**リポジトリ**を利用する必要があります。　
しかし、ユースケースがインターフェースアダプター層にあるリポジトリを直接利用してしまうと、依存の方向が外側を向いてしまい、クリーンアーキテクチャにおいて重要な**依存性のルール**を侵してしまいます。

ユースケースはフレームワークやUI、DBなど外部の影響を受けるべきではありません。

この問題を解決するのが、**インターフェース**でしたね。
第二章でも掲載した、依存関係を逆転させた図です。
![](https://storage.googleapis.com/zenn-user-upload/182fa6ed3fff-20250106.png)

**ユースケースは、リポジトリに直接依存させるのではなく、ドメイン層に定義したリポジトリの「振る舞い」（つまり、インターフェース）に依存させる**ようにします。

### インターフェースに依存させるメリット
「クリーンアーキテクチャが依存性のルールを推しているから、インターフェースに依存させています...」というように暗黙的にルールに従っているわけではありません。

インターフェース（振る舞い）を定義し、それに依存することは、以下のようなメリットがあります。
- モジュールの差し替えによる単体テストの容易性
- 抽象への依存による安定性

#### モジュール差し替えによる単体テストの容易性
インターフェースは、振る舞いです。
以下は、ユーザーリポジトリインターフェースのコードです。
ユーザー登録であれば、ユーザーを「保存する」メソッドが必要になるでしょう。
```go
type UserRepository interface {
	Save(ctx context.Context, user *User) error
}
```
ここで定義されているのは、`context.Context`型の`ctx`と`*User`型の`user`を受け取り、`error`を返すという「振る舞い」なのです。
これにより、このインターフェースを使用するユーザ登録ユースケースは、リポジトリの具体的な実装の中身を知らずに利用することができるのです。

これが単体テスト容易性につながります。

このメリットを実感するには、インターフェースに依存せず、リポジトリの具体実装に依存している場合を考えるとわかりやすいです。

リポジトリの具体実装に依存してしまうと、
- リポジトリの実装にバグがあるとそれを利用しているユースケースのテストも失敗する
- リポジトリがDB操作を行うためのテストDBを用意する必要がある

といったデメリットがあります。
![](https://storage.googleapis.com/zenn-user-upload/28660868e909-20250106.png)

ユースケースのテストを行っているのにテスト結果がリポジトリの実装にも左右されているとなると、果たしてそれはユースケースの単体テストと言えるのか？？となります。

ユースケースのテストをピュアに行うために、リポジトリには期待通りの挙動をしてもらう必要があります。
そこで、インターフェースに利用すると、モジュールをモックに差し替えることにより、期待通りの動きをするリポジトリを用意できます。これで、ユースケースのロジックのみを確かめるテストを行えるようになります。
![](https://storage.googleapis.com/zenn-user-upload/8d69acb25f4b-20250106.png)

ドメインサービスはユースケースよりも内側にあるものですが、インターフェースに依存させているのはこのメリットを享受するためです。ユースケースのテストにおいては、ドメインサービスのロジックはテスト対象になりません。
さらに、ドメインサービスは内部でリポジトリ（インターフェース）を利用しているので、テストが複雑になる可能性があります。ドメインサービスをモックで置き換えればシンプルにテストを行うことができるのです。

### モックとは
テストを実装（実行）するときに、テストする対象ではない箇所に差し替える都合の良いダミーです。
モックという言葉自体には、模倣物・擬似物という意味合いがあります。
「振る舞い」だけを実装した、見かけだけのものということです。

#### 抽象への依存による安定性
インターフェースを「抽象型」、そして具体的な実装を「具体型」と表現することがあります。
そして、**抽象型は具体型よりも変化しにくい**という傾向があります。また、新しい機能を実装する際にはインターフェースの変更なしで済ませることが方針として推奨されているようです。

今回でいえば、「ユーザーを保存する」という振る舞いを持つ`UserRepository`インターフェースを定義していますが、ユーザー登録ユースケースにおいて、この振る舞いが変更されることは少ないでしょう。

例として、何らかの理由で保存先がMySQLといったRDBからRedisなどのNoSQLに変わったとします。ユーザーリポジトリの持つ`Save`メソッドの具体実装は勿論変更されることでしょう。
しかし、ユースケースはインターフェースという「振る舞い」に依存していることにより、具体実装に関しては知りません。
よって、そのような変更の影響を受けずに、ユースケースのコンポーネントを安定させることができるのです。

### アプリケーション層の中のユースケース
この章では、「アプリケーション層の実装」と謳いながらも、ほとんどがユースケースの実装です。
それにクリーンアーキテクチャの文脈では、「ユースケース層」としてこのレイヤーは定義されることが多いです。
ではなぜこのレイヤーをアプリケーション層として、そしてその中にユースケースを配置したのかを述べておきます。

筆者は、

**アプリケーション層とは、アプリケーション（API)固有の要件を満たすロジックを配置する場所**

と捉えています。アプリケーション層という呼び名はレイヤードアーキテクチャの文脈でよく使われているものです。

これならば、アプリケーション層 ≒ ユースケースであり、「ユースケース層」としちゃえばいいじゃん！と言えそうですね。実際、それも合理的であり、正しい設計といえます。

では、なぜアプリケーション層の中にユースケースを配置する構造にしたのかというと、

**このレイヤーで扱いたいのはユースケース（アプリケーションが実現する「機能」のロジック）だけではないから**

です。

例えば、今回は実装しませんが**トランザクション**がそれにあたります。トランザクションは、そのスコープの定義がアプリケーションの要件に基づくものとしてこのレイヤーにインターフェースが置かれることがあります。具体実装はインフラストラクチャ層に置かれるようです。

トランザクションは、各ユースケース内で使用されるものであり、ユースケースを実現させる構成要素であることは間違いありません。しかし、トランザクションはAPIの「機能」としては成立しません。

そこで、ユースケースという概念の抽象度をあげて**アプリケーション層**とし、その中にユースケース・トランザクションが配置できるようになると、見通しが良くなるのではないかなと考えたという次第です。今回はトランザクションを実装しないのですが😢（再喝)

# Data Transfer Object
ユースケースがあるアプリケーション層までが、クリーンアーキテクチャにおける円の「内側」でした。
そしてユースケースは、インターフェースアダプター層におけるハンドラとの間でデータをやり取りします。
この時、例えば、先の例である「ユーザー登録ユースケース」が返り値として`User`オブジェクトを返し、ハンドラに渡したとしましょう。処理としては単純明快で、ぱっと見何もおかしくありません。

しかし、これではハンドラの中でドメインオブジェクト（エンティティ）が操作可能になってしまいます。ドメインオブジェクトがどこからでも操作できてしまう状況は、意図しないバグを生む危険性があります。

**プレゼンテーション（ハンドラ）はドメインオブジェクトを「知っててもいい」けど「知る必要はない」ため、不必要な依存は避けるべき**です。

そこで、ユースケースとプレゼンテーションのやり取り(I/O)は、データ転送用オブジェクトである**Data Transfer Object(DTO)** を使って行うようにします。
DTOは単なるデータクラスです。ロジックを持たせることはしません。
```go
package user

type RegisterUsecaseInputDTO struct {
	Name     string
	Email    string
	Password string
}

type RegisterUsecaseOutputDTO struct {
	ID    string
	Name  string
	Email string
}
```
プレゼンテーションからデータを受け取るための`InputDTO`、プレゼンテーションにデータを渡すための`OutputDTO`を定義しています。
具体的な使い方は、実装されたコードを追う中で理解していきましょう。

```go:app/application/usecase/user/register_usecase.go
package user

import (
	"context"

	"github.com/kakkky/app/domain/errors"
	"github.com/kakkky/app/domain/user"
)

type RegisterUsecase struct {
	userRepository    user.UserRepository
	userDomainService user.UserDomainService
}

func NewRegisterUsecase(
	userRepository user.UserRepository,
	userDomainService user.UserDomainService,
) *RegisterUsecase {
	return &RegisterUsecase{
		userRepository:    userRepository,
		userDomainService: userDomainService,
	}
}

func (ru *RegisterUsecase) Run(ctx context.Context, input RegisterUsecaseInputDTO) (*RegisterUsecaseOutputDTO, error) {
	// userインスタンスを生成
	u, err := user.NewUser(
		input.Email,
		input.Name,
		input.Password,
	)
	if err != nil {
		return nil, err
	}
	//userがすでに登録済みでないか？
	ok, err := ru.userDomainService.IsExists(ctx, u.GetEmail())
	if err != nil {
		return nil, err
	}
	// emailがすでに存在していた場合
	if ok {
		return nil, errors.ErrAlreadyRegisterd
	}
	if err := ru.userRepository.Save(ctx, u); err != nil {
		return nil, err
	}
	// DTOに詰め替えて返す
	return &RegisterUsecaseOutputDTO{
		ID:    u.GetID(),
		Name:  u.GetName(),
		Email: u.GetEmail().Value(),
	}, nil
}
```

```go:app/application/usecase/user/unregister_usecase.go
package user

import (
	"context"

	"github.com/kakkky/app/domain/user"
)

type UnregisterUsecase struct {
	userRepository user.UserRepository
}

func NewUnregisterUsecase(
	userRepository user.UserRepository,
) *UnregisterUsecase {
	return &UnregisterUsecase{
		userRepository: userRepository,
	}
}

func (uu *UnregisterUsecase) Run(ctx context.Context, input UnregisterUsecaseInputDTO) error {
	// 存在しているユーザーしか削除できない
	u, err := uu.userRepository.FindById(ctx, input.ID)
	// エラーかユーザーがnilの場合はエラー
	if err != nil || u == nil {
		return err
	}
	if err := uu.userRepository.Delete(ctx, u); err != nil {
		return err
	}
	return nil
}
```

```go:app/application/usecase/user/update_profile_usecase.go
func (epu *UpdateProfileUsecase) Run(ctx context.Context, input UpdateProfileUsecaseInputDTO) (
	*UpdateProfileUsecaseOutputDTO, error,
) {
	// 存在しているユーザーしか編集できない
	u, err := epu.userRepository.FindById(ctx, input.ID)
	// エラーかユーザーがnilの場合はエラー
	if err != nil || u == nil {
		return nil, err

	if input.Name == "" {
		input.Name = u.GetName()
	}
	if input.Email == "" {
		input.Email = u.GetEmail().Value()
	}
	// input情報をもとに、更新情報を反映したインスタンスを作成
	updatedUser, err := u.UpdateUser(
		input.Email,
		input.Name,
	)
	if err != nil {
		return nil, err
	}
	if err := epu.userRepository.Update(ctx, updatedUser); err != nil {
		return nil, err
	}
	// 更新したオブジェクトをDTOに詰め替える
	return &UpdateProfileUsecaseOutputDTO{
		ID:    updatedUser.GetID(),
		Email: updatedUser.GetEmail().Value(),
		Name:  updatedUser.GetName(),
	}, nil
}
```

## gomock（モック）を用いた単体テスト
テストコードでは、`gomock`パッケージを用いてモックを用意しています。

https://github.com/uber-go/mock

::::message alert
「gomock」というワードで検索すると以下のリポジトリがヒットします。

▶︎ https://github.com/golang/mock

しかし、2023年6月にメンテナンスが終了しています。

そのため代わりに、このリポジトリをフォークしてメンテナンスを継続させている`go.uber.org/mock/gomock`パッケージを使用します。
::::

第1章では、`Dockerfile.app`の以下の部分でインストールしていました。
```Dockerfile
RUN go install go.uber.org/mock/mockgen@v0.3.0
```

基本的な使い方を知ってから実際にテストを回してみましょう。
### 基本的な使い方
#### モックを生成する
定義したインターフェースの上に`//go:generate`ディレクティブによって実行するコマンドを記述しています。
```go
package user

import "context"

//go:generate mockgen -package=user -source=./interface_user_repository.go -destination=./mock_user_repository.go
type UserRepository interface {
	Save(ctx context.Context, user *User) error
	FindByEmail(ctx context.Context, email Email) (*User, error)
	FindById(ctx context.Context, id string) (*User, error)
	FetchAllUsers(ctx context.Context) (Users, error)
	Update(ctx context.Context, user *User) error
	Delete(ctx context.Context, user *User) error
}
```
::::message
#### go generate
`//go:generate xxxxxxx`といったように、 `xxxxx`の中にコマンドを記述しておくと、`go generate`コマンドによって実行することができます。
いちいち、よく実行するようなコマンドを手打ちで実行する必要もなくなりますし、それによる打ち間違いもなくなるので便利です。
::::

モックのコードは以下のコマンドによって生成されます。
```
mockgen -package=user -source=./interface_user_repository.go -destination=./mock_user_repository.go
```
使用している`mockgen`コマンドのフラグは以下の通りです。
| フラグ          | 説明                                                                          |
|----------------|-------------------------------------------------------------------------------|
| `-package`     | 生成されるファイルに明記するパッケージ名                                      |
| `-source`      | モックが満たすべきインターフェースが記述されているファイル                     |
| `-destination` | 生成するコードを書き込むファイル                                              |

Makefileには、`/app`ディレクトリに降りて`go generate ./...`を実行するタスクを定義しているため、以下のコードを打ち込んでコードを生成しましょう。
```
make go-gen
```
### モックをテストで扱う
ユーザー登録ユースケースの単体テストを例にみていきましょう。
```go
func TestUser_RegisterUsecase_Run(t *testing.T) {
	t.Parallel()
	tests := []struct {
		// 省略
		mockFn  func(mr *user.MockUserRepository, mds *user.MockUserDomainService)
		// 省略
	}{
		{
			name: "正常系：ユーザーを登録できる",
			mockFn: func(mr *user.MockUserRepository, mds *user.MockUserDomainService) {
				mds.EXPECT().IsExists(gomock.Any(), gomock.Any()).Return(false, nil)

		},
        {
			name: "準正常系：重複した登録は阻止する",
			mockFn: func(mr *user.MockUserRepository, mds *user.MockUserDomainService) {
				// emailで検索すると、DBに存在していたケース
				mds.EXPECT().IsExists(gomock.Any(), gomock.Any()).Return(true, nil)
			},
        // 省略
		},
	}
	for _, tt := range tests {
		tt := tt
		t.Run(tt.name, func(t *testing.T) {
			t.Parallel()
			// モックを設定
			ctrl := gomock.NewController(t)
			mockUserRepository := user.NewMockUserRepository(ctrl)
			mockUserDomainService := user.NewMockUserDomainService(ctrl)
			tt.mockFn(mockUserRepository, mockUserDomainService)
			// ユースケースオブジェクト
			registerUsecase := NewRegisterUsecase(mockUserRepository, mockUserDomainService)
			ctx := context.Background()
			got, err := registerUsecase.Run(ctx, tt.input)
            // 省略
	}
}
```
テストテーブルの中には以下の関数型を`mockFn`として定義しています。
`MockUserRepository`と`MockUserDomainService`はどちらもgomockにより生成されたモック（オブジェクト）です。
```go
mockFn  func(mr *user.MockUserRepository, mds *user.MockUserDomainService)
```

テストケースによって、モックの挙動を変えられるようにしています。
`モック.EXPECT().メソッド名().Return(期待する返り値)`のように書くことによって、挙動をコントロールすることができます。
```go
        {
			name: "正常系：ユーザーを登録できる",
			mockFn: func(mr *user.MockUserRepository, mds *user.MockUserDomainService) {
				mds.EXPECT().IsExists(gomock.Any(), gomock.Any()).Return(false, nil)
				mr.EXPECT().Save(gomock.Any(), gomock.Any()).Return(nil)
			},
        },
```
上のコードだと、ユーザーを正常に登録できるケースをテストしたいので、`IsExists()`は`false`（つまりユーザー重複しない）と、エラーがないという意味で`nil`を返すようにしています。また、正常に保存処理がされる前提でいるので、`Save()`はエラーなし、つまり`nil`を返すようにしているというわけです。

引数には`gomock.Any()`を入れています。引数に何が入っているかの検証は特に行わないようにしています。`Any()`関数は何でもマッチするマッチャーを返しているようです。
```go
// Any returns a matcher that always matches.
func Any() Matcher { return anyMatcher{} }
```
引数に何か具体的な値を入れれば、引数に渡っている値も正しいかどうかを検証することができます。
興味のある方はぜひやってみてください。


以下の部分でモックを初期化し、モックの挙動を記述した`mockFn`を呼び出し、ユースケース構造体にDI(依存性の注入)しています。
```go
// モックを設定
ctrl := gomock.NewController(t)
mockUserRepository := user.NewMockUserRepository(ctrl)
mockUserDomainService := user.NewMockUserDomainService(ctrl)
// ここでモックの挙動が決定される
tt.mockFn(mockUserRepository, mockUserDomainService)
// ユースケースオブジェクトにDI
registerUsecase := NewRegisterUsecase(mockUserRepository, mockUserDomainService)
```
