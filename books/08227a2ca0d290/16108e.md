docker,docker-composeを使ってカンタンに環境を構築しましょう。

今回は、**MySQLとRedis**を使用するので、コンテナとしてその二つを用意します。また、それら二つを利用する、APIの「本体(=golangの環境)」とも言える**app**コンテナを作成します。

## appコンテナ
### Dockerfileでappコンテナイメージを作成
まずはgolangのイメージを用いて、カスタムしたイメージを作成するための`Dockerfile`を記述していきます。
現在は`/app`ディレクトリにいるかと思われますが、移動してルートディレクトリに`Dockerfile.app`を作成してください。
::::details Dockerfile.appのコード
```dockerfile:Dockerfile.app
FROM golang:1.23.1

WORKDIR /src

COPY ./app/go.mod ./app/go.mod
COPY ./app/go.sum ./app/go.sum
WORKDIR /src/app
# github.com/[あなたの名前]/appモジュールの依存関係を全てコンテナ内にダウンロード
RUN go mod download
# srcディレクトリ配下にローカルのソースコードをコピー
COPY ./ ./

WORKDIR /src/app

# 必要なツールをインストール

RUN go install github.com/air-verse/air@latest
RUN go install go.uber.org/mock/mockgen@v0.3.0
RUN go install github.com/sqlc-dev/sqlc/cmd/sqlc@v1.23.0
RUN go install github.com/swaggo/swag/cmd/swag@latest
RUN go install -tags 'mysql' github.com/golang-migrate/migrate/v4/cmd/migrate@latest

# airを起動
CMD ["air"]
```
::::

ポイントは、
- ローカルの`app/go.mod`、`app/go.sum`をコピーして`go mod download`をしている
  - 最初に依存関係だけコンテナにコピーし、ローカルの依存関係を反映させています(まだプロジェクトを初期化しただけで依存関係はありませんが、再ビルドする際などに有効です)
- その後、ローカルのディレクトリを全てコンテナ内にコピー
- 主にCLIツールをコンテナ内にインストール
- airを起動

となっています。CLIツールはローカルでインストールして使う、でも全く問題ないのですが、開発環境は全てコンテナに閉じ込めたい＆dockerに明記したい感が筆者にはありまして、このような形を取っています。

ただデメリットはあって、`Dockerfile`イメージのビルド時間がかなり伸びてしまう問題があります。特に、今後使用する`sqlc`のインストールは１分弱かかる場合があります。

開発環境をDockerで全て完結させる&カンタンに配布するならこの方法はメリットがありそうですが、ビルドが遅くなるのは超難点ですね。

インストールしているそれぞれのツールについては、後々触れていきます。

## docker-compose
appコンテナ、dbコンテナ、kvsコンテナを作成し、appコンテナがdb、kvsを利用できるようにする...そのためにはdocker-composeが必要です。以下にコードを示します。
::::details compose.ymlのコード
```yml:compose.yml
services:
  app:
    container_name: todo-api
    build:
      dockerfile: ./Dockerfile.app
      context: .
    volumes:
      - type: bind
        source: ./
        target: /src
    ports:
      - "8080:8080"
    tty: true
    environment:
      PORT: ":8080"
      TODO_DB_HOST: db
      TODO_DB_PORT: 3306
      TODO_DB_USER: user
      TODO_DB_PASSWORD: pswd
      TODO_DB_NAME: todo-db
      TODO_KVS_HOST: kvs
      TODO_KVS_PORT: 6379
    depends_on:
      - db
      - kvs
  db:
    container_name: todo-db
    image: mysql:8.0.40-debian
    platform: linux/amd64
    volumes:
      - type: volume
        source: db-store
        target: /var/lib/mysql
      - type: bind
        source: ./app/infrastructure/db/mysql
        target: /etc/mysql/conf.d:cached
    ports:
      - "3306:3306"
    environment:
      MYSQL_DATABASE: todo-db
      MYSQL_USER: user
      MYSQL_PASSWORD: pswd
      MYSQL_ALLOW_EMPTY_PASSWORD: true
    tty: true
  kvs:
    container_name: todo-kvs
    image: redis:latest
    ports:
      - "6379:6379"
    volumes:
      - type: volume
        source: kvs-store
        target: /data
    tty: true
volumes:
  db-store:
  kvs-store:
```
::::
appコンテナには、先に作成したカスタムDockerイメージを使用することを記述しています。また、先述したように`volumes:`のあたりに`bind`という記述がありますね。
これは、ローカルのカレントディレクトリ配下のコードを全て`src`配下にマウントするということを示しています。`Dockerfile.app`で`src`ディレクトリを作成していましたね、それです。

また、dbコンテナに関して、以下の記述があります。
```yml:compose.yml
      - type: bind
        source: ./app/infrastructure/db/mysql
        target: /etc/mysql/conf.d:cached
```
これは、MySQLのデフォルト設定をオーバーライドするためのものです。
従って、`app/infrastructure/db/mysql/conf.d/my.conf`を作成し、以下の記述をしておいてください。
```conf:my.conf
[mysqld]
character-set-server=utf8mb4
collation-server=utf8mb4_unicode_ci

[client]
default-character-set=utf8mb4
```

その他の記述はどれも比較的基本的なものなので、composeファイルについて詳しく理解したい方は、別途お調べください🙏。
特に理解していなくても、開発は進めることができます。

最後に、`Dockerfile.app`をビルド＆コンテナ起動のために、以下のコマンドを打ちましょう。
airなどが立ち上がっていれば成功です。
```
docker-compose up --build
```
以下のコマンドを打って一旦コンテナを削除しておきましょう。
```
docker-compose down
```

### ホットリロードツール air
golangでプログラムを実行する`go run`は、内部でビルドしたバイナリファイルを実行しているので、変更を反映したいときはその都度、`go run`しなければなりません。
テストコードでしかコードをほとんど動かさない、場合はこのままでも問題ないのですが、動作確認も開発中に行いたい場合は、変更のたびにいちいちコマンドを打つのは手間です。

そこで、[ホットリロードツールAir](https://github.com/air-verse/air)を使用すれば、Airがプロジェクト全体を監視してくれて、コード変更時に自動でビルド〜実行を行ってくれるのです。

`Dockerfile.app`内では、ここでインストールしています。
```Dockerfile:Dockerfile.app
RUN go install github.com/air-verse/air@latest
```
そして、最後に以下の部分で、airを起動しています。
```Dockerfile:Dockerfile.app
# airを起動
CMD ["air"]
```

airを使用するためには、設定ファイルが必要です。以下のコマンドで設定ファイル`.air.toml`を生成します。airがインストールされているのはコンテナ内なので、コンテナを一時的に立ち上げてコマンドを実行する`docker compose run`を使用します。`--rm`をつけることで、実行後はコンテナが削除されます。
```
docker compose run --rm app air init
```
`app`ディレクトリにファイルが自動で生成されたはずです。
設定は特にいじりません。以下の部分だけ注目しておきます。
```toml:.air.toml
[build]
  args_bin = []
  bin = "./tmp/main" #ビルドされたバイナリファイルが配置されるところ
  cmd = "go build -o ./tmp/main ." # ビルドコマンド
```
コンテナ内のワーキングディレクトリを`src/app`としているので、airを実行するとローカルでは`app`配下に`tmp/main`が配置されるようになります。

また、コードの変更を検出→ビルド＆再起動についてですが、あくまでairが動いているのはコンテナ内です。
ローカルのソースコードを編集してなぜコンテナ内のairがそれを察知する...?という疑問が生じますが、それは`compose.yml`で記述する**バインドマウント**によるものです。
ローカルのディレクトリ・ファイルがコンテナ内にマウントされ、ローカルの変更はコンテナ内に即座に反映されるようになります。

ホットリロード、超便利です。

https://github.com/air-verse/air
https://qiita.com/urakawa_jinsei/items/44b27d2c23d1c8bb68d7

# Makefileでタスク自動化
golangの開発では、複数のコマンドをMakefileに記載することで作業を効率化するケースが多いようです。
以下にコードを記載します。現段階では使用しないものばかりですが、いくつかのタスクについては後に使用していきます。
ルートディレクトリに`Makefile`を作成してください。
:::: details Makefileコード
```Makefile:Makefile
help: # コマンド確認
	@echo "\033[32mAvailable targets:\033[0m"
	@grep "^[a-zA-Z\-]*:" Makefile | grep -v "grep" | sed -e 's/^/make /' | sed -e 's/://'


##############
### テスト ####
##############

# テスト処理の共通化
# パラメータ:
# - path=<テスト対象のパス> (デフォルト: ./...)
# - opts=<追加オプション> (デフォルト: なし)
# - tags=<ビルドタグ> (デフォルト: なし)
define tests
	$(if $(TEST_TAGS),\
		go test -v -timeout 10m -tags=$(TEST_TAGS) $(TEST_PATH) $(TEST_OPTIONS),\
		go test -v -timeout 10m $(TEST_PATH) $(TEST_OPTIONS)\
	)
endef

# appディレクトリの全体テスト
# コマンド例: $ make test-app opts="-run TestXxx"
test-app:
	$(eval TEST_PATH=./...)
	$(eval TEST_TAGS=$(tags))
	$(eval TEST_OPTIONS=${opts})
	@echo "Running all tests in app..."
	cd ./app && $(call tests)

# ドメイン層のテスト
# コマンド例: $ make test-domain path=./... opts="-run TestXxx"
test-domain:
	$(eval TEST_PATH=$(or $(path),./...))
	$(eval TEST_TAGS=$(tags))
	$(eval TEST_OPTIONS=${opts})
	@echo "Running tests in domain..."
	cd ./app/domain && $(call tests)

# ユースケースのテスト
# コマンド例: $ make test-usecase path=./... opts="-run TestXxx"
test-usecase:
	$(eval TEST_PATH=$(or $(path),./...))
	$(eval TEST_TAGS=$(tags))
	$(eval TEST_OPTIONS=${opts})
	@echo "Running tests in usecase..."
	cd ./app/application/usecase && $(call tests)

# リポジトリのテスト
# コマンド例: $ make test-repo path=./... opts="-run TestXxx"
test-repo:
	$(eval TEST_PATH=$(or $(path),./...))
	$(eval TEST_TAGS=$(tags))
	$(eval TEST_OPTIONS=${opts})
	@echo "Running tests in repository..."
	cd ./app/infrastructure/repository_test && $(call tests)

# クエリサービスのテスト
# コマンド例: $ make test-query path=./... opts="-run TestXxx"
test-query:
	$(eval TEST_PATH=$(or $(path),./...))
	$(eval TEST_TAGS=$(tags))
	$(eval TEST_OPTIONS=${opts})
	@echo "Running tests in queryservice..."
	cd ./app/infrastructure/queryservice_test && $(call tests)

# pkgディレクトリのテスト
# コマンド例: $ make test-pkg path=./... opts="-run TestXxx"
test-pkg:
	$(eval TEST_PATH=$(or $(path),./...))
	$(eval TEST_TAGS=$(tags))
	$(eval TEST_OPTIONS=${opts})
	@echo "Running tests in pkg..."
	cd ./pkg && $(call tests)

test-integration:
	$(eval TEST_PATH=$(or $(path),./...))
	$(eval TEST_TAGS=$(tags))
	$(eval TEST_OPTIONS=${opts})
	@echo "Running tests in integration"
	cd ./app/infrastructure/api_test/integration && $(call tests) -tags=integration

### DBマイグレーション ####

MIGRATE_PATH = infrastructure/db/migrations
DB_URL = mysql://user:pswd@tcp(db:3306)/todo-db?parseTime=true

# マイグレーションファイルを作成
# コマンド例: $ make migrate-create name=<migration-name>
migrate-create:
	$(eval NAME=$(or $(name),$(error "Error: Please specify a migration name using name=<name>")))
	@echo "Creating migration file..."
	cd app/ && migrate create -ext sql -dir $(MIGRATE_PATH) -seq $(NAME)

# マイグレーションを適用
# コマンド例: $ make migrate-up
migrate-up:
	@echo "Applying migrations..."
	docker compose run --rm app migrate --path $(MIGRATE_PATH) --database "$(DB_URL)" -verbose up

# マイグレーションをロールバック
# コマンド例: $ make migrate-down
migrate-down:
	@echo "Rolling back migrations..."
	docker compose run --rm app migrate --path $(MIGRATE_PATH) --database "$(DB_URL)" -verbose down

# マイグレーションのバージョンをセット
# migration-upが失敗した時は、最後のバージョンにforceしなおしてから再度upするようにする
# コマンド例: $ make migrate-force version=<version_number>
migrate-force:
	@echo "Forcing database migration version to $(version)..."
	docker compose run --rm app migrate --path $(MIGRATE_PATH) --database "$(DB_URL)" force $(version)

#############

	@echo "Generating query in sql by sqlc..."
	cd ./app/infrastructure/db/sqlc && sqlc generate

###################

###################
go-gen:
```

# GithubActionsでCI自動化
GithubActionsのコードがよくわからん＆知らん！な方は以下の記事がおすすめです。
https://zenn.dev/kiwichan101kg/articles/2d6850ff72bc98

ドメイン層、リポジトリ、ユースケース等々の大量の単体テスト、エンドポイントの統合テストと、開発が進むにつれてテスト項目は膨れ上がっていきます。コードを実装し、そのコードのテストコードを書いたならば、もちろん手元でテストを実行しますが、それ以外のテストもいちいちテストしていると面倒です。Makefileでタスク登録はしたものの、`git push`する前にいちいちテストするのは面倒＆テストし忘れる可能性もあるわけです。
そこで便利なのが、**Github Actionsを用いた継続的インテグレーション**です。今回は、`git push`でmainブランチにプッシュするたびにテストを走らせるようにします。
https://docs.github.com/ja/actions/about-github-actions/about-continuous-integration-with-github-actions

具体的には、CIワークフローをymlファイルに記述していきます。
ルートディレクトリから`.github/workflows/test.yml`を作成して、以下のコードを記述orコピペしてください。

::::details workflowsのコードを見る
```yml:.github/workflows/test.yml
name: test

on:
    # トリガー
    push:
        branches:
            - main
        # 非機能要件のファイルの変更は除外
        paths-ignore:
            - "app/docs/**"
            - "Dockerfile.**"
            - "compose.yml"
            - "air.toml"
jobs:
    # ユニットテスト
    unit-test:
        name: Run Unit Tests
        runs-on: ubuntu-latest
        steps:
            # チェックアウト
            - name: Checkout Code
              uses: actions/checkout@v4
            # Goのセットアップ
            - name: Go Setup
              uses: actions/setup-go@v5
              with:
                # goバージョンを参照するファイル
                go-version-file: app/go.mod
                # キャッシュ
                cache: true
                # 依存関係のキャッシュにおける追跡ファイル
                cache-dependency-path: app/go.sum
            # マルチモジュールを１つのワークスペースで管理
            - name: Setup Workspace
              run: go work init ./pkg ./app
            # appモジュールのテスト
            - name: Run App Test
              run: make test-app
            # pkgモジュールのテスト
            - name: Run Pkg Test
              run: make test-pkg
     # インテグレーションテスト
    integration-test:
        name: Run Integration Tests
        runs-on: ubuntu-latest
        steps:
            # チェックアウト
            - name: Checkout Code
              uses: actions/checkout@v4
            # Goのセットアップ
            - name: Go Setup
              uses: actions/setup-go@v5
              with:
                go-version-file: app/go.mod
                cache: true
                cache-dependency-path: app/go.sum
            # マルチモジュールを１つのワークスペースで管理
            - name: Setup Workspace
              run: go work init ./pkg ./app
            - name: Run Api Integration Test
              run: make test-integration
```
