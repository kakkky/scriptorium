# `net/http`におけるサーバー・ルーティングの処理
`net/http`におけるサーバー・ルーティングの処理がどのように行われているのかをなんとなく理解し、整理することがこのセクションの目的です。
ご自身でもコードリーディングを行い、実際に処理を追っていただければ、より理解しやすいと思います。VSCodeなどであれば簡単に定義ジャンプできますので、ぜひやって見てください。

それでは、サーバ起動処理・ルーティング処理を見ていきましょう。

単純にサーバーを起動するなら、`http.ListenServe()`関数を使用するだけでそれが可能です。
```go
http.ListenAndServe(":8080", nil)
```
ハンドラは以下のように登録できましたね(11章より)。
```go
http.HandleFunc("GET /",func (w http.ResponseWriter, r *http.Request){...})
```
### `http.ListenServe()`
`http.ListenAndServe()`関数の中では、`*http.Server`構造体を生成した後で、`*http.Server`型の`ListenAndServe()`メソッドが呼ばれているようです。
```go
// ListenAndServe always returns a non-nil error.
func ListenAndServe(addr string, handler Handler) error {
	server := &Server{Addr: addr, Handler: handler}
	return server.ListenAndServe()
}
```

### `http.Server`構造体
`http.Server`型には、サーバーを操作するためのメソッドが定義されています(一部抜粋)。
```go
func (srv *http.Server) ListenAndServe() error
func (srv *http.Server) ListenAndServeTLS(certFile string, keyFile string) error
func (srv *http.Server) Shutdown(ctx context.Context) error
```

構造体の中身は以下のようになっています。
```go
type Server struct {
	// Addr は、サーバーがリッスンする TCP アドレスを "host:port" の形式で指定します。
	// 空の場合は、デフォルトで ":http"（ポート 80）が使用されます。
	Addr string

	// リクエストを処理するハンドラー。
	// nil の場合はデフォルトで http.DefaultServeMux が使用されます。
	Handler Handler 

	// (本当はもっとフィールドがあります)
}
```
`http.ListenAndServe()`の第二引数には`nil`を入れていたので、`Server`構造体の`Handler`フィールドには`nil`が入ることになりますね。

そこで、`Handler`フィールドのコメントに注目すると、
```go
// nil の場合はデフォルトで http.DefaultServeMux が使用されます。
```
とありますね。

この`http.DefaultServeMux`は**マルチプレクサ**と呼ばれるものです。

`http.ListenAndServe()`関数の第二引数に`nil`を入れると、デフォルトのマルチプレクサを使用してくれるようです。


### マルチプレクサ(`http.ServeMux`)
マルチプレクサとは、いわゆる「ルーティングハンドラ」と読み替えることができます。
これも`http.Handler`インターフェースを満たしています。

リクエストが来ると、登録されたパス・ハンドラの組み合わせに従って、リクエストを振り分けます。以下はそれを表した図です。

![](https://storage.googleapis.com/zenn-user-upload/62502fedfe44-20250202.png)

golangにおいて**マルチプレクサは`http.ServeMux`型として表現され**ており、`http.ServeMux`型には、ハンドラを登録するためのメソッドが定義されています(一部抜粋)。
```go
func (mux *ServeMux) Handle(pattern string, handler Handler)
func (mux *ServeMux) HandleFunc(pattern string, handler func(ResponseWriter, *Request))
func (mux *ServeMux) register(pattern string, handler Handler)
```
実際にハンドラーをルーティングに登録するのは`register()`メソッドです。
`Handle()`と`HandleFunc()`メソッドは、`register()`メソッドを呼び出すためのものです。

`*http.ServeMux`型のインスタンス、つまりマルチプレクサを自身で用意して、メソッドを呼び出しを行います。
```go
mux:=http.NewServeMux() // マルチプレクサを用意

mux.Handle("GET /",handler)
mux.HandleFunc("GET /",func(rw http.ResponseWriter,r *http.Request))
```
`http.NewServeMux()`関数によってマルチプレクサを用意できます。

### まとめ
ここまでの話で、サーバー関連は`http.Server`型が、ルーティング関連は`http.ServeMux`型がといったように処理が分離されていると整理することができます。

| 型                  | 役割                             | メソッド（例）                                  |
|---------------------|----------------------------------|------------------------------------------|
| **`http.Server`**    | サーバー関連の処理               | ・ `ListenAndServe()`：サーバーを起動しリクエストを待機    <br> ・ `Shutdown()`：サーバーを安全にシャットダウン       |
| **`http.ServeMux`**  | ルーティング関連の処理          | ・ `Handle()`：パターンに対してハンドラーを登録           <br> ・ `HandleFunc()`：関数型のハンドラーを登録           |


::::message
#### `http.Handle()`関数と`http.HandleFunc()`関数
`http.ServeMux`型の`Handle()`メソッドと`HandleFunc()`メソッドが登場して、若干混乱するかもしれないと思ったので、`http.Handle()`関数と`http.HandleFunc()`関数を改めてここで取り上げておきます。

どちらの関数も、ルーティングにハンドラを登録できるのでしたね。
| メソッド名       | 説明 |
|-----------------|------|
| `http.Handle()`        | `http.Handler` を満たす構造体をルーティングに登録する。|
| `htp.HandleFunc()`    | `func(ResponseWriter, *Request))`のシグネチャをとる関数を`HandlerFunc(handler)`でキャストし、`http.Handler`を満たす形で登録する。|

これらの関数はどちらも、内部でデフォルトのマルチプレクサに対してハンドラを登録しています。
```go
func Handle(pattern string, handler Handler) {
    DefaultServeMux.register(pattern, handler)
}

func HandleFunc(pattern string, handler func(ResponseWriter, *Request)) {
     DefaultServeMux.register(pattern, HandlerFunc(handler))
}
```
デフォルトのマルチプレクサは以下のように定義されています。
```go
// DefaultServeMux is the default ServeMux used by Serve.
var DefaultServeMux = &defaultServeMux

var defaultServeMux ServeMux
```

**`http.Handle()`と`http.HandleFunc()`を使用すると、マルチプレクサを意識せずにハンドラをルーティングに登録することができる**と言えます。

![](https://storage.googleapis.com/zenn-user-upload/c51d880eed2c-20250202.png)

`http.ListenAndServe()`関数の第二引数に`nil`を入れると、デフォルトのマルチプレクサが利用されるのでしたね。

# 実装方針
HTTPサーバー周りの実装と、ルーティング周りの実装をどのようにしていくかの方針を述べていきます。

### 「サーバー周りの処理」と「ルーティング周りの処理」の分離
見出しの通りですが、サーバー起動の処理と、ルーティング周りの処理は分離して実装していきます。

反対に、「分離しない」実装はどのようになるかというと、以下のやり方になります。
- `http.Handle()`か`http.HandleFunc()`をつかってハンドラを登録
- `http.ListenAndServe(":8080",nil)`でサーバーを起動

ハンドラの登録とサーバー起動の処理が関数として分かれてはいるものの、ルーティングを司る`http.ServeMux`の存在がほとんど隠蔽されています。デフォルトのマルチプレクサが内部で使用されていたのでしたね。

今回は、マルチプレクサを自身で用意し、それに対してハンドラを登録することで、サーバー処理を司る`http.Server`型からルーティング処理を切り離します。
::::message 
#### ルーティング(`http.ServeMux`)を切り離すメリット
ルーティング機能を切り離すことによって、拡張性を持たせることが可能です。

巷には、ルーティングの機能を提供するパッケージが多く存在します。代表的なものに、以下の二つなどがあります。
- [chi](https://github.com/go-chi/chi)
- [gorilla/mux](https://github.com/gorilla/mux)

ルーティング、つまりマルチプレクサの機能を提供してくれるものです。
そして、これら二つのマルチプレクサは、`http.Handler`インターフェースを満たし、`net/http`パッケージと互換性を持って実装されています。

そのため、全く同じようにしてハンドラへの登録ができます。また、`http.Handler`インターフェースを満たしているため、`http.ListenAndServe()`関数に渡すことができます(第二引数は`http.Handler`型)。
```go
// net/http
mux := http.NewServeMux()
mux.Handle("/", handlerA)
mux.HandleFunc("/products", handlerB)

http.ListenAndServe(":8080",mux)

// chi
r := chi.NewRouter()
r.Handle("/", handlerA)
r.HandleFunc("/products", handlerB)

http.ListenAndServe(":8080",r)

// gorilla/mux
r := mux.NewRouter()
r.Handle("/", handlerA)
r.HandleFunc("/products", handlerB)

http.ListenAndServe(":8080",r)
```
このように、書き方が変わらないということは、ルーティング機能のみを他ライブラリに乗り換えるなどが容易になり、拡張性が見込めると言えそうですね。
::::

`http.Sever`構造体は以下のようになっていました。
```go
type Server struct {
	Addr string
	Handler Handler // マルチプレクサが入る
	// (本当はもっとフィールドがあります)
}
```
「サーバー操作には`http.Server`のメソッドを利用し、`http.Server`構造体の`Handler`フィールドに代入するマルチプレクサを別で生成する」といったやり方で、ルーティング処理を切り離すようにします。

次から、実装に入っていきます。

# HTTPサーバー起動処理の実装
まずはサーバー処理の方から実装していきましょう。

::::details サーバー処理の実装
```go:app/infrastructure/server/server.go
package server

import (
	"context"
	"log"
	"net/http"
	"os"
	"os/signal"
	"syscall"
	"time"

	"golang.org/x/sync/errgroup"
)

// *http.Server型をラップする
type server struct {
	srv *http.Server
}

// 独自のserver.Server型を返すコンストラクタ
// main関数でマルチプレクサを渡す
func NewServer(port string, mux http.Handler) *server {
	return &server{
		&http.Server{
			Addr:    port,
			Handler: mux,
		},
	}
}

// サーバーを起動する
func (s *server) Run(ctx context.Context) error {
	ctx, stop := signal.NotifyContext(ctx, os.Interrupt, syscall.SIGTERM)
	// シグナルの監視をやめてリソースを開放する
	defer stop()
	eg, ctx := errgroup.WithContext(ctx)
	eg.Go(func() error {
		// サーバー起動中にエラーが起きると、ctxに伝達される（Shutdownによるエラーは正常なので無視）
		log.Printf("server is runnning at port %q...", s.srv.Addr)
		if err := s.srv.ListenAndServe(); err != nil && !errors.Is(err, http.ErrServerClosed) {
			log.Printf("http server on %s failed : %+v", s.srv.Addr, err)
			return err
		}
		log.Printf("The server on %s is gracefully shutting down", s.srv.Addr)

		return nil
	})
	// サーバーからのエラーとシグナルを待機する
	<-ctx.Done()
	// シャットダウンをするまでのタイムアウト時間を設定
	ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
	defer cancel()
	if err := s.srv.Shutdown(ctx); err != nil {
		log.Fatalf("failed to shutdown http server on %s : %+v", s.srv.Addr, err)
	}
    log.Println("server was successfully shut down gracefully")
	// ゴルーチンのクロージャ内のエラーを返す
	// ゴルーチンを待機する
	return eg.Wait()
}
```

### `*http.Server`をラップした`server`構造体
内部に`srv`フィールドとして`http.Server`をもつ、`server`構造体を定義しています。
`NewServer()`関数によって独自にラップした`*server`型を返します。
```go
// *http.Server型をラップする
type server struct {
	srv *http.Server
}

// 独自のserver.Server型を返すコンストラクタ
// main関数でマルチプレクサを渡す
func NewServer(port string, mux http.Handler) *server {
	return &server{
		&http.Server{
			Addr:    port,
			Handler: mux,
		},
	}
}
```
`main.go`における`main関数`でサーバー起動処理としてこの関数を呼び出します。
その際、**引数にルーティングを登録したマルチプレクサ（`http.ServeMux`）を渡すことで、サーバー処理とルーティング処理の分離を図る**ようにしています。

そして、`Run()`関数内でサーバー起動に`http.Server`型の`ListenAndServe()`メソッドを呼び出しています。
```go
s.srv.ListenAndServe()
```

ここで、別に`http.ListenAndServe()`関数でもよくないか？と思われる方もいるかもしれません。
このようにしている理由は二つで、
- サーバー処理のみを扱う`http.Server`型を使用することで責務が明確化する
- グレースフルシャットダウンを行える`Shutdown()`メソッドを使いたい

ざっくりと、「このようにした方が柔軟に実装できるのではないか」という感じでしょうか。

### サーバー起動〜グレースフルシャットダウンの実装
::::message
#### グレースフルシャットダウン

グレースフルシャットダウンとは、

**サーバーが停止する際に、既存の接続やリクエストを適切に処理し終わった後にシャットダウンを行う**

ことです。

すでに受け付けていたリクエストは、そのリクエストの処理が適切に完了するまで待機します。
これによって、安全なサーバーのシャットダウン（切断）を行うというものです。
- [【Go】WebサーバをGraceful Shutdownしてみる(Zenn)](https://zenn.dev/pyotarou/articles/87d43169e0abe0)
::::

サーバー起動〜グレースフルシャットダウンの処理は、`server`独自型に定義した`Run()`メソッドに記述しています。

```go
// サーバーを起動する
func (s *server) Run(ctx context.Context) error {
	ctx, stop := signal.NotifyContext(ctx, os.Interrupt, syscall.SIGTERM)
	// シグナルの監視をやめてリソースを開放する
	defer stop()
	eg, ctx := errgroup.WithContext(ctx)
	eg.Go(func() error {
		// サーバー起動中にエラーが起きると、ctxに伝達される（Shutdownによるエラーは正常なので無視）
		log.Printf("server is runnning at port %q...", s.srv.Addr)
		if err := s.srv.ListenAndServe(); err != nil && !errors.Is(err, http.ErrServerClosed) {
			log.Printf("http server on %s failed : %+v", s.srv.Addr, err)
			return err
		}
		log.Printf("The server on %s is gracefully shutting down", s.srv.Addr)

		return nil
	})
	// サーバーからのエラーとシグナルを待機する
	<-ctx.Done()
	// シャットダウンをするまでのタイムアウト時間を設定
	ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
	defer cancel()
	if err := s.srv.Shutdown(ctx); err != nil {
		log.Fatalf("failed to shutdown http server on %s : %+v", s.srv.Addr, err)
	}
	log.Println("server was successfully shut down gracefully")
	// ゴルーチンのクロージャ内のエラーを返す
	// ゴルーチンを待機する
	return eg.Wait()
}
```
とても長く、複雑に見えますね。

実装コードを順に見ていきましょう。

#### シグナルをハンドリングする
以下のコードで、新たな`context.Context`を生成していますね。
```go
ctx, stop := signal.NotifyContext(ctx, os.Interrupt, syscall.SIGTERM)
// シグナルの監視をやめてリソースを開放する
defer stop()
```

リクエストの処理中に「コンテナの終了」や「サーバープログラムの終了」が行われた場合は、処理の完了を待機してからサーバーを切断する、グレースフルシャットダウンが行われることが望ましいです。

そこで、「コンテナの終了」や「サーバープログラムの終了」がアプリケーションプロセスに送るシグナルを検知するようにし、検知した場合にはグレースフルシャットダウンを行うという流れにしなければなりません。

`signal.NotifyContext()`関数は、引数にとったシグナルの受信を検知してくれます。
今回、引数にとったシグナルは以下のようなものです。
| シグナル             | 説明                                              |
|----------------------|---------------------------------------------------|
| `SIGINT (os.Interrupt)` | ユーザーがCtrl + Cで送信する中断シグナル。プログラムを中断するために使用されます。  |
| `SIGTERM`             | システムから終了を依頼するシグナル。通常、プロセスが終了する準備をするために使用されます。  |

`signal.NotifyContext()`関数は内部でコンテキストにキャンセル機能を追加しています。
```go
func NotifyContext(parent context.Context, signals ...os.Signal) (ctx context.Context, stop context.CancelFunc) {
    // キャンセル機能追加
    ctx, cancel := context.WithCancel(parent)
    // 省略
    return c, c.stop
}
```
つまり、シグナルを検知したら、コンテキストを通じてキャンセル通知を送れるようになっているのです。

シグナルの検知は以下のようにして待機することができます。（キャンセル通知を受け取るまで、処理がブロッキングするからです）
```go
<-ctx.Done()
```

#### ゴルーチンでサーバーを起動する
サーバーの起動は別ゴルーチンとして行い、リクエストを待機するようにしています。
```go
func (s *server) Run(ctx context.Context) error {
    //省略

    // `*errgroup.Group`型・新たなコンテキストの生成
    eg, ctx := errgroup.WithContext(ctx)
    eg.Go(func() error {
        // サーバー起動中にエラーが起きると、ctxに伝達される（Shutdownによるエラーは正常なので無視）
        if err := s.srv.ListenAndServe(); err != nil && !errors.Is(err, http.ErrServerClosed) {
            log.Printf("http server on %s failed : %+v", s.srv.Addr, err)
            return err
        }
    
        //省略
    
        return nil
    })
    // サーバーからのエラーとシグナルを待機する
    <-ctx.Done()
    
    // 省略(シャットダウン処理)
    
    // ゴルーチンのクロージャ内のエラーを返す
    // ゴルーチンを待機する
    return eg.Wait()
}
```
`errgroup`（`sync`パッケージにおけるサブパッケージ）における、`*errgroup.Group`型の`Go()`メソッドによってゴルーチンを起動しています。
```go
func (g *Group) Go(f func() error) {...}
```
`Go()`メソッドは`error`を返すクロージャを引数にとるため、クロージャ内にて`s.srv.ListenAndServe()`メソッドを使用しています。この`http.Serve`型の`ListenAndServe()`メソッドこそがサーバーの起動を行ってくれるものでしたね。

この`errgroup`型の`Go()`メソッドによって起動したゴルーチン内で処理を行うことで、エラーハンドリングが容易になります。
というのも、ゴルーチン内でエラーが起きると、それをコンテキストによって検知できるのです。
```go
// `*errgroup.Group`型・新たなコンテキストの生成
eg, ctx := errgroup.WithContext(ctx)
```
`errgroup`に用意された`WithContext()`関数により、新たなコンテキストが作成されています。
関数内部では、`context.WithCancelCause()`関数が使用されており、キャンセル通知を受け取れるようになっています。

`errgroup.WithContext(ctx)`の引数にとった親コンテキストは、シグナル検知機能を追加した`ctx`です。
それによって新たに作成されるコンテキストはつまり、
- シグナルを検知
- ゴルーチン内エラーを検知

できるようになっていると言うことです。
以下では、「シグナルを検知」と「ゴルーチン内エラー検知」によるキャンセル通知を待ち受けていると言うことになりますね。
```go
<-ctx.Done()
```
つまり、「シグナルを検知」or「ゴルーチン内エラー検知」してキャンセル通知がコンテキストに送られると、その下のシャットダウン処理に進んでいくと言う感じです。

`Run()`関数の最後に記述してある次の部分では、ゴルーチンの終了を待機しています。これにより、ゴルーチンによる処理の完了を待たずして`Run()`関数が終了してしまう、といったことを防げます。
この使い方は`sync.WaitGroup`型のものとそう変わりません。
```go
// ゴルーチンのクロージャ内のエラーを返す
// ゴルーチンを待機する
return eg.Wait()
```
またそれと同時に、ゴルーチン内で起きたエラーを返すようです。

#### `Shutdown()`メソッド
`Shutdow()`メソッドこそがグレースフルシャットダウンを行ってくれるものとなっています。
以下のように定義されています。
```go
// Shutdown は、アクティブな接続を中断することなくサーバーをグレースフルシャットダウンします。
// Shutdown の動作は、まずすべてのリスナーを閉じ、次にアイドル状態の接続をすべて閉じ、
// その後、すべての接続がアイドル状態に戻るのを無期限に待ってからシャットダウンします。
// 指定されたコンテキストの期限がシャットダウン完了前に切れた場合、Shutdown は
// そのコンテキストのエラーを返します。そうでなければ、[Server] の基盤となるリスナー
// を閉じる際に発生したエラーを返します。
//
// Shutdown が呼び出されると、[Serve]、[ListenAndServe]、[ListenAndServeTLS] は
// 直ちに [ErrServerClosed] を返します。そのため、プログラムが即座に終了せず、
// Shutdown の戻りを待つようにしてください。
//
// 一度 Shutdown がサーバーに対して呼び出されると、そのサーバーは再利用できません。
// その後、Serve などのメソッドを呼び出しても [ErrServerClosed] を返します。
func (srv *Server) Shutdown(ctx context.Context) error {...} 
```
`Shutdown()`メソッドを扱う上で、コメントに書かれている以下の２点に注意します。
- コンテキストのタイムアウトを検知すると、エラーが返る
- `ListenAndServe()`は`ErrServerClosed`エラーを返す

まず、前者についてですが、以下のようにコンテキストにタイムアウトを設定しています(時間は適当に設定しています)。
```go
// シャットダウンをするまでのタイムアウト時間を設定
ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel()
if err := s.srv.Shutdown(ctx); err != nil {
    log.Fatalf("failed to shutdown http server on %s : %+v", s.srv.Addr, err)
}
log.Println("server was successfully shut down gracefully")
```
`Shutdown()`には以下のようにコンテキストのキャンセル通知を待ち受けている記述が見られます。
```go
select {
case <-ctx.Done():
	return ctx.Err()
```

また後者について、`ListenAndServe()`は`Shutdown()`により`ErrServerClosed`を返すとあります。コードリーディングしてそれを確かめてみます。
`Sever`構造体には、シャットダウン中かどうかのフラグとして`inShutdown`と言うフィールドがあるようですね。
```go
type Server struct {
    // 他は省略
   inShutdown atomic.Bool // true when server is in shutdown
}
```
`Shutdown()`では、初っ端に、おそらく`inShutdown`フィールドを`true`に変更しているであろう処理が見受けられます。
```go
func (srv *Server) Shutdown(ctx context.Context) error {
	srv.inShutdown.Store(true)
    // 省略
}
```
`ListenAndServe()`では、、`inShutdown`フィールドが`true`であれば`ErrServerClosed`エラーを返すといった記述が見られます。
```go
func (srv *Server) ListenAndServe() error {
	if srv.shuttingDown() {
		return ErrServerClosed
	}
    // 省略
}
```

なるほど、確かに`Shutdown()`すると`ListenAndServe()`から`ErrServerClosed`が返っていますね。
ここで注意して実装したいのが、`s.srv.ListenAndServe()`から返るエラーの中でも`ErrServerClosed`は「正常」なものであるということです。

それを考慮して、`s.srv.ListenAndServe()`からの`err`があってもそれが`ErrServerClosed`だった場合はクロージャとして`error`を返さないようにします。
```go
eg.Go(func() error {
    // サーバー起動中にエラーが起きると、ctxに伝達される（Shutdownによるエラーは正常なので無視）
    log.Printf("server is runnning at port %q...", s.srv.Addr)
    if err := s.srv.ListenAndServe(); err != nil && !errors.Is(err, http.ErrServerClosed) {
        log.Printf("http server on %s failed : %+v", s.srv.Addr, err)
        return err
    }
    log.Printf("The server on %s is gracefully shutting down", s.srv.Addr)

    return nil
})
```
このようにしないと、正常にシャットダウンを行っているにも関わらず、それがゴルーチン内でエラーとなり、`errgroup`にエラーが渡ることになります。つまり、`eg.Wait()`によって`Run()`メソッドからエラーを返してしまうことになります。

それは期待しない挙動なので、`errors.Is()`によってエラーの値を判別するようにしています。

このような工夫で、シャットダウン時には、ゴルーチンが正常終了するようになっています。

# ルーティングの実装
先のサーバー処理を行う`server`型(独自型)は、`http.Server`型をラップしたものでした。
```go
// 独自型
type server struct {
	srv *http.Server
}
// net/http
type Server struct {
    Addr    string
    Handler Handler
}
```
ラップしてある`http.Server`型の`Handler`フィールドこそ、マルチプレクサ（ルーティングハンドラ）です。

`server`独自型のインスタンスを返す`NewServer()`関数には、ルーティングを登録したマルチプレクサを渡します。
```go
func NewServer(port string, mux http.Handler) *server {
	return &server{
		&http.Server{
			Addr:    port,
			Handler: mux,   // ルーティング登録ずみのマルチプレクサが入る
		},
	}
}
```

つまり、ここで言う「ルーティング処理の実装」とは、

**`http.ServeMux`型にルーティングを登録し、それを返すようにする処理**

を書くことだと言えるでしょう。

最終的に`main()`関数では以下のようにサーバーを起動する処理を呼び出します。
```go
srv := server.NewServer(
    cfg.Server.Port,
    router.NewMux(),  // ルーティング登録済みのマルチプレクサを渡す
)
srv.Run(ctx) // サーバー起動
```

ルーティングを登録したマルチプレクサを返す`NewMux()`関数を実装していきましょう。

ミドルウェアを初期化する処理
```go:app/infrastructure/router/middlewares.go
package router

import (
	"net/http"

	"github.com/kakkky/app/adapter/presentation/middleware"
	"github.com/kakkky/app/adapter/repository"
	authUsecase "github.com/kakkky/app/application/usecase/auth"
	"github.com/kakkky/app/infrastructure/auth"
	"github.com/kakkky/app/infrastructure/kvs"
)

// ミドルウェア
var (
	authorization func(h http.Handler) http.Handler
	logger        func(h http.Handler) http.Handler
)

// ミドルウェアを初期化する
func initMiddlewares() {
	authorization = middleware.Authorication(
		authUsecase.NewAuthorizationUsecase(
			auth.NewJwtAuthenticator(),
			repository.NewJwtAuthenticatorRepository(kvs.NewRedisCommander()),
		),
	)
	logger = middleware.Logger
}

//　以下は既に実装済みです。

// 適用させたい順で、ミドルウェアを引数に入れる
// composeMiddlewares(M1,M2,M3)とした場合、M1(M2(M3()))といったようにラップされたミドルウェアを返す
func composeMiddlewares(middlewares ...func(http.Handler) http.Handler) func(http.Handler) http.Handler {
	return func(h http.Handler) http.Handler {
		for i := range middlewares {
			h = middlewares[len(middlewares)-(i+1)](h)
		}
		return h
	}
}
```

### ハンドラー・ミドルウェアを初期化
#### `initHandlers()`関数 
`NewMux()`は`initHandlers()`関数を呼び出していますが、これは内部で３つの関数を呼び出しているだけです。
```go
func initHandlers() {
	initAuthHandlers()
	initUserHandlers()
	initTaskHandlers()
}
```
それぞれは、パッケージ変数として設定したハンドラーを初期化する処理が記述されています。

#### ハンドラー初期化時に依存性を注入する
ルーティングにハンドラー（`http.Handler`型の構造体）を登録するには、ハンドラーの初期化をする必要があります。(どのハンドラにも、`NewXxxHandler()`関数を定義していました。それです。)

ハンドラーは、ユースケース処理を呼び出すものでした。
そのユースケースは、リポジトリやクエリサービス、ドメインサービスの処理を呼び出し、操作していました。
ハンドラーが依存する「ユースケース」コンポーネントは具体型ですが、その「ユースケース」の依存先はインターフェースとしていたことを思い出してください。

以下は、`PostUserHandler`が抱えている依存先を示した図です。
![](https://storage.googleapis.com/zenn-user-upload/8d1202dab034-20250204.png)

インターフェースは単なる「振る舞い」でしたね。
ハンドラーの初期化に際して、

インターフェースという「抽象型」に対して、実装の詳細である「具体型」を注入してやる必要があります。

これを、**Dependency Injection(依存性の注入)**、略してDIといいます。

例えば、ユースケースはリポジトリを利用していましたが、依存していたのはリポジトリのインターフェースでしたね。
そこに、リポジトリの具体型である、`repository.userRepository`をDIします。

また、そのリポジトリもORMを抽象化した`repository.Querier`インターフェースに依存していました。
そこに、sqlcを利用する具体型である`sqlc.SqlcQuerier`をDIしています。

![](https://storage.googleapis.com/zenn-user-upload/c1a7c123a4f8-20250204.png)

コードで表すと、以下のようになります。
```go
postUserHandler = user.NewPostUserHandler(  //ハンドラーの初期化
    userUsecase.NewRegisterUsecase( //ユースケースの初期化
        repository.NewUserRepository(sqlc.NewSqlcQuerier()),  //リポジトリ・sqlc具体型の初期化
        userDomain.NewUserDomainService(repository.NewUserRepository(sqlc.NewSqlcQuerier())),  //ユーザードメインサービスの初期化
    ),
)
```

### ハンドラーをルーティングに登録
`registerRoutes()`では、ハンドラをマルチプレクサに登録しています。
```go

	{
		mux.Handle("POST /users", composeMiddlewares(logger)(postUserHandler))
		mux.Handle("DELETE /users/me", composeMiddlewares(logger, authorization)(deleteUserHandler))
		mux.Handle("GET /users", composeMiddlewares(logger, authorization)(getUsersHandler))
		mux.Handle("PATCH /users/me", composeMiddlewares(logger, authorization)(updateUserHandler))
```

`http.ServeMux`型の`Handle()`メソッドや`HandleFunc()`メソッドに関しては先述しました。
また、前章で実装した`composeMiddlewares()`関数を使用することでミドルウェアを適用していています。

ユーザー登録のエンドポイント（`POST /users`）に関しては、認可制御を設けないため、ミドルウェアをロガーのみに絞っています。

ここでは、「ルーティングパターン」について取り上げます。

#### 強化されたルーティングパターン
`Handle()`メソッドなどについては説明しましたが、ルーティングパターンについてはまだ説明していませんでした。
ルーティングパターンと言っているのは、以下の`pattern`のことです。
```go
func (mux *http.ServeMux) Handle(pattern string, handler http.Handler)
```

Go1.22から、ルーティングパターンは拡張されたようです。
https://tip.golang.org/doc/go1.22#enhanced_routing_patterns

バージョンアップによる拡張で以下のようなことが可能になりました。
- HTTPメソッドの指定
- パスパラメータの表現

順に取り上げてみます。

**＜HTTPメソッドの指定＞**
あるパスに対して、リクエストを受けつけるHTTPメソッドを指定できるようになりました。
以下のように、`HTTPメソッド /パス`の形式で記述できます。
```go
"POST /users"
```

**＜パスパラメータの表現＞**
パスパラメータとして扱いたい部分を `{}`で囲むことでそれを表現できます。
例えば、以下のように記述すると、
```go
"GET /tasks/{id}"
```
以下のようなルーティングパターンがマッチするようになります。
```go
"GET /tasks/1"   //idが1のタスクを取得
"GET /tasks/2"   //idが2のタスクを取得
"GET /tasks/3"   //idが3のタスクを取得
```

また、パスパラメータを取得するために、`PathValue()`メソッドが用意されています。
```go
func (r *http.Request) PathValue(name string) string
```
このメソッドは、いくつかのハンドラーで使用していました。
```go
func (gth *GetTaskHandler) ServeHTTP(rw http.ResponseWriter, r *http.Request) {
    // GET /tasks/1 でリクエストを受け付けた場合、idには"1"が入る
    id := r.PathValue("id")

    // 省略
}
```
::::message
`/hoge/{id}`の`{id}`の部分は**ワイルドカード**とも呼ばれています。
`{id}`が何であってもルーティングパターンとマッチするという点で、確かにワイルドカードと言えそうですね。
他にも、`/hoge/{id...}`とすることで、`/hoge`といったパスパラメータがないパターンもマッチするように出来る書き方もあります。
::::

https://github.com/swaggo/http-swagger

::::message
今回使用している`swaggo/http-swagger`は、`net/http`に対応したものです。
つまり、`net/http`で実装されたハンドラーを提供してくれます。
    
swaggoは、非常に多くのwebフレームワークをサポートしています。
- [サポートしているフレームワーク一覧](https://github.com/swaggo/swag?tab=readme-ov-file#supported-web-frameworks)

```go:app/infrastructure/router/mux.go
import (
```
