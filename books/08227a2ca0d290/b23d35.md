# リポジトリの責務
リポジトリは、オブジェクトの永続化（保存）や再構築（復元）といったデータストア操作を担う役割を果たします。この「データストアの操作」をリポジトリという専用のコンポーネントに切り出すことで、ビジネスロジックと分離され、責務が明確化されます。

たとえば、今回使用するデータストアは MySQL と Redis ですが、ドメインロジックはその「詳細」を知る必要はありません。RDBであろうと NoSQLであろうと、「データを保存・取得する」という役割を果たせれば十分です。リポジトリを介することで、データストアの種類を抽象化し、柔軟かつ一貫した方法で操作できるようになります。

![](https://storage.googleapis.com/zenn-user-upload/b2143340e155-20250111.png)

# リポジトリの実装方針
リポジトリは、データ操作を抽象的に扱うためのものだという話を上で述べました。

このセクションで重要なのは、**ORM**の扱いです。
Redisは一旦さておき、MySQLなどRDBへの操作は、ORMを用いた方が便利なパターンが多いと思います。
::::message 
### ORM(Object-Relational Mapping)
ORMとは、オブジェクト指向プログラミングのクラスとリレーショナルデータベースのテーブルとの間でデータの変換を自動化する技術です。golangの場合だと、**クラス＝構造体**と読み替えることができます。
これにより、SQLを直接記述することなく、プログラム内のオブジェクトをデータベースの行に対応させて操作できるようになります。データベースとのやり取りは簡素化し、扱いやすくなります。
::::
ORMにはさまざまな種類があります。

https://github.com/taro33333/star-golang-orms

ここで強調したいのは、ORMは「詳細」であるということです。実装でもインフラストラクチャ層に配置します。
今回はsqlcを採用しますが（それに関しても後述）、例えばgormにも簡単に乗り換えられる柔軟性を持たせることは重要です。
それを実現するために必要なことは、**リポジトリをORMの具体型ではなく抽象型、つまりインターフェースに依存させること**です。第5章では**抽象型は「安定」している**ということを述べました。

それに、詳細としてインフラストラクチャ層に配置するORMにインターフェースアダプター層のリポジトリが依存してしまっては依存性のルールにも反してしまいますね。

::::message

# インターフェースを定義する
まずインターフェースの名前を決めます。
ORMを抽象化するためのインターフェースだから、`type Orm interface {..}`としてもいいかもしれません。しかし。ORMはあくまでデータ操作をうまくやってくれるもので、自前で実装するパターンもありえます。
それを踏まえて、「クエリを操作する役割」を担うコンポーネントの抽象型と認識できるように`Querier`という命名にしました。

`app/adapter/repository`ディレクトリを用意し、以下のインターフェースを定義してください。
::::details interface_querier.go の実装
```go:app/adapter/repository/interface_querier.go
package repository

import "context"

// ORMはこのインターフェースを満たすように設計する
type Querier interface {
	DeleteTask(ctx context.Context, id string) error
	DeleteUser(ctx context.Context, id string) error
	FetchAllUser(ctx context.Context) ([]FetchAllUsersRow, error)
	FindTaskById(ctx context.Context, id string) (FindTaskByIdRow, error)
	FindUserByEmail(ctx context.Context, email string) (FindUserByEmailRow, error)
	FindUserById(ctx context.Context, id string) (FindUserByIdRow, error)
	InsertTask(ctx context.Context, arg InsertTaskParams) error
	InsertUser(ctx context.Context, arg InsertUserParams) error
	UpdateTask(ctx context.Context, arg UpdateTaskParams) error
	UpdateUser(ctx context.Context, arg UpdateUserParams) error
}

type FetchAllUsersRow struct {
	ID             string
	Email          string
	Name           string
	HashedPassword string
}

type FindUserByEmailRow struct {
	ID             string
	Email          string
	Name           string
	HashedPassword string
}

type FindUserByIdRow struct {
	ID             string
	Email          string
	Name           string
	HashedPassword string
}

type InsertUserParams struct {
	ID             string
	Name           string
	Email          string
	HashedPassword string
}

type UpdateUserParams struct {
	Name  string
	Email string
	ID    string
}

type FindTaskByIdRow struct {
	ID      string
	UserID  string
	Content string
	State   int32
}

type InsertTaskParams struct {
	ID      string
	UserID  string
	Content string
	State   int32
}

type UpdateTaskParams struct {
	State int32
	ID    string
}
```
::::
実は、このインターフェースはsqlcが生成したコードに寄った記述をしています。
というのも、sqlcはSQLからタイプセーフなGoのコードを生成してくれるもの（後に触れます）で、生成されるコードを財産と捉えて（笑）借用しています。
ただし、このインターフェースはsqlcに依存しているわけではありません。
gormでデータベース操作を行う場合は、このインターフェースに従った実装にすることで、gormに依存しない設計が可能となり、将来的に他のORMに切り替える際にも柔軟に対応できるようになります。

## ユーザーリポジトリ
ドメイン層にはリポジトリインターフェースを定義していました。そのインターフェースを満たす形で実装します。
::::details user_repository.go の実装
```go:app/adapter/repository/user_repository.go
package repository

import (
	"context"
	"database/sql"

	"github.com/kakkky/app/domain/errors"
	"github.com/kakkky/app/domain/user"
)

type userRepository struct {
	querier Querier
}

func NewUserRepository(querier Querier) user.UserRepository {
	return &userRepository{
		querier: querier,
	}
}

func (ur *userRepository) Save(ctx context.Context, user *user.User) error {
	arg := InsertUserParams{
		ID:             user.GetID(),
		Name:           user.GetName(),
		Email:          user.GetEmail().Value(),
		HashedPassword: user.GetHashedPassword().Value(),
	}
	if err := ur.querier.InsertUser(ctx, arg); err != nil {
		return err
	}
	return nil
}

func (ur *userRepository) FindByEmail(ctx context.Context, email user.Email) (*user.User, error) {
	u, err := ur.querier.FindUserByEmail(ctx, email.Value())
	if err != nil && errors.Is(err, sql.ErrNoRows) {
		return nil, errors.ErrNotFoundUser
	}
	if err != nil {
		return nil, err
	}
	user := user.ReconstructUser(
		u.ID,
		u.Email,
		u.Name,
		u.HashedPassword,
	)
	return user, nil
}

func (ur *userRepository) FindById(ctx context.Context, id string) (*user.User, error) {
	u, err := ur.querier.FindUserById(ctx, id)
	if err != nil && errors.Is(err, sql.ErrNoRows) {
		return nil, errors.ErrNotFoundUser
	}
	if err != nil {
		return nil, err
	}
	user := user.ReconstructUser(
		u.ID,
		u.Email,
		u.Name,
		u.HashedPassword,
	)
	return user, nil
}

func (ur *userRepository) FetchAllUsers(ctx context.Context) (user.Users, error) {
	us, err := ur.querier.FetchAllUser(ctx)
	if err != nil {
		return nil, err
	}
	// あらかじめ配列のキャパを確保しておく
	users := make(user.Users, 0, len(us))
	for _, u := range us {
		user := user.ReconstructUser(
			u.ID,
			u.Email,
			u.Name,
			u.HashedPassword,
		)
		users = append(users, user)
	}
	return users, nil
}

func (ur *userRepository) Update(ctx context.Context, user *user.User) error {
	params := UpdateUserParams{
		Name:  user.GetName(),
		Email: user.GetEmail().Value(),
		ID:    user.GetID(),
	}
	if err := ur.querier.UpdateUser(ctx, params); err != nil {
		return err
	}
	return nil
}

func (ur *userRepository) Delete(ctx context.Context, user *user.User) error {
	if err := ur.querier.DeleteUser(ctx, user.GetID()); err != nil {
		return err
	}
	return nil
}

```
::::
`userRepository`には、インターフェース`Querier`を持たせています。
実装の詳細として`SqlcQuerier`を第11章にてDI（依存性の注入）します。

ポイントは、`errors.Is(err, sql.ErrNoRows)`としているところです。
```go
if err != nil && errors.Is(err, sql.ErrNoRows) {
		return nil, errors.ErrNotFoundUser
	}
	if err != nil {
		return nil, err
	}
```
標準である`sql`パッケージには、`ErrNoRows`が定義されています。
```go
// ErrNoRows is returned by [Row.Scan] when [DB.QueryRow] doesn't return a
// row. In such a case, QueryRow returns a placeholder [*Row] value that
// defers this error until a Scan.
var ErrNoRows = errors.New("sql: no rows in result set")
```
入力値としてemailを入力したとして、該当するユーザーが見つからなければそれは「入力値エラー」であり、クライアント側の問題であるドメインエラーと見做せます。そのため、`errors.Is`でエラーの値を判別し、それが`ErrNoRows`(=該当のレコードがない)であればドメインエラー(`errors.ErrNotFoundUser`)を返し、それ以外のエラーならそのまま`err`を返すようにしています。
このように、ドメインエラーをハンドリングできるようにしています。

## sqlcとは
以下が公式ドキュメントになります。

https://sqlc.dev/

他のORMと圧倒的に異なる点であり最大の特徴は、

**SQLからタイプセーフなGoコードを生成する**

ことです。
sqlcを使うと、以下のメリットをもたらします。
- 実行されているSQLクエリがわかる
- 意図せぬN+1を生みにくい

### 実行されているSQLクエリがわかる
SQLを直接記述し、それを元にgoコードが生成されます。そのため、ORMに隠蔽されたクエリの動作を機にする必要がありません。実際に実行されるSQLクエリを正確に把握できるのは非常に開発がしやすいです。

### 意図せぬN+1を生みにくい
gormなどの便利なORMは、GoコードからSQLクエリを生成してくれるため非常に強力ですが、SQL操作が抽象化されている分、N+1問題を発生させるコードを書きやすい側面もあると考えています。

たとえば、以下の記事で紹介されているように Eager Loading を利用すればN+1問題を回避することも可能ですが、設定を間違えると問題が発生するリスクがあります
https://www.ariseanalytics.com/activities/report/20240529/

そもそもSQLを直接書くなら、テーブルをJOINしたクエリを書いて一発で取得できるようにするのが普通？の感覚だと思うので、余計な心配がいらないと筆者は思っています。

言語が異なりますが、筆者はよくrailsで「あっ...N+1キタ」となった経験がよくあります。Active Recordも超便利なので、便利なだけに、中途半端な理解で扱ってしまうとパフォーマンス的にアレな結果になります。

（こう思っているのは筆者だけでしょうか...笑）

このように、SQLクエリ中心の開発にはメリットがあります。

## セットアップ
### 設定ファイルを記述
sqlcについては、すでにコンテナ内にインストールされています。
```Dockerfile
RUN go install github.com/sqlc-dev/sqlc/cmd/sqlc@v1.23.0
```
基本的には公式ドキュメントを参照しています。
`app/infrastructure/db/sqlc`ディレクトリを作成してください。

まず、設定ファイルを作成し、記述していきます。
```yml:app/infrastructure/db/sqlc/sqlc.yml
version: "2"
sql:
  - engine: "mysql"
    queries: "./queries/"
    schema: "../migrations/"
    gen: 
      go:
        package: "sqlc"
        out: "./"
        emit_json_tags: false #構造体にjsonタグをつけない
        emit_prepared_queries: false #プリペアードステートメントは使用しない
        emit_interface: false #インターフェースを生成しない
        emit_exact_table_names: false #テーブル名(s抜き)がそのまま構造体としない
        emit_empty_slices: true #:manyクエリでnilの代わりに空スライスが返される
```
 `queries: "./queries/"`で指定したパスは、「SQLクエリを記述しているファイル」が配置されているディレクトリを指します。これが生成されるgoコードの元となります。

また、`schema: "../migrations/"`としている点に注目ください。sqlcは、コードを生成するためにデータベースのスキーマを認識する必要があります。

データベースのスキーマ変更などは、golang-migrateで行っていました。

超便利なことに、sqlcはgolang-migrateに対応してくれています。
https://docs.sqlc.dev/en/stable/howto/ddl.html#golang-migrate

生成したマイグレーションファイル群からスキーマを認識してくれるのです。そのため、`schema: "../migrations/"`として、「スキーマはマイグレーションファイルを見てください」としています。

### SQLを記述
`app/infrastructure/db/sqlc/queries`ディレクトリにsqlファイルを配置し、記述します。
::::details sqlの実装
usersテーブルの操作
```sql:app/infrastructure/db/sqlc/queries/users.sql
-- name: FindUserByEmail :one
select id,email,name,hashed_password
from users
where email = sqlc.arg(email);

-- name: FindUserById :one
select id,email,name,hashed_password
from users
where id = sqlc.arg(id);

-- name: FetchAllUsers :many
select id,email,name,hashed_password
from users;

-- name: InsertUser :exec
insert into users (
    id,
    name,
    email,
    hashed_password
) values (
    sqlc.arg(id),
    sqlc.arg(name),
    sqlc.arg(email),
    sqlc.arg(hashed_password)
);

-- name: UpdateUser :exec
update users
set name=sqlc.arg(name),email=sqlc.arg(email)
where id=sqlc.arg(id);

-- name: DeleteUser :exec
delete from users
where id=sqlc.arg(id);
```

tasksテーブルの操作
```sql:app/infrastructure/db/sqlc/queries/tasks.sql
-- name: FindTaskById :one
select id,user_id,content,state
from tasks
where id = sqlc.arg(id);

-- name: FetchTaskById :one
select t.id,u.name,t.user_id,t.content,t.state
from tasks as t inner join users as u
on t.user_id = u.id
where t.id = sqlc.arg(id);

-- name: FetchUserTasks :many
select t.id,u.name,t.user_id,t.content,t.state
from tasks as t inner join users as u
on t.user_id = u.id
where t.user_id = sqlc.arg(user_id);

-- name: FetchAllTasks :many
select t.id,u.name,t.user_id,t.content,t.state
from tasks as t inner join users as u
on t.user_id = u.id;

-- name: InsertTask :exec
insert into tasks(
    id,
    user_id,
    content,
    state
)values(
    sqlc.arg(id),
    sqlc.arg(user_id),
    sqlc.arg(content),
    sqlc.arg(state)
);

-- name: UpdateTask :exec
update tasks
set state=sqlc.arg(state)
where id = sqlc.arg(id);

-- name: DeleteTask :exec
delete from tasks
where id=sqlc.arg(id);
```
::::
`--name : 生成するメソッド名 :クエリ注釈(種類)`を各クエリの上につけます。

クエリ注釈(Query annotations)は、`:exec`か`:many`か`:one`しか扱っていません。
簡単には、以下の用途で使い分けます。

| クエリ注釈 | 説明                           |
|--------------|--------------------------------|
| `:exec`      | クエリ実行のみ (レコードは返さない) |
| `:many`      | 複数レコードを取得             |
| `:one`       | 単一レコードを取得             |

https://docs.sqlc.dev/en/stable/reference/query-annotations.html

### コード生成
`sqlc generate`コマンドでコードは生成されます。
Makefileにはタスクを定義しています。
```Makefile
# sqlcでコードを生成
sqlc-gen:
	@echo "Generating query in sql by sqlc..."
	cd ./app/infrastructure/db/sqlc && sqlc generate
```
コマンドを打って、コードを生成してください。
```
make sqlc-gen
```
すると、`/sqlc`ディレクトリ配下にいくつかファイルが生成されたと思います。
※ 生成されたファイル群のみ示しています。
```
├── db.go  // 生成されたメソッドを使うためのコード(DBとの連携やトランザクション)
├── models.go // テーブルに対応する構造体
├── tasks.sql.go // `tasks` テーブル関連のSQLクエリと対応するコード
└── users.sql.go // `users` テーブル関連のSQLクエリと対応するコード
```

適宜、ファイルの中身をのぞいてみてください。
`users.sql.go`を少し取り上げてみます。
ユーザーを削除するためのメソッドが以下のように定義されているはずです。
```go
func (q *Queries) DeleteUser(ctx context.Context, id string) error {
	_, err := q.db.ExecContext(ctx, deleteUser, id)
	return err
}
```
レシーバに`*Queries`とあるのに注目してください。sqlcによって生成されるメソッド群は、この`*Queries`を介して扱うことができます。

`db.go`を見てみましょう。
```go
func New(db DBTX) *Queries {
	return &Queries{db: db}
}

type Queries struct {
	db DBTX
}
```
`DBTX`インターフェースは、`sql.DB`（データベース接続）と`sql.Tx`（トランザクション）を抽象化して扱うためのものです。

```go
    return sq.queries.InsertTask(ctx, convertedArg)
```

```go:app/infrastructure/db/container/dockertest.go
	"log"

	"github.com/ory/dockertest/v3"

var (
	userName = "root"
	password = "secret"

func NewDockertestContainer() (*dockertest.Pool, *dockertest.Resource) {
	// デフォルトでUnixソケットを使用する
	pool, err := dockertest.NewPool("")
	if err != nil {
		log.Fatalf("failled to construct pool:%v", err)
	}

			"--collation-server=utf8mb4_unicode_ci",
		},

		// コンテナは停止後に自動削除される
		hc.AutoRemove = true
		// コンテナが異常終了しても再起動しない

			Name: "no",
		}
	})

		log.Fatalf("failed to start resource: %v", err)

	return pool, resource

// コンテナを削除する
func RemoveDockertestContainer(pool *dockertest.Pool, resource *dockertest.Resource) {
	if err := pool.Purge(resource); err != nil {
		log.Fatalf("failed to  purge resource: %s", err)
	}
}
```

## コンテナ内DBに接続する
`NewDockertestContainer()`で返された起動したコンテナの情報`*dockertest.Pool`と`*dockertest.Resource`を使用して、コンテナ内のMySQLサーバーに接続しましょう。

```go:app/infrastructure/db/container/db.go
package container

import (
	"database/sql"
	"fmt"
	"log"
	"path/filepath"
	"runtime"
	"strconv"

	"github.com/golang-migrate/migrate/v4"
	_ "github.com/golang-migrate/migrate/v4/database/mysql"
	_ "github.com/golang-migrate/migrate/v4/source/file"
	"github.com/kakkky/app/domain/errors"
	"github.com/ory/dockertest/v3"
)

// DBに接続する
func NewDB(pool *dockertest.Pool, resource *dockertest.Resource) *sql.DB {
	var db *sql.DB
	// エラーだと再実行を繰り返す
	if err := pool.Retry(func() error {
		var err error
		// 公開ポート番号を取得
		port, err = strconv.Atoi(resource.GetPort("3306/tcp")) //コンテナ内のポート番号は3306
		if err != nil {
			return err
		}
		// DBに接続
		db, err = sql.Open("mysql", fmt.Sprintf("%s:%s@tcp(%s:%d)/%s?parseTime=true", userName, password, hostname, port, dbName))
		if err != nil {
			return err
		}
		// 接続確認
		return db.Ping()
	}); err != nil {
		log.Fatalf("failed to connect to database: %v", err)
	}
	return db
}

func SetupDB() {
	migrationsPath := getMigrationsPath()
	m, err := migrate.New(migrationsPath, fmt.Sprintf("mysql://%s:%s@tcp(%s:%d)/%s?parseTime=true", userName, password, hostname, port, dbName))
	if err != nil {
		log.Fatalf("failed to create migrate instance:%v", err)
	}
	// マイグレーションをテストDBに適用させる
	if err := m.Up(); err != nil {
		if errors.Is(err, migrate.ErrNoChange) {
			log.Println("migrations have already been applied")
		} else {
			log.Fatalf("failed to up migrations:%v", err)
		}
	}
}

const migrationsRelativePath = "../migrations"

// どこからSetupDBを呼び出しても/migrationsへのパスを取得できるようにする
func getMigrationsPath() string {
	// Callerを呼んだファイル名（ファイルパス）を取得する
	_, callerFile, _, ok := runtime.Caller(0)
	print(callerFile)
	if !ok {
		log.Fatal("failed to get caller directory")
	}
	// ファイルパスからディレクトリ部分を取り出す
	callerDir := filepath.Dir(callerFile)
	// /migrationsへの絶対パスを作成
	migrationsAbsPath := "file://" + filepath.Join(callerDir, migrationsRelativePath)
	return migrationsAbsPath
}
```

```go
	if !ok {

	return migrationsAbsPath
}
```

- ファイルパスからディレクトリ部分を取り出す(つまり`/container`ディレクトリ)
- `file://`スキームをつけ、`/migrations`への絶対パスを作成

## テストフィクスチャの用意
### テストフィクスチャとは
テストフィクスチャ（Test Fixture） とは、**テストを実行するために必要な初期設定やデータのこと**です。テストが期待通りに実行される環境や条件を整えるために使用します。

これも便利なパッケージがありまして、testfixturesというものを使っていきます。
https://github.com/go-testfixtures/testfixtures

ドキュメントにある通り、Railsのフィクスチャ形式を真似ているようです。
ymlファイルに記述するのですが、とてもシンプルで筆者的にとても扱いやすいです。

>Basically this package mimics the "Ruby on Rails' way" of writing tests for database applications, where sample data is kept in fixtures files. Before the execution of every test, the test database is cleaned and the fixture data is loaded into the database.
>
>訳) 基本的に、このパッケージはデータベースアプリケーションのテストを書く「Ruby on Railsの方法」を模倣しており、サンプルデータはフィクスチャファイルに保存されます。

以下のコマンドでインストールしてください。
```
make get-app name="github.com/go-testfixtures/testfixtures/v3"
```

### 実装
`app/infrastructure/db/testhelper`ディレクトリを作成してください。
```go:app/infrastructure/db/testhelper/fixtures.go
func SetupFixtures(t *testing.T, fixture_path ...string) {
	t.Helper()

	fixtures, err := testfixtures.New(
		testfixtures.Database(db.GetDB()),
		testfixtures.Dialect("mysql"),
		testfixtures.SkipResetSequences(),
		testfixtures.Files(
			fixture_path...,
		),
	)
	if err != nil {
		t.Fatalf("testfixtures failed to create Loader instance:%v", err)
	}
	// テーブルのデータを削除&用意
	if err := fixtures.Load(); err != nil {
		t.Fatalf("testfixtures failed to load fixtures:%v", err)
	}
}
```
特にややこしい点もないかなと思います。

引数は`(fixture_path ...string) `というふうに、可変長引数となっています。タスクのデータを用意するなら、付随して所有者であるユーザーのデータも必要ですよね。幾つでもフィクスチャファイルを受け付けるようにするためにこうしています。

また、`testfixtures.Load()`は、以下の通り、ロードする前に一旦データベースのデータを一掃してくれるようです。
```go
// Load wipes and after load all fixtures in the database.
//
//	if err := fixtures.Load(); err != nil {
//	        ...
//	}
func (l *Loader) Load() error {
    // 省略
}
```
テストケースごとにこの処理を差し込めば、テストケースごとにデータベースの状況を操作してテストできそうですね。

```go:app/infrastructure/repository_test/user_repository_test.go
func TestUserRepository_Save(t *testing.T) {
	userRepository := repository.NewUserRepository(sqlc.NewSqlcQuerier())
	// ユーザーインスタンスを用意
	user0, _ := user.NewUser(
		"user0@example.com",
		"user0",
		"password",
	)
	type args struct {
		user  *user.User
		email user.Email
	}
	// テストテーブル
	tests := []struct {
		name    string
		args    args
		want    *user.User
		wantErr bool
	}{
		{
			name: "正常系: 1人ユーザーが追加され、emailで検索できる",
			args: args{
				user:  user0,
				email: user0.GetEmail(),
			},
			want:    user0,
			wantErr: false,
		},
	}
	for _, tt := range tests {
		tt := tt
		t.Run(tt.name, func(t *testing.T) {
			ctx := context.Background()
			// ユーザーを保存
			if err := userRepository.Save(ctx, tt.args.user); (err != nil) != tt.wantErr {
				t.Errorf("userRepository.Save()=error %v ,but wantErr:%v", err, tt.wantErr)
			}
			// ユーザーをemailで検索
			got, err := userRepository.FindByEmail(ctx, tt.args.email)
			// 返すエラーはErrNotFoundUserのみであるべき
			if (err != nil) != tt.wantErr {
				t.Errorf("userRepository.FindByEmail() =　error %v,but wantErr :%v", err, tt.wantErr)
			}
			if diff := cmp.Diff(got, tt.want, cmp.AllowUnexported(user.User{}, user.Email{}, user.HashedPassword{}), cmpopts.IgnoreFields(user.User{}, "id", "hashedPassword")); diff != "" {
				t.Errorf("userRepository.FindByEmail() -got,+want :%v ", diff)
			}
		})
	}
}
```
