### エンティティ
まずは、Userエンティティを記述します。
`app/domain/user`ディレクトリを作成してください。
```go:app/domain/user/user.go
package user

type User struct {
	id             string
	email          Email
	name           string
	hashedPassword HashedPassword
}
```
エンティティの性質として、**可変**であるというものがありました。
これは、エンティティの持つ属性が振る舞い（＝メソッド等）による変更を許可されているということです。
しかしながら、可変なオブジェクトは「厄介」なので、**構造体のフィールドを非公開にして直接的な変更を防ぎ**、**値を変更する振る舞いを持つメソッドを定義せずオブジェクトを不変**とする設計としたいと思います。

「可変」はあくまで性質として許可されているに過ぎません。
::::message
#### 「厄介」な可変オブジェクト
インスタンスが可変であると、意図せぬ影響を及ぼす可能性を孕みます。

可変だと、仕様変更時などに意図しない**副作用**を持つ関数を作ってしまい、予期せぬ動作を招いてしまうという事態におちいります。副作用とは、関数が引数を受け取り、戻り値を返す以外に、変数などを変更することです。

端的にいえば、**インスタンスが自由に変更される余地を残すと意図せず変更しちゃってバグになるよ**ということです。

golangにおいて、不変を強制するJavaでいう`final`修飾子はありませんが、パッケージ外に対する不変性は以下のようにすることで確保できます。
- 小文字にして非公開(unexport)にする
- セッター等、変更するようなメソッドを定義しない

同パッケージ内からはフィールドの変更が可能になってしまうのですが、パッケージ外からは「操作」のためにアクセスすることができなくなるので比較的安全と言えるでしょう。

### 値オブジェクト
User構造体のフィールドを見れば分かるとおり、型がプリミティブでないことがわかるでしょうか。こちらを実装します。

まずは`Email`値オブジェクトから
```go:app/domain/user/user_email.go
package user

import (
	"net/mail"

	"github.com/kakkky/app/domain/errors"
)

type Email struct {
	value string
}

func NewEmail(value string) (Email, error) {
	// バリデーション
	if _, err := mail.ParseAddress(value); err != nil {
		return Email{}, errors.ErrInvalidEmail
	}
	return Email{value: value}, nil
}

func reconstructEmail(value string) Email {
	return Email{value: value}
}

func (e Email) Value() string {
	return e.value
}

```
`Email`型には`value`フィールドを持たせており、これも非公開であり不変ですね。
`NewEmail()`は**ファクトリ関数**です。golangにはコンストラクタがありませんが、新しいインスタンスを返すように処理を書いたものがファクトリ関数です。

ポイントとして、
- ファクトリ関数の中でバリデーションを行っている
- インスタンスの参照型を返さず、値型で返している
- 再構成用の関数がある
- 独自のエラー型を定義している（もう少し後で説明）

それぞれ説明していきます。

#### ファクトリ関数の中でバリデーションを行っている

これによって、`User`に形式の正しいメールアドレスを持たせることを保証できます。
emailには、メールの形式を守るなどの「ルール」があります。これを例えばUserエンティティにメソッドとして用意してしまうとUserが膨れ上がり、責務を抱え過ぎてしまいます。

ルール・振る舞いを持っている属性は、このように値オブジェクトとしてエンティティから切り出せます。

#### インスタンスの参照型を返さず、値型で返している

ポインタ型として`*Email`を返すようにファクトリ関数を書いていないのには理由があります。
**等価性によって区別されるという性質**が値オブジェクトにはありました。

ポインタ型（参照型）とすると、同じように生成したインスタンスでも等価ではありません。ポインタ型は変数のメモリ上のアドレスを示すものだからです。
```go
func NewEmail(value string) (*Email, error) {
    // 省略
	return &Email{value: value}, nil
}

email1:=NewEmail("hogehoge@email.com")
email2:=NewEmail("hogehoge@email.com")

fmt.Println(email1 == email2) // falseになる。
```

ですので、等価性によって単純に評価できるようにするには、**値型**として表現するのが良さそうです。これはあくまで、値オブジェクトの性質に則っての設計です。

::::message
#### エンティティとポインタ

値オブジェクトが値型として表現される理由はわかっていただけたかと思います。
しかし、値オブジェクトとは打って変わってエンティティにはポインタを使用していましたので、その理由もここに記しておきます。

エンティティは、**同一性によって区別される**性質がありました。
これは、識別子（id）によって区別されるということなので、単純に`==`で評価することがありません。どれだけ属性が変化しようが、エンティティは識別子により区別されます。
また、**ポインタは、構造体がデータを多く含んでいる場合に有効**のようです。
エンティティは基本的にデータを多く含むものと捉えています。
これらの理由から、エンティティをポインタとしました。

ポインタか値かについては以下の記事が参考になります。APIの一貫性を保つために、構造体のメソッドはポインタレシーバーを統一的に使うことを推奨していますね。今回のハンズオンでも、統一して基本的には構造体のメソッドをポインタレシーバーとしています。

しかし、値オブジェクトなどのデータが小さい構造体に関しては、先述した「等価性による評価」などの理由に加え、パフォーマンス面を考えて値レシーバーとしました。

参考記事
- [When to use pointers in Go(Medium)](https://medium.com/@meeusdylan/when-to-use-pointers-in-go-44c15fe04eac)

#### 再構成用の関数がある

`reconstructEmail()`関数はオブジェクトの**再構成**を担うメソッドです。

主に**リポジトリ**から使用され、DBからとってきたデータをUserオブジェクトとして復元するためのものです。
よくみると`NewUser()`ファクトリ関数と同じくUserオブジェクトインスタンスを返していることは同じですね。しかし、バリデーションロジックがありません。これは、データベースに格納されている値はすでにバリデーション済みであるからです。ここでわざわざ検証し直す必要性は薄いです。

また、`NewUser()`では`id`を関数内で作成していたため引数に`id`を取る必要がありませんでしたが、再構成の際は、すでに存在しているユーザーの`User`オブジェクトを復元するため`id`を入れているという点も異なります。
また、この関数は後で記述するユーザーの再構成用の関数`ReconstructUser()`で使用されるためだけの関数ですので、非公開にしています。
::::message
このように、**他パッケージ（外部）から使用されない前提がある関数・メソッドは基本的に非公開**にして開発を進めています。
これは、コードを見ただけで他からも使われているものなのかどうかを認識できるようにするためです。

非公開ならば、「この関数が影響している範囲はこのパッケージに限られるな」とわかるようになります。

同じように`HashedPassword`値オブジェクトを実装しましょう。
具体的なコードを見る前に、単に`Password`とするのではなく`HashedPassword`とした理由を述べておきます。

セキュリティ的にパスワードを平文で管理していいはずもないので、`Password`オブジェクトを用意するならば、そこにハッシュ化の処理を持たせるのが自然です。
ただ、**パスワードをハッシュ化するということは、ドメイン知識から外れる**と筆者は思います。ハッシュ化しなければならないのは完全に機能要件であり、アプリケーション由来のものです。

そこで、

**元から、ハッシュ化されたパスワードを持つものとしてモデリングすれば、値オブジェクトにハッシュの比較処理等を実装していてもおかしくない**

と考え方を変えます。
すると、ハッシュ化はドメイン知識となり、自然に実装できるようになるのです。

以下の記事を参考にしました

https://zenn.dev/10inoino/articles/69cb27159fc121

以下、コードです。
`HashPassword`の振る舞いとして、ハッシュパスワードと平文パスワードを比較する`compair()`メソッドを定義しています。メソッドは非公開にして、Userからこのメソッドを呼び出します。「集約ルート」についてはこの後触れます。
```go:app/domain/user/user_hashed_password.go
package user

import (
	"unicode/utf8"

	"github.com/kakkky/app/domain/errors"
	"github.com/kakkky/pkg/hash"
)

type HashedPassword struct {
	value string
}

const (
	minPasswordLength = 6
)

func newHashedPassword(value string) (HashedPassword, error) {
	// バリデーション
	if minPasswordLength >= utf8.RuneCountInString(value) {
		return HashedPassword{}, errors.ErrPasswordTooShort
	}
	// ハッシュ化する
	hashed, err := hash.Hash(value)
	if err != nil {
		return HashedPassword{}, err
	}

	return HashedPassword{value: hashed}, nil
}

func reconstructHashedPassword(value string) HashedPassword {
	return HashedPassword{value: value}
}

func (hp HashedPassword) Value() string {
	return hp.value
}

// ハッシュ化されたパスワードと比較
// 集約ルートUserから呼び出す
func (p HashedPassword) compare(target string) error {
	if err := hash.Compare(p.value, target); err != nil {
		return errors.ErrPasswordMismatch
	}
	return nil
}
```
`hash`パッケージを`pkg`から持ってきているのがわかりますでしょうか。
```go
import (
    "github.com/kakkky/pkg/hash"
)
```
ハッシュ化するというのは汎用的な処理なので、`pkg`モジュールに実装しましょう。
::::details pkg/hash の実装
```go:pkg/hash/hash.go
package hash

import "golang.org/x/crypto/bcrypt"

func Hash(target string) (string, error) {
	hashed, err := bcrypt.GenerateFromPassword([]byte(target), bcrypt.DefaultCost)
	if err != nil {
		return "", err
	}
	return string(hashed), nil
}

func Compare(hashed, target string) error {
	err := bcrypt.CompareHashAndPassword([]byte(hashed), []byte(target))
	return err
}
```

```go:pkg/hash/hash_test.go
func TestHash(t *testing.T) {
	tests := []struct {
```

#### テーブルドリブンテスト
golangでは、テーブルドリブンテストというテスト手法が推奨されています。
というのも特に特別なパッケージを使用するとかではなく、テストケースを配列（スライス）にまとめるというものです。
```go
func TestAdd(t *testing.T) {
	// テストテーブル
	tests := []struct {
		name     string
		a, b     int
		expected int
	}{
		{name: "正の数同士を足す場合", a: 1, b: 2, expected: 3},
		{name: "正の数と0を足す場合", a: 5, b: 0, expected: 5},
		{name: "負の数を足す場合", a: -1, b: -2, expected: -3},
	}
    // テストテーブルにあるテストケースをforループで回す
	for _, tt := range tests {
        // それぞれのテストケースをサブテストとして実行する
		t.Run(tt.name, func(t *testing.T) {
			result := calculator.Add(tt.a, tt.b)
			if result != tt.expected {
				t.Errorf("[%s] Add(%d, %d) = %d; want %d",
					tt.name, tt.a, tt.b, result, tt.expected)
			}
		})
	}
}
```
テストテーブルには、テストケース名や入力値・期待値などを含めます。
そして、テストケースの配列をforループで回し、`t.Run()`メソッドにより各テストケースをサブテストとして実行します。

この手法だと、以下のようなメリットがあります。
- テストの抜けを見つけやすい
- テストケースを追加しやすい
- パッと見てわかりやすい

テストテーブルを見ただけでどんなテストケースがあるのかが一目でわかるため、この手法が結構好きです。

### ユーザーエンティティにロジックを実装する
値オブジェクトが実装できたので、それを利用しつつ、エンティティにも同じようにファクトリ関数、そして振る舞いを持たせます。
::::details user.go の実装
```go:app/domain/user/user.go
package user

import (
	"github.com/kakkky/pkg/ulid"
)

type User struct {
	id             string
	email          Email
	name           string
	hashedPassword HashedPassword
}

// ファクトリー関数
func NewUser(
	email string,
	name string,
	password string,
) (*User, error) {
	validatedEmail, err := NewEmail(email)
	if err != nil {
		return nil, err
	}
	HashedPassword, err := newHashedPassword(password)
	if err != nil {
		return nil, err
	}
	return &User{
		id:             ulid.NewUlid(),
		email:          validatedEmail,
		name:           name,
		hashedPassword: HashedPassword,
	}, nil
}

// 既存のユーザーを返す
// インスタンスの再構成
func ReconstructUser(
	id string,
	email string,
	name string,
	hashedPassword string,
) *User {
	return &User{
		id:             id,
		email:          reconstructEmail(email),
		name:           name,
		hashedPassword: reconstructHashedPassword(hashedPassword),
	}
}

// ユーザーオブジェクト更新
func (u *User) UpdateUser(
	email string,
	name string,
) (*User, error) {
	validatedEmail, err := NewEmail(email)
	if err != nil {
		return nil, err
	}
	return &User{
		id:             u.id,
		email:          validatedEmail,
		name:           name,
		hashedPassword: u.hashedPassword,
	}, nil
}

// 値のゲッターメソッド
func (u *User) GetID() string {
	return u.id
}
func (u *User) GetName() string {
	return u.name
}
func (u *User) GetEmail() Email {
	return u.email
}
func (u *User) GetHashedPassword() HashedPassword {
	return u.hashedPassword
}

// パスワードを比較する
func (u *User) ComparePassword(plainPassword string) error {
	return u.hashedPassword.compare(plainPassword)
}
```

#### ファクトリ関数はインスタンスを参照型を返している

値オブジェクトのファクトリ関数は、インスタンスを値型で返していました。それは、値オブジェクトが不変であったからです。

#### 集約とは
1つのオブジェクトは、複数のオブジェクトが集まって構築されます。「集約」は、関連するオブジェクト同士をまとめる境界線として定義されます。

集約はオブジェクトのグループの不変条件を維持し、オブジェクトの操作に秩序をもたらします。
例えば、現段階では**ユーザー集約**が以下のようになっています。
![](https://storage.googleapis.com/zenn-user-upload/cdc774f3a2ae-20241231.png)

ユーザー集約の内部には、`User`、`HashedPassword`、`Email`があります。
集約内部のオブジェクトは外部から操作されてはいけません。

そこで、**集約ルート**と呼ばれるオブジェクトに集約内部のオブジェクト操作を限定します。今回であれば、`User`が集約ルートです。`Email`や`HashedPassword`を操作するのは`User`のみです。
非常に納得できる例えがあります。

ユーザー情報を更新するのはドメインルールです。emailとnameを受け取って、emailには`NewEmail()`ファクトリ関数を実行することでバリデーションをかけています。

```go
	email string,
	name string,
) (*User, error) {
	validatedEmail, err := NewEmail(email)
	if err != nil {
		return nil, err
	}

		id:             u.id,
		email:          validatedEmail,
		name:           name,
```

### テスト項目における正常系と準正常系
テスト項目を、**正常系/準正常系/異常系**と分けて考えています。
#### 正常系
期待される入力が与えられ、メソッドが正しく動作することを確認します。
#### 準正常系
不完全・不正な入力が与えられた場合でも、適切に動作することを確認します。
#### 異常系
仕様で想定されていない状況や状態でシステムがどう振る舞うかを確認します。

正常系のテストはわかりやすいです。正しい値を入れて正しく返す、ごく一般の想定した動作フローを考えればいいからです。
テストを簡単に分けるなら、「正常系/異常系」の２種に分けられます。正しい状況と正しくない状況を想定するのですが、後者の**正しくない状況はもう少し細分化できます**。
それは、
- **システムが想定している範囲内の不正な状況**
  本章の一番最後で取り上げている**ドメインエラー**として、こちら側が想定している不正な入力値の場合を検証します。例えば、「メールアドレスの形式が不正だ」などがそうです。
  
- **システムが想定していない不正な状況**
　ネットワーク系のエラーが起きた時や、関数内部における処理が失敗したときなどがそれにあたります。何らかのエラーでレシーバに`nil`が入ってしまった(`nil pointer deference`、いわゆる「ぬるぽ」)場合などもそうです。システムがクラッシュしないかどうかを確かめます。

の２つです。

そこで、今回は主に「正常系」と「準正常系」をテスト項目としてテストを行なっていきます。異常系のテストはしづらいと考えたので、今回は取り扱わないようにしました。

#### タスク状態のenum的表現
enumとは列挙型のことであり、数値にたいしてプログラムで扱う別名を与えるものです。

タスク状態は、バリエーションが未完了/進行中/完了の３つです。これなら、データベースに`"todo","doing","done"`と文字列で格納するよりも、数値で扱う方が効率的です。

golangには、enumが用意されていませんが、同様の表現を`iota`を使って表現できます。「enum的」と表現したのはこれが理由です。
```go
const (
	Todo State = iota  // 0
	Doing              // 1
	Done               // 2
)
```
タスク状態を数値として扱うのはデータベースへのI/O付近です。しかし、エンドポイントにリクエストを送る際はJSONで数値を送るとなるととてもわかりにくいですね。
レスポンスとしてタスク状態は`0`だよ！という風に返ってきてもなんのこっちゃですね。エンドポイントにおけるI/Oでは、文字列で扱った方が良さそうです。

つまり、**リポジトリでは数値として扱う必要**があり、**プレゼンテーションにDTOを渡すユースケースでは文字列で扱う必要**がありそうです。

そのために、数値を返す`IntValue()`メソッドと文字列で返す`StrValue`メソッドの両方を用意しています。

同じように、ファクトリ関数と再構成用関数も見ていきます。

```go:app/domain/user/user_domain_service.go
func (uds userDomainService) IsExists(ctx context.Context, email Email) (bool, error) {
	user, err := uds.userRepository.FindByEmail(ctx, email)

	if err != nil && errors.Is(err, errors.ErrNotFoundUser) {
		return false, nil
	}
	// それ以外ならエラーとして返す
	if err != nil {
		return false, err
	}
	return user != nil, nil
```

#### エラー型オブジェクトのインスタンスを比較する

`errors.Is(err,target error)`は、第一引数と第二引数のインスタンスが一致しているかどうかの真偽値を返します。エラーの値を比較していると考えるとわかりやすいです。
```go
package main

import (
	"errors"
	"fmt"
)

// カスタムエラー
var customError = errors.New("emit macho dwarf: elf header corrupted")

// カスタムエラーを生成する関数
func emitError() error {
	return customError
}

func main() {
	err := emitError()
	// エラーの値を比較
	if errors.Is(err, customError) {
		fmt.Println("The error matches the customError")
	} else {
		fmt.Println("The error does not match")
	}
	// 出力: The error matches the customError
}

```
#### エラー型オブジェクトのインスタンスの型を比較する
`errors.As(err error, target any)` は、第一引数に渡されたエラー型オブジェクトに対して、第二引数の型で「型アサーション（型変換が可能かどうかを確認）」を行い、型の一致をチェックします。結果として、真偽値を返します。
厳密には「型を比較している」という表現は少し誤解を招くかもしれませんが、直感的に扱うならこのように理解するのが良いと思います。
```go
// fsパッケージにて定義されているエラー型
type PathError struct {
	Op   string
	Path string
	Err  error
}
```
```go
import (
	"errors"
	"fmt"
	"io/fs"
	"os"
)

func main() {
	if _, err := os.Open("non-existing"); err != nil {
        // 期待するエラー型
		var pathError *fs.PathError
		if errors.As(err, &pathError) {
			fmt.Println("Failed at path:", pathError.Path)
		} else {
			fmt.Println(err)
		}
	}

}
//出力
//Failed at path: non-existing
```

簡単に書いてしまえば、２つのメソッドは以下のように整理できます。
- `errors.Is()`はエラーの値そのもの（インスタンス）を比較
- `errors.As()`はエラーの型を比較

```go:app/domain/errors/errors.go
	ErrNotFoundUser     = newErrDomain("ErrNotFoundUser", "user not found")

	ErrNotFoundTask           = newErrDomain("ErrNotFoundTask", "task not found")
	ErrContentEmpty           = newErrDomain("ErrContentEmpty", "Do not empty the content")
	ErrInvalidTaskState       = newErrDomain("ErrInvalidTaskState", "invalid task state , please select todo/doing/done")
	ErrForbiddenTaskOperation = newErrDomain("ErrForbiddenTaskOperation", "can't operate others tasks")

// ドメインエラー
type ErrDomain struct {
	err error
}

// ドメインエラーのコンストラクタ
func newErrDomain(errType, message string) *ErrDomain {
	return &ErrDomain{
		err: fmt.Errorf("errType : %v , Message : %v", errType, message),
	}
}

// ドメインエラーかどうか
func IsDomainErr(target error) bool {
	var errDomain *ErrDomain
	return errors.As(target, &errDomain)
}

// errorインターフェースを満たすため
func (e *ErrDomain) Error() string {
	return e.err.Error()
}

// errors.Isをラップ
// パッケージ名の衝突を考慮
func Is(err, target error) bool {
	return errors.Is(err, target)
}
func New(message string) error {
	return errors.New(message)
}
```

値を全て`ErrDomain`型とするために、ファクトリ関数を定義しています。
```go
// ドメインエラーのファクトリ関数
func newErrDomain(errType, message string) *ErrDomain {
	return &ErrDomain{
		err: fmt.Errorf("errType : %v , Message : %v", errType, message),
	}
}
```
`Err-`から始まるエラー値をエラータイプとして表し、エラーメッセージから一目でどんなエラーかを認識できるようにしました。

### `errors.As()`で`ErrDomain`型かどうかを判別する
以下の関数では、内部で`errors.As()`を使用しています。
```go
// ドメインエラーかどうか
func IsDomainErr(target error) bool {
	var errDomain *ErrDomain
	return errors.As(target, &errDomain)
}
```
ドキュメントの例に倣って実装しました。
https://pkg.go.dev/errors#As

この関数は主にプレゼンテーションで扱い、エラーが`ErrDomain`かどうかでステータスコードが400番台になるか500番台になるかを決定できるようにします。

### `errors`パッケージの関数をラップする
`errors.New()`と`errors.Is()`は、普通に使用していきたいのですが、`domain/errors`パッケージとしているせいで、`errors`パッケージと衝突する可能性があります。
```go
import (
	"errors"
	"github.com/kakkky/app/domain/errors"　//errorsというパッケージ名が衝突
)
```
プロジェクトにおいてエラーを扱うパッケージを`github.com/kakkky/app/domain/errors`に集約して管理するために、`errors.Is()`と`errors.New()`を実装しました。内部で`errors`パッケージを使っているだけ(つまりラップしているだけ)です。

```go
// パッケージ名の衝突を考慮して関数をラップしている
func Is(err, target error) bool {
	return errors.Is(err, target)
}
func New(message string) error {
	return errors.New(message)
}
```
