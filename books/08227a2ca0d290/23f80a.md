# プレゼンテーションのテスト方針
プレゼンテーションのテストは行っていませんでした。
ここでは、どのようにそれらをテストしていくかの方針について述べていきます。

まずは、単体テスト/結合テストという用語について触れていきます。
## 単体テスト/統合テスト
テストの種類には大きく分けると、**単体テスト・統合テスト**の２種類があります。

### 単体テスト
単体テストとは、プログラムの最小単位（関数・メソッド・クラスなど）の動きを個別に確認するテストです。
一般的には、外部依存（DB・ネットワークなど）を排除し、モックやスタブを使って独立した動作を確認します。

例えば、ユースケースのテストが単体テストにあたります。
これらは、実際、いくつかの別コンポーネントに依存していますが、依存先はインターフェースであり、テスト時は「モック」に差し替えることで「ユースケース単体」の挙動を検証することができていました。

### 結合テスト
結合テストとは、複数のコンポーネントを組み合わせて、連携が正しく動作するかを確認するテストです。
実際のDBや外部APIなどの依存先を使うことが多いです。

8章にて実装したリポジトリーのテストは、「統合テスト」だと言えるでしょう。テストDB環境やsqlcといったORMなど、インフラストラクチャ層のコンポーネントを多く利用して、リポジトリが正しくデータ操作できるかを確かめました。

## プレゼンテーションのテストは「エンドポイントの統合テスト」として実施
見出しの通りです。

このように判断したポイントは二つあります。
- ハンドラーは多くの依存を抱えている
- モックに差し替えた時のコードの複雑性

### ハンドラーは多くの依存を抱えている
プレゼンテーション（ハンドラー・プレゼンター）は、いわば**APIの入口**ということもできるでしょう。
つまり、プレゼンテーションは、総じて多くの依存先を抱えています。
以下は、前章でも用いた図です。
![](https://storage.googleapis.com/zenn-user-upload/05f0f3c48e74-20250205.png)
また、プレゼンテーションは、それ単体にビジネスロジックがあるわけではなく、ユースケース処理を呼び出すのが主な責務です。

### モックに差し替えた時のコード複雑性
上で、ハンドラーは多くの依存先を抱えていると述べました。
ドメインサービス、リポジトリ、ユースケース、さらにDB環境をモック化してテストを行うとなると、コードが複雑になるのは自明です。大量のモック化を行う必要があります...。


これら２点を踏まえると、プレゼンテーション単体の挙動を確かめるのではなく、ユースケースやリポジトリ、ドメインサービス等のコンポーネントとの連携を確かめつつプレゼンテーションの挙動も確認できるよう、「エンドポイントの統合テスト」として実施した方が良いのではないかいう判断ができます。


## エンドポイントの統合テストとは
ここでいう「エンドポイントの統合テスト」とは、

**リクエストを送信して、期待通りのレスポンスかどうかを検証する**

こととします。

エンドツーエンドで挙動を確かめるとも言えそうですね。

テストコードの中でリクエストを投げ、レスポンスを確かめます。レスポンスを確かめるのに、「ゴールデンテスト」という手法を用いていきます。

# ゴールデンテストとは
ゴールデンテストとは、**期待される出力（ゴールデンファイル）を事前に保存し、テスト時に実際の出力と比較する手法**です。

主に構造化された出力（JSON, XML, HTMLなど） のテストに用いられ、差分を検出することで**リグレッション（意図しない変更）を防ぐ**目的があります。

ゴールデンテストを扱いやすくするためのパッケージとして`sebdah/goldie`を使用します。
https://github.com/sebdah/goldie
以下のコマンドを打ってインストールしてください。
```
make get-app name="github.com/sebdah/goldie/v2"
```
このパッケージを使うと、実際のレスポンスからゴールデンファイルを自動生成してくれます。
いちいち自身でJSONのレスポンスをファイルに記述して...という手間が必要ありません。

ざっくりいうと、
- `-update`フラグをつけてテストを実行するとゴールデンファイルが生成される
- フラグなしでテストを実行すると、「出力されたレスポンス」と「既に生成されたゴールデンファイルに記録されているレスポンス」を比較する

という使い方をします。

## ヘルパー関数の用意
テスト用のヘルパー関数を用意していきましょう。
用意する関数は以下のとおりです。
- JSONのフォーマットを整形する（`FormatJSON()`）
- ランダムに生成されるULIDの値を固定化する（`NormalizeUlid()`）
- レスポンスとして返るJSONが含む`jwt_token`フィールドの中身を固定化する（`NormalizeJWT()`）
- 認証状態を操作する
    - ログイン状態にする（`LoginForTest()`）
    - ログアウト状態にする(`LogoutForTest()`)

::::details ヘルパー関数の実装
JSONのフォーマットを整形するヘルパー関数
```go:app/infrastructure/api_test/testhelper/format_json.go
package testhelper

import (
	"bytes"
	"encoding/json"
	"testing"
)

func FormatJSON(t *testing.T, b []byte) []byte {
	t.Helper()

	var out bytes.Buffer
	// bodyをインデント整形し、バッファoutに書き込む
	err := json.Indent(&out, b, "", "  ")
	if err != nil {
		t.Fatal(err)
	}

	return out.Bytes()
}
```
ランダムに生成されるULIDの値を固定化するヘルパー関数
```go:app/infrastructure/api_test/testhelper/normalize_ulid.go
package testhelper

import (
	"regexp"
	"testing"
)

func NormalizeULID(t *testing.T, b []byte) []byte {
	t.Helper()

	regexp := regexp.MustCompile(`"id":\s?"[0-9A-HJKMNP-TV-Z]{26}"`)
	s := regexp.ReplaceAllString(string(b), `"id": "ulid"`)
	return []byte(s)
}
```
レスポンスとして返るJSONが含む`jwt_token`フィールドの中身を固定化する
```go:app/infrastructure/api_test/testhelper/normalize_jwt.go
package testhelper

import (
	"regexp"
	"testing"
)

func NormalizeJWT(t *testing.T, b []byte) []byte {
	t.Helper()

	// 正規表現でJWT全体を "jwt" に置き換える
	regexp := regexp.MustCompile(`"jwt_token":\s?"[^"]+"`)
	s := regexp.ReplaceAllString(string(b), `"jwt_token": "jwt"`)
	return []byte(s)
}
```
認証状態を操作するヘルパー関数
```go:app/infrastructure/api_test/testhelper/setup_auth.go
package testhelper

import (
	"context"
	"testing"
	"time"

	"github.com/kakkky/app/adapter/repository"
	"github.com/kakkky/app/infrastructure/auth"
	"github.com/kakkky/app/infrastructure/kvs"
)

// ログイン状態をセットアップする
// userID：JTIのペアを、KVSに保存する
// 生成したJWTトークンを返す
func LoginForTest(t *testing.T, userID string) string {
	t.Helper()

	jwtAuthenticator := auth.NewJwtAuthenticator()
	// トークン生成
	jwtToken, err := jwtAuthenticator.GenerateJwtToken(userID, "jti")
	if err != nil {
		t.Fatalf("error occuerd in jwtAuthenticator.GenerateJwtToken() :%v", err)
	}
	jwtAuthenticatorRepository := repository.NewJwtAuthenticatorRepository(kvs.NewRedisCommander())
	// Redisに保存
	jwtAuthenticatorRepository.Save(context.Background(), time.Duration(2*time.Hour), userID, "jti")
	return jwtToken
}

func LogoutForTest(t *testing.T, userID string) {
	t.Helper()

	jwtAuthenticatorRepository := repository.NewJwtAuthenticatorRepository(kvs.NewRedisCommander())
	if err := jwtAuthenticatorRepository.Delete(context.Background(), userID); err != nil {
		t.Fatalf("error occured in jwtAuthenticatorRepository.Delete() :%v", err)
	}
}
```

#### `FormatJSON()`
レスポンスでJSONがゴールデンファイルに書き込まれますが、その際に整形されたJSONであった方が見てわかりやすいです。
`json.Indent()`関数によってインデントを揃えるなどしています。

#### `NormalizeULID()`
この関数は、レスポンスに含まれる以下のようなフィールドの値を固定化するためのものです。
`POST`系のハンドラー（`postUserHandler`と`postTaskHandler`）のテストにて使用します。

タスク・ユーザーの両者とも、識別子として`id`フィールドを持っています。
```go
// ユーザーエンティティ
type User struct {
	id             string
	email          Email
	name           string
	hashedPassword HashedPassword
}

// タスクエンティティ 
type Task struct {
	id      string
	userId  string
	content Content
	state   State
}
```

そして、割り当てる`id`には、`ulid`を使用していました。つまり、生成される`id`はランダムだということです。
そうなると、毎回、`POST /user`とリクエストを投げた時に返ってくるレスポンスが異なってしまいます。
```json
// １回目のレスポンス
{
  "status": 201,
  "data": {
    "id": "01JKAEFYKJY010E45XMTYSFQHR",
    "email": "user0@test.com",
    "name": "user0"
  }
}

// ２回目のレスポンス
{
  "status": 201,
  "data": {
    "id": "01JKAEFY9W2VPFK31SYX9P15GM",  // idが異なる
    "email": "user0@test.com",
    "name": "user0"
  }
}
```

レスポンス内容が毎回変わってしまうようでは、ゴールデンテストが一向に成功しません。
そのために、JSONの`id`フィールドの値を`"ulid"`という文字列に固定化するようにしています。

ランダムなulid(例：`"01JKAEFY9W2VPFK31SYX9P15GM"`)→`"ulid"`文字列への変換には、正規表現を用いています。

#### `LoginForTest()`・`LogoutForTest()`
ほとんどのエンドポイントは、ログインしていないとミドルウェアによって弾かれてしまいます。
```json
// ヘッダーにトークンを含めなかった場合
{
    "status": 401,
    "message": "authorization Header is missing"
}
```
そのため、ログイン状態をあらかじめセットアップしてからエンドポイントを叩くというようにします。

ここでいう「ログイン状態」とは、以下の２点が揃っていることです。
- 有効なJWTトークンが`Authorization`ヘッダーに含まれているか
- Redisにおいて、ユーザーidに紐づく`JTI(JWTトークンのid)が保存されているか

これらをパスすれば認可制御ミドルウェアはリクエストを通します。

テスト内では以下のように使用します。
```go
// Authorizationヘッダーを付加する
if tt.isLogin {
    jwtToken := testhelper.LoginForTest(t, "1")
    defer testhelper.LogoutForTest(t, "1")
    // リクエストヘッダーに Bearer Token方式でトークンを含める
    r.Header.Set("Authorization", "Bearer "+jwtToken)
}
```
テストケースによっては、未ログイン時の挙動を確かめたい時もあるため、`tt.isLogin`フラグが`true`の時のみログイン状態をセットアップするようにしています。

idが1であるユーザーがエンドポイントを叩いていると想定して、`LoginForTest()`の第二引数に`"1"`を渡しています。

`LoginForTest()`は、第二引数に渡ったユーザーidを元にJWTトークンを生成して返します。また、Redisにはユーザーidに紐づくJTIを保存します。
こうすることにより、引数に入れたidを持つユーザーを「ログイン状態」にしています。

また、`LogoutForTest()`はRedisからユーザーidに紐づくJTIを削除することによって「ログアウト状態」を実現しています。

 #### `t.Helper()`について
Goのテストにおいてヘルパー関数を定義する際に使用します。
ヘルパー関数として定義した関数内に`t.Helper()`メソッドを記述すると、

**ヘルパー関数内でエラー(`t.Fatal()`など)が発生した場合にヘルパー関数の呼び出し元をエラーメッセージの出力位置として表示**するようになります。
つまり、テスト内の行番号を返してくれるということです。

反対に、`t.Helper`を記述しないと、ヘルパー関数の行番号をエラーメッセージに表示するようになります。

「テストにおいてどの行で失敗したか」が知る方がデバッグしやすいのは想像に易いでしょう。

また、テスト用のヘルパー関数であることを明示的にするためにも、`t.Helper()`を記述するようにしています。

## テスト記述
テストを記述していきましょう。

### TestMainを記述
リポジトリのテストの際も同様のことを行いました。

`*testing.M`を引数にとる以下のような関数には、同パッケージにおける共通処理を記述できるのでした。
```go
func TestMain(m *testing.M) {
	// 前処理
	m.Run()   // 各テストケースの実行
    // 後処理
}
```

各エンドポイントテストケースにおいて共通処理としたいものは、以下の通りです。
- テストDBコンテナの起動
- DBへの接続処理
- DBマイグレーションの適用
- Redisへの接続処理
- ルーティングの初期化

「ルーティングの初期化」以外はリポジトリの時と変わりません。

::::details TestMainのコード
```go:app/infrastructure/api_test/integration/api_test.go
package integration

import (
	"log"
	"net/http"
	"testing"

	"github.com/kakkky/app/infrastructure/db"
	"github.com/kakkky/app/infrastructure/db/container"
	"github.com/kakkky/app/infrastructure/kvs"
	"github.com/kakkky/app/infrastructure/router"
)

var mux http.Handler

func TestMain(m *testing.M) {
	//dockertestコンテナを起動
	pool, resource := container.NewDockertestContainer()
	log.Println("success to start dockertest container")
	defer func() {
		container.RemoveDockertestContainer(pool, resource)
		log.Println("success to remove dockertest container")
	}()
	// DBに接続
	testDB := container.NewDB(pool, resource)
	log.Println("success to connect test-db")
	defer testDB.Close()
	// マイグレーションを適用させる
	container.SetupDB()
	log.Println("success to apply migrations")
	// dbパッケージ変数にテスト用DBをセット
	db.SetDB(testDB)
	log.Println("dockertest & test-db settings complete")

	// テスト用のredisサーバーを起動
	cli := kvs.NewRedisTestClient()
	defer cli.Close()

	// ルーティングを初期化
	mux = router.NewMux()

	m.Run()
}
```
::::

「ルーティングの初期化」とは何をしているかというと、`router.NewMux()`の呼び出しです。
これにより、ルーティングが登録されたマルチプレクサ(`*http.ServeMux`)が取得できます。

マルチプレクサは、以下のようにパッケージ変数として管理しています。
```go
var mux http.Handler
```
次に記述する各エンドポイントのテストでは、ルーティングを登録したマルチプレクサ(`mux`変数)をテストケース毎に利用したいため、テスト関数内からアクセスできるようにしているのです。

テストケースごとに`mux`変数を利用する理由は、次で使用する`net/http/httptest`パッケージの使い方に関連しています。

#### ＜`net/http/httptest`パッケージ＞
実はすでに使用している(13章「ルーティングの実装」)ものですが、HTTPが絡むテストには`net/http/httptest`パッケージを使用するのが一般的です。

このパッケージを使うと、**HTTPサーバーを起動せずともHTTPリクエスト（もどき）を送信し、ハンドラーの挙動を確かめることができます**。

具体的には、`ServeHTTP()`メソッドの引数に渡す`ResponseWriter`型と`*Request`型のモックを用意することができ、擬似的なHTTPリクエストを送信することができます。
```go
// *Request型のモック
// HTTPメソッド、パス、リクエストボディ(`io.Writer`型)を引数に渡す
r := httptest.NewRequest(http.MethodPost, "/hoge", bytes.NewBuffer(b))
// ResponseWriter型のモック
rw := httptest.NewRecorder()
// マルチプレクサに対してHTTPリクエスト(擬似)を送信
mux.ServeHTTP(rw, r)
```
`ResponseWriter`型の`rw`にはレスポンス内容が書き込まれます。

::::message
#### `ServeHTTP()`呼び出されるタイミング
テストでは、マルチプレクサに対して`ServeHTTP()`メソッドを呼び出すことで「HTTPリクエスト送信」していると述べました。

マルチプレクサも、「ルーティングハンドラー」であり、`http.Handler`型なので、`ServeHTTP()`メソッドが定義されているわけです。

ただ、実装したハンドラー(`postUserHandler`等)にも`ServeHTTP()`メソッドを定義していましたね。
`http.Handler`型を満たすために定義される`ServeHTTP()`メソッドですが、これはいつ呼び出されるのでしょうか。

サーバーを起動し、HTTPリクエストを受け付けるためのメソッドである`*http.Server`型の` ListenAndServe()`メソッドをコードリーディングして処理を追ってみましょう。

`ListenAndServe()`メソッドは、`*http.Server`型の`Serve()`メソッドを呼び出しています。
```go
// Serve は、リスナー l 上で着信接続を受け付け、それぞれの接続ごとに
// 新しいサービス用のゴルーチンを作成します。ゴルーチンはリクエストを読み取り、
// srv.Handler を呼び出してレスポンスを返します。
func (srv *Server) Serve(l net.Listener) error {
    // 省略
	for {
    	// 省略
		go c.serve(connCtx)
	}
}
```
`srv.Handler`を呼び出してリクエストを処理するとありますね。この`Handler`は`Server`構造体にある`Handler`フィールドのことであり、マルチプレクサが入っているのでしたね。

さらに内部を追ってみましょう。
`Serve()`メソッド内では、`*conn`型の`serve()`メソッドが呼び出されています。
```go
func (c *conn) serve(ctx context.Context) {
    // 省略
    serverHandler{c.server}.ServeHTTP(w, w.req)
    // 省略
}
```
ここで、`serverHandler`型の`ServeHTTP()`メソッドが呼び出されています。
`serverHandler`は以下のように、`*Server`構造体をラップしたものです。
```go
type serverHandler struct {
    srv *Server
}
```
`serverHandler`型の`ServeHTTP()`メソッドの実装を見てみましょう。
```go
func (sh serverHandler) ServeHTTP(rw ResponseWriter, req *Request) {
	handler := sh.srv.Handler
	if handler == nil {
		handler = DefaultServeMux
	}
	if !sh.srv.DisableGeneralOptionsHandler && req.RequestURI == "*" && req.Method == "OPTIONS" {
		handler = globalOptionsHandler{}
	}

	handler.ServeHTTP(rw, req)
}
```
`sh.srv.Handler`、つまりマルチプレクサが`hadler`変数に格納されています。
ということは、以下のように呼び出されている`ServeHTTP()`メソッドは、`*http.ServeMux`型のものであると考えられます。
```go
handler.ServeHTTP(rw, req)
```

`*http.ServeMux`型に定義された`ServeHTTP()`メソッドの実装を見てみます。
```go
func (mux *ServeMux) ServeHTTP(w ResponseWriter, r *Request) {
	if r.RequestURI == "*" {
		if r.ProtoAtLeast(1, 1) {
			w.Header().Set("Connection", "close")
		}
		w.WriteHeader(StatusBadRequest)
		return
	}
	var h Handler
	if use121 {
		h, _ = mux.mux121.findHandler(r)
	} else {
		h, r.Pattern, r.pat, r.matches = mux.findHandler(r)
	}
	h.ServeHTTP(w, r)
}
```
`*Request`型からリクエスト情報を取得し、それを元に`findHandler()`メソッドによって対応するハンドラーを探しています。
マルチプレクサにはルーティングが登録されているのでしたね。そこから、リクエスト情報に紐づくハンドラーを検索することができます。

そして、対応するハンドラーの`ServeHTTP()`メソッドが呼び出されています。
これこそ、自身でハンドラーに実装した`ServeHTTP`メソッドです。

#### `sebdah/goldie`パッケージの使用

`g.Assert()`メソッドは、実際に検証を行います。
```go
g.Assert(t, tt.gfName, resp)
```
既に生成されているゴールデンファイルに記録されたレスポンスとテストにおいて出力されたレスポンスを比較し、差分が検出された場合にエラーを発生させます。
引数には、「ゴールデンファイル名(`tt.gfName`)」「テスト内で出力されたレスポンス(`resp`)」を渡しています。

そして、この`Assert()`メソッドは、テスト実行時に`-update`フラグをつけるかどうかで挙動が変わります。
テスト実行時に`-update`フラグをつけた場合、ゴールデンファイルを生成（または上書き）します。
書き込まれるのは、テスト内で出力されたレスポンス（`resp`）です。

以下で挙動の違いを整理しておきました。
| フラグ        | 挙動                                                         |
|--------------|--------------------------------------------------------------|
| `-update`  | ゴールデンファイルを新規作成、または既存ファイルを上書きする。 |
| なし        | 既存のゴールデンファイルと比較し、差分があればテストを失敗させる。 |

#### `integration`ビルドタグ
ファイル上部に以下のようなアノテーションを記述しています。
```go
//go:build integration
```
このような`//go:build xxxx`はビルドタグと呼ばれます。

このビルドタグによって、ソースコードをビルドに含めるかどうかを指定することができます。

例として、`//go:build hoge`というビルドタグをとあるソースコードに付けたとします。
そのソースコードをビルドに含めたい場合は、`-tags=hoge`オプションをつけて実行します。反対に、フラグをつけないとソースコードはビルドに含まれません。

これを利用して、統合テストの実行を制御しています。
今回の場合は、テストの実行に`-tags=integration`オプションをつけないと、統合テストは行われません。

このようにしているのには、エンドポイントの統合テストの負荷が高いために、プロセスを分けて実行したいという狙いがあります。

`make test-app`コマンドでは、テストが全て行われるように内部で`go test ./...`を実行していますが、`-tags`オプションをつけていないため統合テストは実行されません。

統合テストのみを実行するためのタスクをMakefileに定義しています。
`-tags=integration`をつけていることを確認してください。
```Makefile
test-integration:
	$(eval TEST_PATH=$(or $(path),./...))
	$(eval TEST_TAGS=$(tags))
	$(eval TEST_OPTIONS=${opts})
	@echo "Running tests in integration"
	cd ./app/infrastructure/api_test/integration && $(call tests) -tags=integration
```
https://devlights.hatenablog.com/entry/2020/09/24/011502

`Shift+⌘+p`で`setting.json`を開き、以下のように追加しておいてください。

#### CIの所要時間を短縮する
ビルドタグによってテストプロセスを分けて実行できるようにしていることで、CI全体の実行時間を短縮することができます。
以下のように、単体テスト（`unit-test`）と統合テスト(`integration-test`) のジョブの二つを並行処理するようにしています。
```yml
jobs:
    # ユニットテスト
    unit-test:
        name: Run Unit Tests
        runs-on: ubuntu-latest
        steps:
            # 省略
            # appモジュールのテスト
            - name: Run App Test
              run: make test-app
            # pkgモジュールのテスト
            - name: Run Pkg Test
              run: make test-pkg
     # インテグレーションテスト
    integration-test:
        name: Run Integration Tests
        runs-on: ubuntu-latest
        steps:
            # 省略
            - name: Run Api Integration Test
              run: make test-integration

```

すべてのテストを一度に実行するよりも、このように並行処理で行うことでCI所要時間が１分近く短縮されます。※筆者の環境における観測範囲


また、今回は単体テストに含めていますが、リポジトリやクエリサービスのテストもテストDB環境を用意していたり負荷が高いので、そちらもビルドタグをつけてプロセスを分けてあげると更なる時間の短縮も見込めそうですね。

今後このAPIに追加実装などをしていく場合、ゴールデンテスト手法を用いたリグレッションテストを実行することで、変更による意図しない影響を防ぐことができます。
