# Kindとは
Kindは、DockerコンテナをNodeとして転用し、クラスターとして構成してくれる開発用ツールです。
Kubernetes In DockerでKindのようです。

https://kind.sigs.k8s.io/

Kindに関しては深入りせず、早速デプロイしてk8sを動かしてみましょう。

# Kindクラスターにデプロイする
以下の手順でデプロイします。
- Kindクラスター用のconfigファイルを用意
- Kindクラスターを起動
- manifestを適用

以下に従ってKindをインストールしておいてください。

https://kind.sigs.k8s.io/docs/user/quick-start/#installation

## Kind用のconfigファイルを用意
Worker Nodeをマルチノードとしたり、Kindクラスターの設定をconfigファイルで管理できます。

https://kind.sigs.k8s.io/docs/user/quick-start/#configuring-your-kind-cluster

以下のようにファイルを記述します。

1つのControle Planeノード、1つのWorkerノードをクラスタに用意する構成です。

```yaml:k8s/cluster/kind/config.yaml
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
  - role: control-plane
  - role: worker
    extraPortMappings:
      - containerPort: 30080 # NodePort
        hostPort: 80
        protocol: TCP
```

また、前章にてNodePort Serviceで公開するようにmanifestを記述しており、Worker Nodeの`:30080`番ポートへの通信がPodの`:80`番ポートにService経由で転送されるようにしていました。
Kindでは、Worker NodeはDockerコンテナとして起動されるので、以下のようにホストポートとWorker Nodeコンテナポートのマッピングをしています。

```yaml
- role: worker
    extraPortMappings:
      - containerPort: 30080 # NodePort
        hostPort: 80
        protocol: TCP
```

https://kind.sigs.k8s.io/docs/user/quick-start/#mapping-ports-to-the-host-machine

これで、`http://localhost:80`の通信がWorker Nodeの`:30080`に転送されるようになります。

## クラスタにコンテナイメージをロードする
Kindでは、デプロイするコンテナイメージを起動したクラスタにダウンロードしておく必要があります。

https://kind.sigs.k8s.io/docs/user/quick-start/#loading-an-image-into-your-cluster

k8s一般の話ではないかと思うのでさくっといきます。

::::message
この作業をせずにデプロイしようとすると、以下のようなエラーが出ます。
```
 unpack image "docker.io/library/app:20251123173531": failed to resolve reference "docker.io/library/app:20251123173531": pull access denied, repository does not exist or may require authorization: server message: insufficient_scope: authorization failed
```

`docker.io/library`、つまりDocker Hubのリポジトリにイメージを探しにいってくれています。
しかし、ビルドしたイメージはローカルマシン上にしかなかったため存在せず、デプロイに失敗した感じです。
::::

まずはイメージビルドから行います。
2章あたりでも行なったことです。

今回は、`app`イメージにタイムスタンプのイメージタグをつけて`docker build`しましょう。
```bash
TIMESTAMP=$(date +"%Y%m%d%H%M%S")
docker build -t app:$TIMESTAMP .
```

`echo $TIMESTAMP`とかでタイムスタンプに何が適用されたかは確認して控えておいてください。

ビルドされたイメージを以下のコマンドでkindクラスターにロードしましょう。
```bash
kind load docker-image app:{TIMESTAMP} --name sandbox
```
これで準備が整いました。

```yml:k8s/values/development/values.yaml

  name: app
```

### kube-proxyがControl Planeにもある
`kubectl get pods`で叩くとkube-proxyが出力されたことからわかるように、kube-proxyはpodとして動作しているようです。

```
NAMESPACE            NAME                                            NODE
// ...
kube-system          kube-proxy-fhbw8                                sandbox-control-plane
// ...
kube-system          kube-proxy-rskt5                                sandbox-worker
```

そして、Worker Nodeのコンポーネントとしてkube-proxyについては取り上げていました。
しかし見てみると、Control PlaneとWorker Nodeの両方に配置されています。

公式documentをよく見てみると、「どのNode上でもkube-proxyは実行されている」とのことが書いてあります。

> Every node in a Kubernetes cluster runs a kube-proxy (unless you have deployed your own alternative component in place of kube-proxy).

https://kubernetes.io/docs/reference/networking/virtual-ips/#kube-proxy

つまり、Control PlaneもNodeであるということでしょう。
以下の一文のmachineは、nodeと置き換えて捉えても問題ないと思います。

> Control plane components can be run on any machine in the cluster.

https://v1-33.docs.kubernetes.io/docs/concepts/architecture/?utm_source=chatgpt.com#control-plane-components

また、kube-proxyはDaemonSetとして展開されているので、Controle Plane Nodeにあって当然、と考えることもできますね。

それに、Control Planeには、前章で説明したようなコンポーネント(`etcd`, `kube-apiserver`, `kube-scheduler`)がPodとして存在していることが出力からわかります。kube-proxy は、Podへの通信(ネットワーク)に関わる制御を行なうものですから、やはりControl Planeにも必要な存在であることが言えそうですね。

::::message
`resolv.conf`は、Linuxサーバーにおける名前解決に関する設定が記載されているファイルになります。

OSには「リゾルバ」というプログラムが入っています。このリゾルバはDNSクライアントに相当するものであり、Linux系OSの場合は`/etc/resolv.conf`を参照してDNSサーバーにipアドレスを問い合わせます。

```bash

# DNSサーバのIPアドレス => corednsのserviceのClusterIP
nameserver 10.96.0.10 
# 名前解決の細かい挙動設定 => ドットが5個未満の名前はsearchドメインを補完して解決
options ndots:5
```

### kindnetって何
主要なコンポーネントとして取り上げなかったものについて説明します。
と言っても、kindnet pod自体は、名前から察せられるようにKind Cluster特有のものになります。

kindnetはCNI（Container Network Interface）プラグインの一種です。

https://kindnet.es/docs/design/cni/

CNIとは、Podやコンテナのネットワークを管理・接続するための標準仕様（インターフェース）です。

https://kubernetes.io/ja/docs/concepts/extend-kubernetes/compute-storage-net/network-plugins/

k8sのネットワークといえば、前章でkube-proxyについて取り上げました。
> - kube-proxyがService/EndpointSliceリソースをもとにiptablesを使い、Node上にネットワークルールを構築している
> - Linuxカーネルがこれらのルールを適用することで、Service宛のリクエストがPodのIPアドレスに変換される

対して、CNIプラグインは**Podネットワークの構築**の役割を果たしているといえます。

「Podネットワークの構築」の意味するところについて、少しだけ解像度を上げていきましょう。

CNIの文脈において、**container = network namespace（netns)** になります。
::::message
netnsはLinuxのネットワーク機能です。
１台のマシン上に仮想ホストを作成でき、その仮想ホストにはIPアドレスやNICを持たせることもできます。
::::

インターフェースとしては以下の二つが主に定められています。
```
- ADD : 
  - netnsにinterfaceを作成(→別netnsと通信する口を作る)
  - netnsにipアドレスを割り当て
  - ルーティング設定
- DEL : 
　- interfaceを削除（→通信の口を閉じる）
  - IPアドレスを解放
  - ルーティングを削除
```

ここで理解しておきたいのは、**Pod単位でnetnsが作られており、コンテナはそのnetnsを共有している**ことです。
http-server podのnetnsをコンテナが共有していることを以下で確認します。
```bash
# Podのnetns idを確認
% kubectl exec  app-http-server-5449665dbb-7mkjc -n app-development -- readlink /proc/1/ns/net
Defaulted container "http-server" out of: http-server, nginx
net:[4026534098]

# http-serverコンテナのnetns idを確認
% kubectl exec  app-http-server-5449665dbb-7mkjc -c http-server -n app-development -- readlink /proc/1/ns/net
net:[4026534098]

# nginx(サイドカー)コンテナのnetns idを確認
% kubectl exec  app-http-server-5449665dbb-7mkjc -c nginx -n app-development -- readlink /proc/1/ns/net
net:[4026534098]
```

CNIプラグインはnetns(≒ Pod)にIPアドレスを付与し、netns外との通信ができるように仮想NIC(Network Interface Card)であるveth(Virtual Ethernet Device)を配置します。
![](https://storage.googleapis.com/zenn-user-upload/236720b4516b-20260404.png)

これではまだPod同士は独立したネットワークです。では、どうやってPod同士、ひいてはWorker Node(ホストマシン)外と通信できているのでしょうか。

ここからはLinuxのお話にもなってきますが、vethはペアで成り立ちます。
https://note.com/minato_kame/n/n7de03017804d

以下のように、vethがペアで接続されることで、Podの独立したnetnsがホスト（root netns）と通信可能になります。これにより、PodネットワークがWorker Nodeのルーティングに組み込まれます。
![](https://storage.googleapis.com/zenn-user-upload/59acefbd76df-20260404.png)

::::message
CNIはインターフェースであり、実装方法は様々です。

https://www.tkng.io/cni/

例えば、今回のKindの場合、Worker NodeはDockerコンテナです。
Worker Nodeコンテナのeth0も実際はvethであり、ホストマシンのvethと接続されます。そのvethがブリッジ(L2スイッチ)に接続され、ネットワークを実現しているようです。
参考：https://note.com/minato_kame/n/n81b1a4396807
::::

まとめると、
- CNIプラグインがPodという1つのnetnsにIPアドレスを割り当て、vethでWorker Nodeのroot netnsと接続し、ルーティングに組み込むことで、「Pod間ネットワークの構築」が実現されている

といえそうです。

さらに、kube-proxy, Serviceを含めてk8s ネットワークを改めて整理すると、
- kube-proxyがService/EndpointSliceリソースをもとにiptablesを使い、Node上にネットワークルールを構築している
- Linuxカーネルがこれらのルールを適用することで、Service宛のリクエストがPodのIPアドレスに変換される
- CNIプラグインがPodのIPアドレスを管理し、Pod間およびPodと外部のネットワークを接続することで、通信が実現される

k8sのネットワーク実現方法の解像度が上がってきましたね。

### kubeletはPodではない？
Worker Nodeで主要なコンポーネントとしてkubeletの説明をしました。
kubeletは、Controle Planeのkube-api-serverから指示を受け取ってPodのライフサイクルを制御するのでした。

しかし、クラスター内のPod一覧を覗いても、kubelet podは特に見当たりませんでしたね。
つまり、kubeletはPodではなく、Node上で動くデーモンプロセスであるということです。
Nodeの要件は以下のように定められているようです。
>ノード適合性テストを実行するには、ノードは標準的なKubernetesノードと同じ前提条件を満たす必要があります。最低限、ノードには以下のデーモンがインストールされている必要があります。
>・Docker、containerd、CRI-OなどのCRI互換コンテナランタイム
>・kubelet

https://v1-33.docs.kubernetes.io/docs/setup/best-practices/node-conformance/?utm_source=chatgpt.com#node-prerequisite

試しに、起動中のWorker Node(KindなのでDockerコンテナですが)に入って見てみましょう。
`docker exec -it [ps id] bash`とかで入ってください。
```bash
root@sandbox-worker:/# which kubelet
/usr/bin/kubelet
```
確かにkubeletがインストールされていますね。

また、kubeletプロセスが起動していることも確認できました。
```bash
root@sandbox-worker:/# ps -eo pid,comm,cmd,%cpu,%mem | grep kubelet
    176 kubelet         /usr/bin/kubelet --bootstra  1.3  1.2
```

kubeletがちゃんと動いていることをさらに確かめてみましょう。以下でkubeletのlogがリアルタイムで出力されます。
```bash
root@sandbox-worker:/# journalctl -u kubelet -f
```
試しに、別のターミナルで`kubectl`でPodを削除してみてください。
```bash
kubectl delete pod app-http-server-5449665dbb-7mkjc -n app-development
```
すると、ログに以下のようなPod削除関連のログが出ていることが確認できるはずです。以下で抜粋&見やすい形で示します。
```bash
# コンテナの状態削除
RemoveStaleState: removing container nginx
RemoveStaleState: removing container http-server
RemoveStaleState removing state

# ボリュームのアンマウント
UnmountVolume started for volume "kube-api-access..."
UnmountVolume started for volume "nginx-conf"
UnmountVolume.TearDown succeeded
Volume detached

# コンテナ削除
RemoveContainer containerID=...
```

`kubectl`はkube-api-serverへリクエストするコマンドです。`kubectl delete pod`コマンドを叩いた時、kubeletはapi-serverから削除イベントを受け取っていて、実際にコンテナの削除を行なっていたということでしょう。
