# Amazon EKS（Elastic Kubernetes Service)
EKSは、AWSから提供されるK8sのマネージドサービスの１つです。

https://docs.aws.amazon.com/ja_jp/eks/latest/userguide/what-is-eks.html

Controle PlaneはAWS側が管理します。これが「マネージド」の意味するところです。
これにより、開発者の関心は、アプリケーションPodが動くWorker Nodeのみに限定することができます。

![](https://storage.googleapis.com/zenn-user-upload/4d6dbcce59a4-20260411.png)
*https://docs.aws.amazon.com/ja_jp/eks/latest/userguide/what-is-eks.html*

上の画像から分かる通り、Worker NodeにはEC2インスタンスが利用されます。
https://docs.aws.amazon.com/ja_jp/AWSEC2/latest/UserGuide/concepts.html

EC2インスタンスとは、「仮想サーバー」です。AWS物理サーバーの上で動く仮想マシンであり、使用するAMI(Amazon Machine Image)を選択可能です。AMI = OSイメージと捉えてください。
また、インスタンスタイプ(= CPUやMemoryといったサーバーの性能のグレードの単位)の選択も可能になっています。

# Terraform
Terraformは、[HashiCorp](https://www.hashicorp.com/ja)社により提供される、IaC(Infrastructure as Code)になります。
https://developer.hashicorp.com/terraform

IaCにより、インフラの構成や設定をコードとして管理できます。
https://cloud.sakura.ad.jp/column/iac/#anc01

Terraformは、主たるクラウドプロバイダーに対応しており、AWSだけでなくAzure, GCPなどのあらゆるインフラの管理が可能です。

## Terraformを用いたインフラ設定のフロー
先んじて、Terraformでどのようにインフラ設定を追加/修正していくのかのフローを理解しておきましょう。

1. tfファイルを記述する
2. `terraform plan`で、適用予定の差分をプレビューする
3. `terraform apply`で、その差分を実際のインフラに適用する


![](https://storage.googleapis.com/zenn-user-upload/2f25ede635cf-20260411.png)
*https://developer.hashicorp.com/terraform/intro#how-does-terraform-work*

`1. tfファイルを記述する（理想の状態を定義）`は、この後実際に記述していくのでいいとして、2・3はここである程度理解しておきましょう。

### 2.`terraform plan`で、適用予定の差分をプレビューする

https://developer.hashicorp.com/terraform/cli/commands/plan

planコマンドの内部では以下のようなプロセスが行われているようです。
1. Stateファイルと実際のリモートオブジェクトと同期(refresh)
2. Stateファイル（現在）とtfファイル（理想の構成）を比較する
3. 差分（実行予定の変更）を算出・表示する

tfファイルを変更した際に、適用前に差分を確認できるため、意図しない変更が含まれていないかを検証でき、安全な運用につながります。

ちなみにStateファイルとは、「現在のインフラ状態」をjsonで表現したものになります。Terraformコードで宣言しているリソースと、実際のリモートリソース（ID, ARNなど）がマッピングされています。
https://developer.hashicorp.com/terraform/language/state

以下のように、tfファイル上のリソースはAWS上のこのリソースを指すという情報が対応づけされているんですね。
```json
{
  "module": "module.eks",
  "type": "aws_eks_cluster",
  "instances": [
    {
      "attributes": {
        "arn": "arn:aws:eks:...:cluster/eks-sandbox" //<-- 実リソースを一意に識別する情報（Terraformが操作対象を特定するために使用）
      }
    }
  ]
}
```
このように、TerraformはStateファイルを通じて「どのリソースを操作するか」を正確に把握しています。

このStateファイルはデフォルトではローカルで管理されるようになっていますが、S3などリモート上で管理されることが多いです。
ローカルだと、以下のような困り点があります。
- チームで共有できない
- 誰が最新の状態か分からない
- 上書きによる競合が発生する
- Stateファイル消失時のリスクが高い

しかしながら今回は簡単なハンズオンですので、ローカルでこのStateファイルを管理していきます。

### 3.`terraform apply`で、その差分を実際のインフラに適用する 
apply時にも内部的にplanが実行されているようです。

その上で、以下のように振る舞います。
1. 実際のリモートリソースに対して、差分に基づいた変更を行う
2. 変更結果に基づいて、Stateファイルを更新する

----

`provider`ブロックでは、使用するプロバイダーに関する設定を記述します。今回は、AWSを利用するので`aws`が設定値となります。

## 1. VPC
VPC(Amazon Virtual Private Cloud)とは、AWS内に仮想ネットワークを構築できるリソースです。
これはつまり、「AWSの物理ネットワークの上に、論理的に隔離されたネットワークを作る」ことと言えます。

https://docs.aws.amazon.com/ja_jp/vpc/latest/userguide/what-is-amazon-vpc.html

リソースを配置していくのは「VPC内」になります。
インフラ構成を配置する「枠」をAWS内に用意することから始めるということです。

![](https://storage.googleapis.com/zenn-user-upload/b1ca0a76c6db-20260412.png)

VPCをmoduleを用いて宣言します。

```tf:terraform/main.tf
module "vpc" {
  source = "terraform-aws-modules/vpc/aws"

  name = "eks-sandbox-vpc"
  cidr = "10.0.0.0/16"

  azs             = ["ap-northeast-1a", "ap-northeast-1c"]
  public_subnets  = ["10.0.0.0/24", "10.0.1.0/24"]
  private_subnets = ["10.0.2.0/24", "10.0.3.0/24"]

  enable_nat_gateway = true
  single_nat_gateway = true

  tags = {
    Name        = "eks-sandbox-vpc"
    Terraform   = "true"
    Environment = "dev"
  }
}
```

https://registry.terraform.io/modules/terraform-aws-modules/vpc/aws/latest

### Terraformのresourceとmodule
Terraformのresource, moduleについてここで触れておきます。

https://developer.hashicorp.com/terraform/language/resources

以下のようにイメージしておきましょう。

```

```

`source`は、moduleの定義元を指します。
指定方法には以下があります：

- ローカルパス（例：./modules/vpc）
- Gitリポジトリ
- Terraform Registry

https://developer.hashicorp.com/terraform/language/block/module#source

今回は、Terraformレジストリ上で公開されている`vpc`moduleを利用するので、`terraform-aws-modules/vpc/aws`を設定しています。

https://registry.terraform.io/modules/terraform-aws-modules/vpc/aws/latest

設定しているInputについて、それぞれ見ていきます。

`name`は`vpc`につけている名前です。
`cidr`では、VPC内で使用できるプライベートIPアドレスの範囲を設定しています。
```tf
name = "eks-sandbox-vpc"

```

VPCにおけるCIDRブロックについては以下に説明があります。
https://docs.aws.amazon.com/ja_jp/vpc/latest/userguide/vpc-cidr-blocks.html

ネットワーク知識としてのCIDRを知らない方は、以下を参照ください。
https://wa3.i-3-i.info/word11989.html

今回の設定ですと`10.0.0.0 〜 10.0.255.255`のIPアドレス空間、つまり約65000個のIPアドレスを使えるということになります。

以下では、利用するAvailability Zoneのリストを設定しています。
```tf
azs             = ["ap-northeast-1a", "ap-northeast-1c"]
```
リージョンとして`ap-northeast`(東京)を設定していました。リージョンは、複数のデータセンターからなっています。
ここでは、`1a` `1c`の二つを利用することで、冗長化を図ることができています。

![](https://storage.googleapis.com/zenn-user-upload/495960ee628c-20260412.png)

::::message
冗長化なんて今回必要ないんですが、「複数のAZを利用することが必要」というALBリソース(後述)の制約のため、2つ選択しています。

> You must select at least two Availability Zone subnets.

https://docs.aws.amazon.com/elasticloadbalancing/latest/application/application-load-balancers.html
::::

以下では、VPCで4つのサブネットを設定しています。
```tf
public_subnets  = ["10.0.0.0/24", "10.0.1.0/24"]
private_subnets = ["10.0.2.0/24", "10.0.3.0/24"]
```

サブネットは一般的なネットワーク用語です。VPCという仮想ネットワークを、４分割するということになります。
https://wa3.i-3-i.info/word11973.html

publicとprivateで分かれていることからもわかりますが、サブネットには主に二つの種類があります。
- パブリックサブネット：
    - インターネット ↔︎ サブネットで通信が可能
- プライベートサブネット：
    - インターネット → サブネットの通信が不可能
    - サブネット → インターネットの通信はNATがあれば可能

パブリックサブネットのルートテーブルには、デフォルトルート(0.0.0.0/0)としてInternet Gatewayが設定されているため、VPC外への通信がそのまま可能です。

Internet Gatewayは、VPCとインターネットとの間の通信を可能にするリソースと捉えればいいです。
https://docs.aws.amazon.com/ja_jp/vpc/latest/userguide/VPC_Internet_Gateway.html

また、サブネットは、各AZごとに作成する必要があります。2つのAZに１つずつパブリックサブネット、プライベートサブネットを置いています。
https://docs.aws.amazon.com/ja_jp/vpc/latest/userguide/configure-subnets.html#subnet-basics

ちなみに、`vpc`moduleにはInternet Gatewayリソースも含まれています。この時点で以下のような構成図になりました。
![](https://storage.googleapis.com/zenn-user-upload/4139cd965646-20260412.png)

最後に、NAT Gateway(Network Address Translation)を１つプライベートサブネットに配置されるようにします。
```tf
enable_nat_gateway = true
single_nat_gateway = true
```
https://docs.aws.amazon.com/ja_jp/vpc/latest/userguide/vpc-nat-gateway.html

プライベートサブネットのデフォルトルートにはNATが設定されます。
つまり、プライベートサブネットからインターネットへの通信においては、パケットがNATを経由してInternet Gatewayから出るという形になります。

### Internet GatewayとNAT Gateway
ここで、この二つの振る舞いについてまとめておきます。

その前に、AWSの文脈では、２つのIPアドレスがあることを整理しておきましょう。

- パブリックIP
    - インターネットからルーティング可能なIPアドレス
- プライベートIP
    - VPC内でのみ有効な仮想のIPアドレス

リソースは基本的にプライベートIPが付与されていますが、加えてパブリックIPアドレスを付与することもできます。

パケットがInternet Gatewayを通過する際に、リソースに付与されているパブリックIPアドレスを送信元IPアドレスとしてインターネットにトラフィックされるようになっています。


例えばEC2インスタンスが「パブリックサブネットに置かれている」 + 「パブリックIPアドレスが付与されている」場合、

1. パケットがデフォルトルートとしてInternet Gatewayにルーティングされる
2. 付与されているパブリックIPアドレスを送信元IPアドレスとしてインターネットにトラフィックされる

という感じになります。

![](https://storage.googleapis.com/zenn-user-upload/d1ce12051592-20260412.png)

NAT Gatewayは、送信元のプライベートIPアドレスをパブリックIPアドレスに書き換えて(SNAT)、Internet Gatewayにルーティングします。

例えばEC2インスタンスが「プライベートサブネットに置かれている」+「パブリックサブネットにNATが配置されている」場合、

1. パケットがデフォルトルートとしてNAT Gatewayにルーティングされる
2. NAT Gatewayで送信元IPアドレスがパブリックアドレスとして変換される
3. パブリックサブネットのデフォルトルートとしてInternet Gatewayにルーティングされる
4. インターネットにトラフィックされる

という感じになります。

![](https://storage.googleapis.com/zenn-user-upload/e85538422479-20260412.png)

## 2. EKS Cluster

### kubelet→Controle Planeの通信経路
EKS Clusterは、k8sクラスターです。
概要は先述したので省きますが、ここは再喝しておきます。

> Controle PlaneはAWS側が管理します

https://docs.aws.amazon.com/ja_jp/eks/latest/best-practices/subnets.html


これはつまり、Controle Planeは自分の配置したVPCではなく、AWSの管理する別のVPC内にあるということです。

![](https://storage.googleapis.com/zenn-user-upload/67fdcdf92536-20260418.png)
*https://docs.aws.amazon.com/ja_jp/eks/latest/best-practices/subnets.html*

::::message
図にあるように、Controle Plane↔︎Worker Nodeの通信は2通りの方法があります。
どちらの方法になるかは、[`kube-api-server`のエンドポイント](https://docs.aws.amazon.com/ja_jp/eks/latest/userguide/cluster-endpoint.html)をPublicにするかPrivateにするかで変わります。

デフォルトでは`kube-api-server`のエンドポイントがPublicになるので、デフォルトの設定値前提で今回は進めます。

また、Publicにすることで気軽に`kubectl`によりapi-serverに接続したいためでもあります。本来は、Privateにするのが望ましいかもしれません。
::::

ここで、k8sクラスター起動時のことを思い出してみます。
Worker Node内のkubeletがkube-api-serverに「私（Node）を登録してください」とリクエストを投げるのでした。
つまり、初っ端からWorker Node→Controle Planeへの通信が発生するわけです。
そして、Worker NodeはPrivate Subnetに置いています。

つまり、kubeletが`POST /api/v1/nodes`(Node登録API)を叩いてクラスターにJoinするには、NATが必要です。

![](https://storage.googleapis.com/zenn-user-upload/2777979a9a8f-20260418.png)

今回、外部APIを叩くようなアプリケーションをdeployするわけではないので、VPC作成時にNATを配置した理由はここにあったというわけです。

それでは、記述していきます。

### EKSクラスターのメインの記述
```tf: terraform/main.tf
# eks cluster
module "eks" {
  source = "terraform-aws-modules/eks/aws"

  name               = "eks-sandbox"
  kubernetes_version = "1.33"

  vpc_id     = module.vpc.vpc_id
  subnet_ids = module.vpc.private_subnets

  endpoint_public_access = true

  create_iam_role = false

  addons = {
    coredns    = {}
    vpc-cni    = {}
    kube-proxy = {}
  }

  tags = {
    Name        = "eks-sandbox-cluster"
    Terraform   = "true"
    Environment = "dev"
  }
}
```

https://registry.terraform.io/modules/terraform-aws-modules/eks/aws/latest

moduleとして`terraform-aws-modules/eks/aws`を使っていることには注目しておきましょう。

`vpc_id`にはクラスタが属するVPCのIDを、`subnet_ids`には、Worker Nodeの属するSubnetのID配列をおきます。
```tf
vpc_id     = module.vpc.vpc_id
subnet_ids = module.vpc.private_subnets
```
上で宣言した`vpc`moduleのoutputにアクセスして設定しています。

以下では、クラスターをPublicエンドポイントで設定する記述をしています。ここは先述のとおりです。
```tf
endpoint_public_access = true
```

create_iam_role = false

### IAM Role
IAM(Identity Access Management)は、リソースへのアクセスを管理するためのものです。
用語がいくつかありますが、一文で以下のように表せます。
- **プリンシパル**が、**IAMロール**を引き受け ( = **AssumeRole**)、そのロールに付与された**ポリシー**に基づいてAWSリソースを操作できる

| 用語            | 説明                                                                 |
|-----------------|----------------------------------------------------------------------|
| プリンシパル    | リソースにアクセスするユーザー・アプリケーション                     |
| IAMポリシー     | リソースへのアクセス権限を定義するJSONドキュメント                   |
| IAMロール       | 特定のプリンシパルが引き受けることができる権限の集合（ポリシーを持つ）|
| AssumeRole      | プリンシパルがSTSにリクエストし、IAMロールを引き受けるための一時的な認証情報を取得する操作 |

リソースは、IAMロールの権限なしには他リソースを操作できません。
今回で言うと、EKSクラスターは
- Worker NodeとしてEC2インスタンスを管理
- ENI(Elastic Network Interface)を作成してEC2にアタッチ

など、他リソースへアクセスする必要があります。

そのため、EKSには必要なリソースを操作できるIAMロールをアタッチしてやる必要があります。
```tf
# IAM role for EKS Cluster
resource "aws_iam_role" "eks_cluster_role" {
  name               = "eks-cluster-role"
  assume_role_policy = data.aws_iam_policy_document.eks_cluster_assume_role_policy.json
}

data "aws_iam_policy_document" "eks_cluster_assume_role_policy" {
  statement {
    sid    = "AllowEKSClusterAssumeRole"
    effect = "Allow"
    principals {
      type        = "Service"
      identifiers = ["eks.amazonaws.com"]
    }
    actions = [
      "sts:AssumeRole"
    ]
  }
}

resource "aws_iam_role_policy_attachment" "eks_cluster_AmazonEKSClusterPolicy" {
  policy_arn = "arn:aws:iam::aws:policy/AmazonEKSClusterPolicy"
  role       = aws_iam_role.eks_cluster_role.name
}
```

`data`ブロックは、既存リソースや外部情報を読み取り、Terraform内のあらゆるリソース定義で参照されるデータソースを宣言します。
https://developer.hashicorp.com/terraform/language/block/data


上の記述では、
1. IAMロール(`eks_cluster_role`)を用意
2. IAMロールを引き受けることができるプリンシパルを定義した信頼ポリシー（eks_cluster_assume_role_policy）を定義し、`eks_cluster_role`に設定
3. IAMロールを引き受けて何ができるかの権限を定義したポリシー(`eks_cluster_AmazonEKSClusterPolicy`)をIAMロールにアタッチ

といったことを行なっています。
![](https://storage.googleapis.com/zenn-user-upload/f514e5c31e6c-20260418.png)

そして、これにより以下のことを実現します。
- EKSがAssumeRoleができる
- このロールにより`AmazonEKSClusterPolicy`で許可された操作ができる

https://docs.aws.amazon.com/ja_jp/aws-managed-policy/latest/reference/AmazonEKSClusterPolicy.html

利用したmodule, resourceのリファレンスを以下に記載します。
https://registry.terraform.io/providers/hashicorp/aws/latest/docs/resources/iam_role.html

https://registry.terraform.io/providers/hashicorp/aws/latest/docs/data-sources/iam_policy_document

https://registry.terraform.io/providers/hashicorp/aws/latest/docs/resources/iam_role_policy_attachment

最後に、`eks`moduleにIAMロールを紐づけておきます。
```tf
module "eks" {
  # ...
  create_iam_role = false
  iam_role_arn    = aws_iam_role.eks_cluster_role.arn
  # ...
}
```

### Access Entries
次に、`kubectl`コマンド等によってクラスターにアクセスできるユーザーを管理します。
これには、EKS Access Entriesという機能を利用します。
https://docs.aws.amazon.com/ja_jp/eks/latest/eksctl/access-entries.html
https://docs.aws.amazon.com/ja_jp/eks/latest/userguide/access-entries.html
これは、IAMユーザーと[Kubernetes RBAC](https://kubernetes.io/ja/docs/reference/access-authn-authz/rbac/)を結びつける機能のようです。RBACは、k8sの世界における、ロールベースで権限を管理する認可（authorization）の仕組みのことです。

EKSの設定のみでk8sクラスターの権限設定まで一気通貫で行えるのが便利とされています。

https://www.eksworkshop.com/ja/docs/security/cluster-access-management/understanding


それをTerraform上どう記述していくかというと、eks moduleでは、`access_entries`というinputがあるのでそれを利用します。
https://registry.terraform.io/modules/terraform-aws-modules/eks/aws/latest#cluster-access-entry

```tf:terraform/main.tf
# eks cluster
module "eks" {
# ...
  access_entries = {
    developer = {
      principal_arn     = var.developer_user_arn
      kubernetes_groups = []

      policy_associations = {
        cluster_admin = {
          policy_arn = "arn:aws:eks::aws:cluster-access-policy/AmazonEKSClusterAdminPolicy"
          access_scope = {
            type       = "cluster"
            namespaces = []
          }
        }
      }
    }
  }

# ...
}

# Variables for IAM user
variable "developer_user_arn" {
  description = "IAM user ARN for developer"
  type        = string
  default     = "arn:aws:iam::<YOUR_ACCOUNT_ID>:user/<YOUR_NAME>"
}
```

::::message
`variable`ブロックは、その名の通り変数です。`terraform apply`実行時にdefault値を上書きして使うことも可能という特徴があります。

https://developer.hashicorp.com/terraform/language/block/variable
::::

上の記述によって、開発者のIAMユーザー（= プリンシパル）をAccess Entryに登録し、そのユーザーに`AmazonEKSClusterAdminPolicy`を紐づけています。

`AmazonEKSClusterAdminPolicy`は、RBACにおける`cluster-admin`にマッピングされます。
https://docs.aws.amazon.com/ja_jp/eks/latest/userguide/access-policy-permissions.html#access-policy-permissions-amazoneksadminpolicy

指定のIAMユーザーはEKSクラスターに対して、RBACでいうcluster-admin相当のKubernetes操作権限を持つようになり、kubectl経由でクラスター内のあらゆるリソースを作成・更新・削除できるようになるということですね。

::::message
cluster-adminというスーパー権限を持たせることは、最小権限の原則に反していますが、あくまでハンズオンで色々できるようにするためということでご了承ください。
::::

RBACは「追加型」の権限設定であり、デフォルトはDenyとなります。そのため、明示的に権限が付与されていないIAMユーザー（またはロール）は、Kubernetes APIへの操作ができないということになります。

::::message
Kindクラスターの場合は、そういった認可制御を入れてなくてもkubectlができていました。
これの理由はシンプルで、RBACの制御が有効でなかったというだけになります。
::::

### Security Group
Security Groupは、リソースに紐づけることができる「通信ルールのまとまり」です。よく仮想のファイアウォールだとも表現されます。

通信ルールには２種類あります。
- Inbound
    - 外→内の通信。Igressともいう
- Outboud
    - 内→外の通信。Egressともいう。

例えば、Security Group Aに、
- Security Group Bからの通信を許可
- Security Group Aから発する通信は制限しない

ルールを付与した場合、以下のようなイメージです。

![](https://static.zenn.studio/user-upload/ced227acddb7-20260423.png)

以下の記述で、次のようなルールを持つSecurity GroupをNode Groupに付与します。
- Inbound Rule:
    -  ALBのSecurity Groupから、Nodeの30000〜32767ポートへの通信を許可する
- Outbound Rule:
    - Nodeから発する通信は全て許可

```tf:terraform/main.tf
module "eks_node_group" {
  # ...
  create_security_group = true
  security_group_ingress_rules = {
    alb_nodeport = {
      description                  = "Allow ALB to communicate with Node Group"
      from_port                    = 30000
      to_port                      = 32767
      protocol                     = "tcp"
      referenced_security_group_id = aws_security_group.alb_sg.id
    }
  }

  security_group_egress_rules = {
    all = {
      description = "Allow all outbound traffic"
      from_port   = 0
      to_port     = 0
      protocol    = "-1" // 全てのprotocolを許可。ref: https://registry.terraform.io/providers/hashicorp/aws/latest/docs/resources/vpc_security_group_ingress_rule#ip_protocol-1
      cidr_ipv4   = "0.0.0.0/0" // 全てのアドレス範囲
    }
  }
  # ...
}
```

ALBに関しては後述します。そもそもALBのSecurity Groupは宣言してないのでまだ存在しませんが、`aws_security_group.alb_sg.id`と書いておいてください。

また、`30000〜32767`はk8sのNodePortのデフォルト範囲です。やや広いですが、ハンズオンとしては一旦これでよしとします。

## 4. ALB
続いて、ALB(Application Load Balancer)を配置します。

https://docs.aws.amazon.com/ja_jp/elasticloadbalancing/latest/application/introduction.html

ALBは、**アプリケーション層(L7)でのルーティングが可能**な**リバースプロキシ型**の**ロードバランサ**です。

用語を整理します。
- **L7ルーティング**
    - [OSI参照モデル](https://aws.amazon.com/jp/what-is/osi-model/)の7層目 = アプリケーション層
    - データ通信の最上レイヤー
    - API呼び出しはこのレイヤーに属すると考えれば良い
        - 通信プロトコルはHTTPなど
- **リバースプロキシ**
    - 複数以上のアップストリームサーバー（ = 主となるアプリケーション・バックエンドサーバー）の前段に立つ
        - 複数のサーバーへの負荷分散 / ルーティングを行う
        - また、主サーバーを保護できるなどのメリットも。
    - nginxなどもこれに該当
- **ロードバランサ**
    - 負荷の偏りを防ぐ(スケーラビリティ向上)
    - 障害時の可用性向上
        - ヘルスチェックを行っており、正常なアップストリームサーバーにのみリクエストを流す


こちらも提供されている公式moduleを利用します。
https://registry.terraform.io/modules/terraform-aws-modules/alb/aws/latest      

```tf:terrafrom/main.tf
module "alb" {
  source = "terraform-aws-modules/alb/aws"

  name    = "eks-sandbox-alb"
  vpc_id  = module.vpc.vpc_id
  subnets = module.vpc.public_subnets

  enable_deletion_protection = false # ハンズオン用なのでALBを削除できるようにする

  tags = {
    Name        = "eks-sandbox-alb"
    Terraform   = "true"
    Environment = "dev"
  }
}
```

ポイントとしては、ALBリソースをパブリックサブネットに置いていることです。
```tf
subnets = module.vpc.public_subnets
```

Node Groupをプライベートに置いていたので、インターネットには直接アクセスできません。そのため、パブリックサブネットに配置したALBを入口として、そこから内部のNodeへルーティングするようにします。
![](https://static.zenn.studio/user-upload/ec81d651fc8f-20260425.png)

### リスナールール
リスナールールは、リクエストの条件（パスやホスト名など）に基づいて、適切なターゲットグループへルーティングを行います。

今回は、
- ALBに到達した`HTTP:80`のリクエストを指定のターゲットグループにルーティングする

というふうにしたいと思います。
リスナールールはL7を見るコンポーネントなので、ドメイン名やパスでも制御は可能です。
が、今回は独自ドメインも発行しませんし、デプロイするサービスも１つなので、単純にすべてのリクエストを単一のターゲットグループへ転送するシンプルな構成とします。


![](https://static.zenn.studio/user-upload/ece41ea1dcdd-20260425.png)


https://registry.terraform.io/providers/hashicorp/aws/latest/docs/resources/lb_listener
```tf:terraform/main.tf
resource "aws_lb_listener" "http" {
  load_balancer_arn = module.alb.arn
  port              = 80
  protocol          = "HTTP"
  default_action {
    type             = "forward"
    target_group_arn = aws_lb_target_group.alb_tg_to_ng.arn # 後ほど設定
  }
}
```
::::message
httpはデフォルトで80ポートを使用します。
そのため、この設定はHTTP（ポート80）での通信を受け付けるリスナーを定義していることになります。
::::

::::message
今回は、単にHTTP通信を受け入れ指定のターゲットグループへ渡すという記述をしています。

他にも、ALBはL7ルーティングということで
- パスベースルーティング
- ホストベースルーティング
- HTTPヘッダベースルーティング

といったようなルーティング設定が可能です。
::::

### ターゲットグループ
ターゲットグループは、リスナールールによってルーティングされる宛先（= ターゲット）の集合体です。

今回用意しているアプリケーションサーバーは、k8sのNodePort Serviceによって、Worker Node(= EC2)の30080ポートを開いていました。

そのため、「EC2インスタンスの30080ポートにHTTPリクエストを転送する」というターゲットグループを設定します。

https://registry.terraform.io/providers/hashicorp/aws/latest/docs/resources/lb_target_group

```tf:terraform/main.tf
resource "aws_lb_target_group" "alb_tg_to_ng" {
  name        = "eks-sandbox-alb-tg"
  port        = 30080
  protocol    = "HTTP"
  target_type = "instance"
  vpc_id      = module.vpc.vpc_id

  health_check {
    path                = "/healthz"
    protocol            = "HTTP"
    matcher             = "200-399"
    interval            = 30
    timeout             = 5
    healthy_threshold   = 2
    unhealthy_threshold = 2
  }

  tags = {
    Name        = "eks-sandbox-alb-tg"
    Terraform   = "true"
    Environment = "dev"
  }
}
```

また、その宛先ターゲットグループに対するヘルスチェック設定を記述しています。Node A, Bの２つがあったとして、Node Aのヘルスチェックが失敗したとします。すると、Node Aはターゲットグループのルーティング対象から除外されるようになります。

ちなみに、アプリケーションコードにヘルスチェック用エンドポイントは設定していました。
```go:app/main.go
func main() {
    // 省略
　　　mux.Handle("GET /healthz", http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		w.WriteHeader(http.StatusOK)
	}))

	http.ListenAndServe(":8080", accessLogMiddleware(mux))
}
```

これで、ターゲットグループの設定ができました。

そしてさらに、ターゲットグループにはターゲットの実体を「登録」しておく必要があります。
https://registry.terraform.io/providers/hashicorp/aws/latest/docs/resources/autoscaling_attachment
```tf:terraform/main.tf
# Attach ALB target group to ASG of EKS Node Group
resource "aws_autoscaling_attachment" "eks_node_group_attachment" {
  autoscaling_group_name = module.eks_node_group.node_group_autoscaling_group_names[0]
  lb_target_group_arn    = aws_lb_target_group.alb_tg_to_ng.arn
}
```

上の記述では、Auto Scaling Group（＝Node Group）をターゲットグループに紐づけています。これにより、Auto Scaling Groupに属するEC2インスタンス（Node）がターゲットとして登録されます。

### Security Group
ALBの属するセキュリティグループを作成し、Inbound/Outboundルールを設定します。

- Inbound Rule:
    - 80ポートのhttp通信を受け入れる
- Outbound Rule:
    - どこにでもリクエストしてOK

::::message
最小限にするなら、Outboundの方は、ポート`30080`番に絞るのが適切かもしれません
::::

```tf:terraform/main.tf
# ALB
module "alb" {
  # ...
  security_groups = [aws_security_group.alb_sg.id]
  # ...
}

# Security Group for ALB
resource "aws_security_group" "alb_sg" {
  name        = "alb-sg"
  description = "Security group for ALB"
  vpc_id      = module.vpc.vpc_id

  ingress {
    description = "Allow HTTP traffic"
    from_port   = 80
    to_port     = 80
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }

  egress {
    description = "Allow all outbound traffic"
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }

  tags = {
    Name        = "eks-sandbox-alb-sg"
    Terraform   = "true"
    Environment = "dev"
  }
}
```

おさらいですが、Node Groupの方のSecurity Groupでは、ALBのSecurity Groupを参照してInbound Ruleを設定していました。
これにより、ALB➡︎Node Groupの通信経路が許可されるようになっています。
```tf
# node group
module "eks_node_group" {
  # ...
  security_group_ingress_rules = {
    alb_nodeport = {
      description                  = "Allow ALB to communicate with Node Group"
      from_port                    = 30000
      to_port                      = 32767
      protocol                     = "tcp"
      referenced_security_group_id = aws_security_group.alb_sg.id
    }
  }
  # ...
}
```

## 5. ECR
ここまででEKSで動くための環境があらかたできています。

ECRは、コンテナイメージを保存/管理するためのレジストリです。

EKSのWorker Node内で動くPodの中で動くコンテナは、kubeletによってECRからPullしたコンテナイメージを参照して実行されます。

https://registry.terraform.io/providers/hashicorp/aws/latest/docs/resources/ecr_repository
```tf:terraform/main.tf
# ecr repository
resource "aws_ecr_repository" "ecr_repository" {

    scan_on_push = true # pushされたコンテナイメージを自動で脆弱性チェック
  }

  }

```

## 6. VPC Endpoint
VPC Endpointは、構築したVPC内➡︎AWSマネージドサービスへプライベート接続するためのものです。

https://docs.aws.amazon.com/ja_jp/vpc/latest/privatelink/create-interface-endpoint.html
https://docs.aws.amazon.com/ja_jp/vpc/latest/privatelink/what-is-privatelink.html

今回でいえば、ECRがそれに当たります。

もちろん、NAT & Internet Gatewayを用意しているので、インターネット経由でアクセスすることはできます。が、VPC Endpointを使うことで通信がAWS内部で完結するのでその点でセキュアだと言えます。

VPC Endpointは２種類あり、
- **インターフェース型**
    - [AWS PrivateLink](https://aws.amazon.com/jp/privatelink/)という、VPCの中から、インターネットを使わずにAWSサービスや他のVPCサービスへプライベートIP経由で直接つなぐことができるネットワーク基盤を利用したインターフェース。
    - 実体としては、プライベート接続するためのENIを作成するイメージ
- **ゲートウェイ型**
    - VPC内のルートテーブルに、AWSサービス宛のトラフィックをAWS内部ネットワークに流す設定をする
    - インターネット（NAT/IGW）を経由せず、ルート制御によってAWS内部経路へ振り分けるイメージ
    - S3 / DynamoDBのみ
      
https://dev.classmethod.jp/articles/vpc-endpoint-gateway-type/
https://dev.classmethod.jp/articles/aws-vpcendpoint-privatelink-beginner/
https://qiita.com/miyuki_samitani/items/9d9f7a0c417cb75a6c85

とにかく、VPC Endpointを立てれば、AWSサービスにインターネットを経由せずにアクセス可能だと理解すればいいと思います。

::::message
EKS Controle Planeも一応、AWSマネージドなリソースでしたが、こちらはVCP Endpoint経由でのアクセスは不可能です。

Controle Planeのkube-api-serverは、単なるk8s クラスター管理のためのAPIサーバーであり、AWSとして公開されているサービスではありません。ただマネージドであるというだけです。
そのため、PrivateLinkの対象として提供されておらず、VPC Endpoitは利用できないのではないかと筆者は理解しています。
::::


以下で記述していきます。
https://registry.terraform.io/providers/hashicorp/aws/latest/docs/resources/vpc_endpoint.html

```tf:terraform/main.tf
# vpc endpoint for accessing ECR from private subnet
resource "aws_vpc_endpoint" "vpc_endpoint_for_ecr_api" {
  vpc_id             = module.vpc.vpc_id
  service_name       = "com.amazonaws.ap-northeast-1.ecr.api"
  vpc_endpoint_type  = "Interface"
  subnet_ids         = module.vpc.private_subnets
  security_group_ids = [aws_security_group.vpc_endpoint_sg.id] # 後に設定

  private_dns_enabled = true

  tags = {
    Name        = "eks-sandbox-ecr-api-endpoint"
    Terraform   = "true"
    Environment = "dev"
  }
}

resource "aws_vpc_endpoint" "vpc_endpoint_for_ecr_dkr" {
  vpc_id             = module.vpc.vpc_id
  service_name       = "com.amazonaws.ap-northeast-1.ecr.dkr"
  vpc_endpoint_type  = "Interface"
  subnet_ids         = module.vpc.private_subnets
  security_group_ids = [aws_security_group.vpc_endpoint_sg.id] # 後に設定

  private_dns_enabled = true

  tags = {
    Name        = "eks-sandbox-ecr-dkr-endpoint"
    Terraform   = "true"
    Environment = "dev"
  }
}

# vpc endpoint for accessing S3 from private subnet
resource "aws_vpc_endpoint" "vpc_endpoint_for_s3" {
  vpc_id            = module.vpc.vpc_id
  service_name      = "com.amazonaws.ap-northeast-1.s3"
  vpc_endpoint_type = "Gateway"
  route_table_ids   = module.vpc.private_route_table_ids

  tags = {
    Name        = "eks-sandbox-s3-endpoint"
    Terraform   = "true"
    Environment = "dev"
  }
}
```
ECR操作のために3つのVPC Endpointを設定しています。
- [com.amazonaws.region.ecr.dkr](https://docs.aws.amazon.com/ja_jp/AmazonECR/latest/userguide/vpc-endpoints.html#:~:text=%E3%81%A7%E3%81%AF%E3%81%82%E3%82%8A%E3%81%BE%E3%81%9B%E3%82%93%E3%80%82-,com.amazonaws.region.ecr.dkr,-%E3%81%93%E3%81%AE%E3%82%A8%E3%83%B3%E3%83%89%E3%83%9D%E3%82%A4%E3%83%B3%E3%83%88)
    - `docker pull`でイメージ取得
- [com.amazonaws.region.ecr.api](https://docs.aws.amazon.com/ja_jp/AmazonECR/latest/userguide/vpc-endpoints.html#:~:text=com.amazonaws.region.ecr.api)
    - ECR API呼び出し（認証トークン、イメージのメタデータ取得等）
- [com.amazonaws.region.s3](https://docs.aws.amazon.com/ja_jp/AmazonECR/latest/userguide/vpc-endpoints.html#:~:text=com.amazonaws.region.s3)
    - ECRはS3を利用してイメージレイヤーを保存するため、S3へのアクセスも必要


ECRへのPrivateLink接続をするためには、上の3つのVPC Endpointが必要だということが書かれています。

> Amazon EC2 インスタンスでホストされる Amazon ECS タスクの場合、Amazon ECR エンドポイントと Amazon S3 ゲートウェイエンドポイントの両方が必要です。

https://docs.aws.amazon.com/ja_jp/AmazonECR/latest/userguide/vpc-endpoints.html

### Security Group
VPC内ならどこからでもVPC Endpointへの通信を受け付けるようにしておきます。
```tf:terraform/main.tf
# Security Group for VPC Endpoints
resource "aws_security_group" "vpc_endpoint_sg" {
  name        = "vpc-endpoint-sg"
  description = "Security group for VPC endpoints"
  vpc_id      = module.vpc.vpc_id

  ingress {
    description = "Allow HTTPS from VPC"
    from_port   = 443
    to_port     = 443
    protocol    = "tcp"
    cidr_blocks = [module.vpc.vpc_cidr_block]
  }

  egress {
    description = "Allow all outbound"
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }

  tags = {
    Name        = "vpc-endpoint-sg"
    Terraform   = "true"
    Environment = "dev"
  }
}
```

また、HTTPS接続のみを許可する必要があるとドキュメントに記載があります。
> VPC エンドポイントにアタッチされたセキュリティグループでは、VPC のプライベートサブネットから、ポート 443 で着信接続を許可する必要があります。

https://docs.aws.amazon.com/ja_jp/AmazonECR/latest/userguide/vpc-endpoints.html

::::message
#### S3 VPC EndpointにはSecurity Groupをアタッチできない
記述を見てもらえるとわかりますが、3つのVPC Endpointのうち`vpc_endpoint_for_s3`のみ、Security Groupをアタッチしていません。
これは、S3のVPC Endpointがゲートウェイ型だからです。


対するインターフェース型だと、実体としてENIが作成されます。そして、Security GroupはENIに紐づくものです。

ゲートウェイ型は、ルートテーブルによって経路変更をしているだけなので、Security Groupを
紐づけることができないといった感じになります。


このハンズオンでは行っていませんが、ゲートウェイ型だと[IAM・バケットポリシーでアクセス制御](https://docs.aws.amazon.com/ja_jp/AmazonECR/latest/userguide/vpc-endpoints.html#ecr-setting-up-s3-gateway:~:text=%E3%81%A6%E3%81%8F%E3%81%A0%E3%81%95%E3%81%84%E3%80%82-,Amazon%20ECR%20%E3%81%AE%E6%9C%80%E5%B0%8F%20Amazon%20S3%20%E3%83%90%E3%82%B1%E3%83%83%E3%83%88%E3%82%A2%E3%82%AF%E3%82%BB%E3%82%B9%E8%A8%B1%E5%8F%AF,-Amazon%20S3%20%E3%82%B2%E3%83%BC%E3%83%88)を行う設計になっているようです
::::
