# はじめに
Kubernetes（以降、k8s）という、コンテナ化されたアプリケーションを自動で配置・実行・管理するためのオーケストレーションプラットフォームがあります。

k8sではアプリケーションの状態や構成を manifest（マニフェスト） と呼ばれる YAML ファイルで定義します。このハンズオンでは、そのmanifestを効率的に整理・管理するためにhelmfileというツールを用います。

この章では、k8sの仕組みにも触れていきます。

# k8sコンポーネントをイメージで捉える
上で示した図では、かなり雑にk8sを概念的に表していましたが、k8sのアーキテクチャをここで抑えておきます。
ここを抑えておくことで、5章で扱うAWSリソースとの関係性もクリアに理解することができます。それゆえ、筆者的に大事な部分だと思うので、しっかり扱うことにします。

![](https://storage.googleapis.com/zenn-user-upload/4e575d7b1ff5-20251220.png)
*https://kubernetes.io/ja/docs/concepts/architecture/*

まず、kubernetes クラスターという大きな塊があります。これは、簡単に言えばk8sの世界そのものだと考えるといいと思います。

> Kubernetes (k8s) クラスタは、コンテナ化されたアプリケーションを実行するノードの集合体です。
> 
> 引用：https://www.redhat.com/ja/topics/containers/what-is-a-kubernetes-cluster

そして、クラスタを構成するのは、大きく２つの種類のノードに分かれます。
- **Worker Node**
    - Podが実際に動作する実行環境
- **Controle Plane(Master Node)**
    - クラスター全体の状態を管理する

クラスター内に存在するControl Planeは1つですが、Worker Nodeは複数個の配置が可能です。
それでは、それぞれのノードに含まれるコンポーネントをそれぞれ見ていきます。

が、その前に、重要なリソースについて理解することから始めましょう。
"Pod", "Service"の大きく分けて二つを取り上げます。
## Pod
Podとは、コンテナの集合体です。

１つのPodには、協調して稼働させる必要があるコンテナを１ユニットとして稼働させることができます。
そのように、メインとなるアプリケーションコンテナに付随して起動させるコンテナを、サイドカーコンテナといいます。

今回は、以下のようにnginxをサイドカーコンテナとして用意し、リバースプロキシとして一緒に稼働させます。
![](https://storage.googleapis.com/zenn-user-upload/0c5963c3fab3-20251220.png)

他にも、ログ収集用にfluentd等をサイドカーコンテナとしておくことも多いようです。

また、Pod内にはvolume, IPアドレスも含まれます。

![](https://storage.googleapis.com/zenn-user-upload/6c3bb77f9e91-20251224.png)
*https://kubernetes.io/ja/docs/tutorials/kubernetes-basics/explore/explore-intro/*

### ReplicaSet
ReplicaSetは、指定されたレプリカ数でPodを稼働し続けることを保証します。
Podを複製し、それを束ねて管理するリソースと捉えることができます。

これにより、Podを冗長化させることができます。たとえば、3つのレプリカ数でPodが稼働していた場合、1つが落ちても他の2つは稼働しているため、サービスを継続して提供することができます。
また、Serviceリソース（後述）と組み合わせることで、リクエストが複数のPodへ分散されます。

![](https://storage.googleapis.com/zenn-user-upload/2d351633d5f1-20251220.png)

まとめると、Podが冗長化することによって、可用性+負荷分散の点でメリットが大きいんですね。

### Deployment
Deploymentは、Replicasetを管理する、最上位のデプロイ単位と言えます。
つまり、「Deployment→Replicaset→Pod→コンテナ」という関係性になります。

Pod単体で扱うことも、Replicasetを直接扱うこともほとんどなく、基本的にはDeploymentを利用します。

k8sは、新旧Podの入れ替え(=デプロイ)を、ダウンタイムを最小限に行えると述べましたが、これはDeploymentが内部でReplicaSetを管理し、ローリングアップデート戦略を用いるからです。

::::message
#### ローリングアップデート
アプリケーションの可用性に影響を与えないよう、一気に新旧Podを総入れ替えするのではなく、段階的なアップデートを行います。

![](https://storage.googleapis.com/zenn-user-upload/cbce095c689a-20251220.png)
*https://kubernetes.io/ja/docs/tutorials/kubernetes-basics/update/update-intro/*
::::

ReplicaSetは、あくまで同一Podの複製なので、新旧Podをローリングアップデートするには、ReplicaSetを管理するもう１つ上のリソースが必要であり、それがDeploymentになります。

![](https://storage.googleapis.com/zenn-user-upload/ca0f093d0a16-20251220.png)

## Service
Pod内のコンテナはループバック経由(`localhost`)での通信が可能です。
そして、Podはクラスタ内でユニークなIPアドレスを持っています。
つまり、Pod間は通信が可能ということになります。

そこで、あるPod-Aから、Pod-Bにアクセスしたいという状況を考えてみます。

![](https://storage.googleapis.com/zenn-user-upload/7d125b05c7c3-20251220.png)


Pod-BのIPアドレスを直接指定すれば良いです。

しかしながら、先述したように、Podは再作成される短命なリソースです。
再作成された場合、その新たなPodには新しいIPアドレスが付与されます。
![](https://storage.googleapis.com/zenn-user-upload/f25b0fc68f31-20251220.png)

つまり、Podが持つIPアドレスを見て通信していては、再作成されたときに追従できず通信が不可能になってしまいます。

この問題を解決するのがServiceリソースです。
Serviceが提供する機能性として以下２つを取り上げます。
- Pod群に紐づく安定したDNS名を持つ、通信の抽象レイヤー
- クラスタ内外への通信の公開

### Pod群に紐づく安定したDNS名を持つ、通信の抽象レイヤー
直接Pod-Bに通信するのではなく、関連づけられたServiceに対して通信するように構成することができます。

![](https://storage.googleapis.com/zenn-user-upload/f67d237b4be8-20251221.png)

Serviceは、`<service-name>.<namespace>.svc.cluster.local`という規則でDNS名を持っています。
::::message
このDNSによる名前解決を可能にしているのは、CoreDNSというadd-onのリソースになります。
ServiceのDNS名に対してClusterIPもしくは PodのIPアドレスを応答します。

EKSでも、デフォルトでこのCoreDNSのPodが起動するようになっています。
https://docs.aws.amazon.com/ja_jp/eks/latest/userguide/managing-coredns.html
::::

もう少し深掘ります。
Serviceには、Endpoints/EndpointSliceというリソースが紐づいています。
ここではEndpointSliceリソースを扱います。
::::message
Endpointsが元来存在したものです。EndpointSliceは、Endpointsの持っていたパフォーマンス的な課題を解決するために実装された新たなリソースになります。
::::

EndpointSliceリソースには、Serviceとそれに紐づく全てのPodへの`IPアドレス:ポート`の情報が格納されています。ちなみに、このルーティング情報を格納するのは、EndpointSlice Controller（Control Plane）になりますがこれについては後述します。

リソースの関係性としては、以下のように表せます。
![](https://storage.googleapis.com/zenn-user-upload/e2f5fa350c7f-20251221.png)

さらには、EndpointSlice自体がルーティングをしているわけではなく、このEndpointSliceの情報を見て、kube-proxyというコンポーネントがネットワーク設定をiptablesコマンドで設定しており、実際のネットワーク処理はLinuxカーネルに任せています。これについても後述します。

### クラスタ内外への通信の公開
Serviceにはタイプがあり、それによってクラスタ内へも外へも通信を公開することができます。

#### クラスタ内への公開：ClusterIP
デフォルトのタイプになります。実はこれはすでに上で扱っていたことで、Serviceという通信の抽象レイヤーを介してPodにアクセス可能になるというものです。

Serviceには、ClusterIPというクラスター内における仮想のIPアドレスが付与されます。そして、CoreDNSによって`<service-name>.<namespace>.svc.cluster.local`といったDNS名からClusterIPに名前解決されるため、別PodからはDNS名でアクセスできるのでした。

なお、このClusterIPは外部からアクセスしても有効ではありません。

#### クラスタ外への公開：NodePort, LoadBalancer
NodePortタイプでは、各Worker Nodeに共通のポート（NodePort）を開放し、そのポートへの通信をServiceに転送することで、クラスタ内のPodへの通信を外部に公開します。

PodやServiceなどのリソースは、k8sが管理しているネットワーク空間におけるものです。そのネットワークの窓口的存在としてServiceが立ち、それがWorker Nodeのportと紐づくことで、k8sのネットワークと外部ネットワークが橋渡しされるようになります。

![](https://storage.googleapis.com/zenn-user-upload/59878b1a42c9-20251224.png)

::::message
Worker Nodeもクラスタの内部なのに、Worker NodeのPortは外部と通信が可能なのか.....? と疑問に思うかもしれません。
これは、Worker Nodeが論理的にはk8sクラスタの一部でありつつ、物理的・ネットワーク的にはクラウドやホストOS上に存在する1台のマシン（VM/コンテナ）だからです。

EKSの場合、EC2のサーバーインスタンスがWorker Nodeとして利用されます。
::::


LoadBalancerタイプだと、クラウドプロバイダのAPIを叩くことでService用にロードバランサーがプロビジョニングされるようになります。K8sリソースによって、AWSリソースであるNLB(Network Load Balancer)の作成が指示されるといった感じです。

実際は、同様にNodePortで通信が公開されており、それをうまくLoadBalancerと紐づけてくれるServiceタイプであると言えそうです。
![](https://storage.googleapis.com/zenn-user-upload/aa8d316c3abd-20251221.png)
*https://youtu.be/T4Z7visMM4E?si=bYFnY6xRJolmE6E0 より抜粋*

Serviceが、k8sネットワーク内の通信を抽象化してくれることを述べましたが、このtypeは、その一点のみをサポートしてくれます。

これは、外部サービスのエンドポイントをExternalName Serviceで抽象化して、具体エンドポイントを隠蔽するなどの用途で使われるようです。

## Worker Node
それでは、Podが動く実行環境であるWorker Nodeの中に存在するコンポーネントについてみていきます。
Podはコンテナ群を束ねているものでした。
つまり、実質的にはコンテナの実行を任されているNodeになります。

Worker Nodeは、Pod（ひいてはコンテナ）を実行するための「器」のようなものとイメージすると良いかと思います。
Worker Nodeの持つCPUやメモリなどのリソース状況（「空き容量」）等をみて、Control Plane（後述）によってPodの配置がスケジューリングされます。


![](https://storage.googleapis.com/zenn-user-upload/61996e5d8530-20251224.png)


また、ラベルセレクター等で指定しない限りは、namespaceの境界なくPodがNodeにスケジュールされるようになっています。

https://kubernetes.io/ja/docs/concepts/scheduling-eviction/assign-pod-node/

kubernetesにはnamespaceの概念があり、１クラスター内でリソース分割を行うことができます。
`kubectl`コマンドでPod等のリソースを操作するにしても、指定したnamespace単位で行うことになります。

https://kubernetes.io/ja/docs/concepts/overview/working-with-objects/namespaces/

なので、namespace によって概念的・論理的には分離されているPodリソースであっても、物理的にはWorker Node上で混在して実行されるという感じですね。

Worker Nodeには、以下のコンポーネントが含まれます。
- コンテナランタイム
- kubelet
- kube-proxy

順番に見ていきましょう。


### コンテナランタイム
コンテナを実行するためには、コンテナランタイムが必要です。
ここでは、コンテナランタイムという表現は高レベルのコンテナランタイム（前章を参照）を指します。

前章では、OCIという規格によって、コンテナイメージ、レジストリ、ランタイムの仕様が標準化されていることを述べました。

ここでは、さらにk8sがコンテナランタイムを扱うためのインターフェースが規格化されている点に注目します。

#### CRI
先は、「k8sがコンテナランタイムを扱う」と雑に表現しました。
ちゃんと表現し直すと、k8sの中のkubeletというコンポーネントがコンテナランタイムを操作します。

そこで、kubeletが多様なコンテナランタイムを扱うためのインターフェースが、Container Runtime Interface(CRI)です。


https://kubernetes.io/ja/docs/concepts/architecture/cri/

https://kubernetes.io/blog/2016/12/container-runtime-interface-cri-in-kubernetes/

この「インターフェース」の実態は、kubeletとやりとりするためのgRPCプロトコル定義になります。
以下で定義されているエンドポイントを用意されていれば、コンテナランタイムが何であれ理論上はkubeletと通信することが可能になります。
https://github.com/kubernetes/cri-api/blob/c75ef5b/pkg/apis/runtime/v1/api.proto

前章ではOCIという似たような響きの言葉が出てきました。整理してCRIを付け足すと以下のようになります。
![](https://storage.googleapis.com/zenn-user-upload/b5c0574b3be3-20251227.png)

CRIに対応しているコンテナランタイムは以下のようなものがあります。
- containered
- CRI-O

::::message
EKSは、コンテナランタイムをDocker Engineからcontainerdに移行したようです。
- [All you need to know about moving to containerd on Amazon EKS
](https://aws.amazon.com/jp/blogs/containers/all-you-need-to-know-about-moving-to-containerd-on-amazon-eks/?utm_source=chatgpt.com)

Docker Engine単体ではCRIに対応しておらず、かつてはk8s側でdockershimというアダプターを利用するという実装が組み込まれていました。

![](https://storage.googleapis.com/zenn-user-upload/309cf25e1627-20251227.png)

### kubelet
kubeletは、各Worker Node上で動く主要なエージェントであり、クラスタにおける司令塔であるContorol Planeとの通信を行います。

通信の流れは基本的に、kubelet→Controle Planeの一方通行です。

- Worker NodeをControl Planeに登録
- Control PlaneからPullしたPodSpecを元にPodの状態を管理
- Pod/Worker Nodeの状態をControl PlaneにPush

#### Worker NodeをControl Planeに登録
Control Planeの内部にあるコンポーネントでkube-api-server(以下、api-server)というものがあります。
::::message
kube-api-server = 「Control Planeと外部(Worker Nodeも含む)がやり取りするための窓口」と捉えておいてください。
詳しくは後述します。
::::

kubeletは、以下の流れで動作しているWorker Nodeをapi-serverに登録します。
ざっくりコードも追ってみましょう。

```go:kubernetes/pkg/kubelet/kubelet_node_status.go
// registerWithAPIServer registers the node with the cluster master. It is safe
func (kl *Kubelet) registerWithAPIServer() {
　// 省略

 //kubelet自身が動くマシン自体をWorker Nodeオブジェクトとして返す
 node, err := kl.initialNode(context.TODO())
 // Worker Nodeを実際にapi-serverに登録
 registered := kl.tryRegisterWithAPIServer(node)
}
```
::::details initialNode()
kubeletが動作するマシン上の情報を詰めています。
```go:kubernetes/pkg/kubelet/kubelet_node_status.go
func (kl *Kubelet) initialNode(ctx context.Context) (*v1.Node, error) {
	node := &v1.Node{

				kubeletapis.LabelArch: goruntime.GOARCH,
			},
		},
	}
```

#### Control PlaneからPullしたPodSpecを元にPodの状態を管理
kubeletは、api-serverにPodオブジェクトを問い合わせ、あるべき状態を把握します。
api-serverからPushされるわけではありません。

PodSpecとは、その名の表す通りであり、Podのあるべき状態であり、Podオブジェクトに含まれます。
https://github.com/kubernetes/community/blob/master/contributors/devel/sig-architecture/api-conventions.md#spec-and-status

以下は、kubeletの中で呼ばれる、api-serverからPodオブジェクトをPullするための関数です。
```go:/kubernetes/pkg/kubelet/config/apiserver.go
// NewSourceApiserver creates a config source that watches and pulls from the apiserver.
func NewSourceApiserver(....){
    // このノードに割り当てられたPodを監視するためのListWatch作成
    // GET /api/v1/pods?fieldSelector=spec.nodeName=xxx
　	lw := cache.NewListWatchFromClient(c.CoreV1().RESTClient(), "pods", metav1.NamespaceAll, fields.OneTermEqualSelector("spec.nodeName", string(nodeName)))
    
    go func() {
        logger.Info("Watching apiserver")
        // Reflectorを起動してWatch API を開始
        // LIST(初期データ) → WATCH(ストリーム接続でイベント継続受信)
        newSourceApiserverFromLW(lw, updates)
    }()
}
```

#### iptables/netfileter
iptablesは、Linux カーネルのパケット処理ルール（→netfileter）を設定するためのCLIです。

...となれば、理解すべきはnetfileterですね（次から次へと知らない知識が....😖）。

netfilterは、以下の3つの概念で構成されます。
- table:
    - 目的別にパケット処理を分類する論理的な単位
    - 「このパケットに何をしたいか」という処理の目的を表す
    - 例：
        - `filter`(許可)
        - `nat`（アドレス/ポート変換）
        - `mangle`(パケット改変)
        - `raw`（conntrack制御）
- chain:
    - パケットが通過する処理ポイント（フック）
    - パケットのライフサイクル上の「どの処理段階で処理するか」を表す
    - 例：
        - `PREROUTING`(ルーティング判定前)
        - `INPUT`(ローカルプロセス宛てのパケット)
        - `FORWARD`(他ホストへ転送されるパケット)
        - `OUTPUT`(ローカルプロセスから送信されるパケット)
        - `POSTROUTING`(ルーティング判定後)
- rule:
    - 条件とアクションの組み合わせ
    - chainの中に順序付きで並ぶ
    - アクション例：
        - `DNAT`(宛先アドレス変換)
        - `SNAT`(送信元アドレス変換)
        - `ACCEPT`(パケットを通す)
        - `DROP`(パケットを落とす)
        - `JUMP`(chainを跨ぐ)

kube-proxyが操作するほとんどがnatテーブルになります。(次いでfilter, mangleテーブルになりそうです)
ここではnatテーブルについて取り上げます。

以下のように設定されているものとイメージしましょう。

**nat table**
| hook        | chain       | rule（役割）                       |
| ----------- | ----------- | ------------------------------ |
| PREROUTING  | PREROUTING  | 宛先IP/Port条件で **別chainへJUMP**   |
| PREROUTING  | DNAT-CHAIN  | **DNAT（宛先IP/Port書き換え）**        |
|  |   | 例：203.0.113.10:80 ⇨ 192.168.1.100:8080|
| OUTPUT      | OUTPUT      | 自プロセス発の通信を **別chainへJUMP**     |
| OUTPUT      | DNAT-CHAIN  | **DNAT（loopback含む）**           |
| POSTROUTING | POSTROUTING | 送信元IP条件で **SNAT / MASQUERADE** |
| | | 例：192.168.1.100:8080 ⇨ 203.0.113.10:80|

`203.0.113.10:80`宛のパケットが送られてきた場合は以下のように以下のように宛先/送信元のアドレスが変換されるなどします。
![](https://storage.googleapis.com/zenn-user-upload/c230e738e42a-20251230.png)

netfilterを通して、フック（パケットの処理段階）ごとに対応するchainのruleが動作するイメージです。
ちなみに、上の表だと`DNAT-CHAIN`は任意に設定したchain名になります。

また、ルーティング処理はカーネル内の別システムが担いますがここでは割愛します。Linuxカーネルがうまくやってくれるとだけ把握しておきましょう。
::::

| ----------- | ---------------- | --------------------------------------------------------------------------------------------------------------------------- |

#### 例：ReplicaSetController
ReplicaSetは、指定した数分のPodを稼働させ続けることを保証するリソースでした。
実際はこのコントローラーが動作することで、機能を満たしています。
```go:kubernetes/pkg/controller/replicaset/replica_set.go
// 超省略
func (rsc *ReplicaSetController) syncReplicaSet(ctx context.Context, key string) error {
    // 1. etcdから望ましい状態(ReplicaSet)を取得
    namespace, name, _ := cache.SplitMetaNamespaceKey(key)
    rs, err := rsc.rsLister.ReplicaSets(namespace).Get(name)
    if err != nil {
        return err  // 削除済みなら終了
    }

    // 2. 現在の状態(実際のPod)を取得
    selector, _ := metav1.LabelSelectorAsSelector(rs.Spec.Selector)
    allActivePods := controller.FilterActivePods(logger, allRSPods)
    activePods, _ := rsc.claimPods(ctx, rs, selector, allActivePods)

    // 3. 調整処理(manageReplicas)
    manageReplicasErr = rsc.manageReplicas(ctx, activePods, rs)
    
    // 4. ステータス更新
    newStatus := calculateStatus(rs, activePods, ...)
    updateReplicaSetStatus(logger, rsc.kubeClient, rs, newStatus)
    
    return manageReplicasErr
}
```

Pod（コンテナ）を実行するのはkubeletなので、コントローラーはetcdに保存しているオブジェクトを修正する形になります(api-server経由)。

### kube-scheduler
kube-schedulerは、Worker NodeへのPodの割り当てを行います。

https://kubernetes.io/ja/docs/concepts/scheduling-eviction/kube-scheduler/

Filterロジックで実行可能なWorker Nodeを絞り込みます。CPU/メモリ要求を満たすか、ラベルセレクタが一致するかなどを見てフィルタリングします。

ScoreロジックでフィルタされたWorker Nodeらを採点し、最高得点のWorker Nodeを選択します。

最終的に、選択したWorker Nodeを割り当ててスケジュール完了とします(api-server経由)。
```diff json
 {
 "metadata": {
     "name": "my-rs-pod-4",
     "namespace": "default",
     "ownerReferences": [{
     "kind": "ReplicaSet",
     "name": "my-rs",
     "uid": "abc123",
     "controller": true
     }]
 },
 "spec": {
     "containers": [{
     "name": "nginx",
     "image": "nginx:1.21"
     }],
-    "nodeName": ""  // まだ未割り当て
+    "nodeName": "node-2"
 },
 "status": {
-    "phase": "Pending" // まだ起動していない
+    "phase": "Pending",
+    "conditions": [
+      {
+        "type": "PodScheduled",
+        "status": "True",
+        "lastTransitionTime": "2025-12-31T10:00:00Z"
+      }
+    ]
 }
 }
```

これをkubeletが見て、Podが該当のWorker Nodeで起動するようになります。

### etcd
etcdは、クラスター内のリソース全ての状態を保存する分散型のキーバリューストアになります。

https://www.redhat.com/ja/topics/containers/what-is-etcd

etcdはそれでいてgRPCサーバーのようです。つまり、kube-api-server↔︎etcdの間はgRPC通信になります。
https://etcd.io/docs/v3.2/dev-guide/api_grpc_gateway/

etcdはwatch APIを提供しており、api-serverは起動時にetcdをwatchします。そして、api-serverはstreamingで変更イベントを受け取ります。

https://etcd.io/docs/v3.2/learning/api/#:~:text=%7D-,Watch%20API,-The%20Watch%20API

https://en.wikipedia.org/wiki/Kubernetes?utm_source=chatgpt.com#:~:text=The%20API%20server%20uses%20etcd%27s%20watch%20API%20to%20monitor%20the%20cluster

etcdをwatchするクライアントメソッドを定義している箇所もありますね。

https://github.com/kubernetes/kubernetes/blob/master/staging/src/k8s.io/apiserver/pkg/storage/etcd3/watcher.go

ここで、kubelet,api-server,etcdの関係図を簡単に整理してみました。
`kubectl`コマンドでPodを追加するような変更を適用させたとします。

![](https://storage.googleapis.com/zenn-user-upload/32c04abca56f-20260101.png)

流れは以下のようになります。実際はもう少し複雑かとは思いますが、イメージです。

0. 起動時に各コンポーネントがWatch接続
   - kubelet → api-server (HTTP)
   - api-server → etcd (gRPC)
1. kubectlコマンドでPod追加を実行し、api-serverが受信
   - `kubectl apply -f pod.yaml`
   - 内部的には`POST /api/v1/namespaces/default/pods`といったPOSTリクエスト
   - [docs](https://kubernetes.io/docs/reference/kubernetes-api/workload-resources/pod-v1/#create-create-a-pod)
2. api-serverがetcdの`PUT()`を叩いて新規Podオブジェクトを保存
   - `PUT()`はetcd gRPCサーバーに用意されたメソッド
   - [docs](https://etcd.io/docs/v3.2/learning/api/#put:~:text=the%20range%20request.-,Put,-Keys%20are%20saved)
3. etcdはapi-serverに`PUT`イベントを通知
   - PUTのイベントタイプは、ストアに新しい値が保存されたことを意味する
   - [docs](https://etcd.io/docs/v3.2/learning/api/#:~:text=Type%20%2D%20The%20kind%20of%20event.%20A%20PUT%20type%20indicates%20new%20data%20has%20been%20stored%20to%20the%20key.%20A%20DELETE%20indicates%20the%20key%20was%20deleted.)
```proto
// 超省略レスポスンスメッセージのイメージ
WatchResponse {
  events: [{
    type: PUT           // ← etcdイベント
    kv: { version: 1 }
  }]
}
```

4. api-serverは3を受けてkubeletに`ADDED`イベントを通知
5. kubeletがPodを実行

# manifestを用意(管理)する

マニフェスト（manifest）とは、k8sオブジェクトを宣言的に定義するYAML/JSONァイルであり、クラスターに対して「リソースの望ましい状態（desired state）」を記述します。

https://kubernetes.io/docs/concepts/overview/working-with-objects/#describing-a-kubernetes-object

作成したマニフェストは `kubectl apply` コマンドでクラスターに適用します。

```sh
kubectl apply -f manifest.yaml
```

また、`kubectl apply`は冪等性を持ち、同じマニフェストを何度適用してもクラスターの状態は常に定義された内容に収束します。

### 構成
以下に、今回用意するマニフェストの構成をリソースごとにまとめます。

- **Deployment**
    - マルチコンテナPod (Goアプリ + nginxサイドカー)
    - RollingUpdate戦略 (maxSurge/maxUnavailable設定可能)
    - 両コンテナにCPU/メモリのrequests/limits設定
    - ConfigMapでnginx設定を注入 (リバースプロキシ設定)
        - nginxがポート80で受けて、localhostのGoアプリにproxy_pass
- **Service**
    - NodePortタイプ
    - targetPort: 80 (nginxコンテナ)
        - nginxがGoアプリケーションコンテナにリクエストを流す。
- **HorizontalPodAutoscaler**
    - CPU/メモリの両方でPodのReplica数をスケーリング

::::message
#### HorizontalPodAutoscaler
HorizontalPodAutoscaler（HPA)は、PodのCPU・メモリなどのメトリクスをもとに、Replica数を自動的に増減させるk8sのコントローラです。  
HPAは定期的にメトリクスを取得し、定義された目標値（target）と現在値を比較してスケーリングを行います。

HPA が利用するメトリクスは、k8sのMetrics API（`metrics.k8s.io`など）を通じて提供されます。  
そのため、HPAを利用するにはmetrics-serverなどのMetrics APIコンポーネントがクラスター内で動作している必要があります。

- 参考(公式)：
    - [水平Pod自動スケーリング](https://kubernetes.io/ja/docs/tasks/run-application/horizontal-pod-autoscale/)
    - [Kubernetes Metrics (v1beta1)](https://kubernetes.io/docs/reference/external-api/metrics.v1beta1/?utm_source=chatgpt.com)
    - [リソースメトリクスパイプライン](https://kubernetes.io/ja/docs/tasks/debug/debug-cluster/resource-metrics-pipeline/)
::::

今回は、hpaを有効に利用するためのメトリクスサーバーとして、metrics-serverを利用します。metrics-serverのpodも追加で起動するということになります。

https://github.com/kubernetes-sigs/metrics-server

## Helm Chartを定義する
今回は、k8sを動かす環境が二つあります。
- 開発環境（4章のKindクラスター)
- 本番環境（6章のEKSクラスター）

双方の環境では、上述した「構成」は変わりないですがパラメータは変えたいところです。
例えば、
- 開発環境ではPodがあまりスケールする必要はないが、本番環境では余裕を持ってスケールするようにしたい
- cpu/memoryのリソースを変えたい
- Goアプリケーションコンテナのイメージ名に含まれるリポジトリ名が環境によって異なる
    - 開発環境ではローカルマシン上
    - 本番環境ではECR

などなど。

環境ごとにマニフェストを複製して管理することもできますが、それでは DRY の原則に反し、メンテナンスもしづらくなります。

そこで、これらの課題を解決する手段として**Helm Chart**を利用します。

### Helm Chartとは何か
Helm Chartとはマニフェストをテンプレート化し、再利用可能な形で管理するための仕組みです。

https://helm.sh/ja/

1 つの Chart は、以下のようなファイル構成を持ちます。
```
my-chart/
├── Chart.yaml          # Chartのメタデータ（名前・バージョン・依存関係など）
├── values.yaml         # デフォルト値
├── templates/          # Kubernetesマニフェストのテンプレート
│   ├── deployment.yaml # Deploymentのテンプレート（Pod・image・resources 等）
│   ├── service.yaml    # Serviceのテンプレート（Podへの通信定義）
│   └── ...
└── .helmignore         # Chartに含めないファイル定義（.gitignore相当）
```

Helm は、このChart（テンプレート）とvalues.yaml（パラメータ）を組み合わせることで、最終的にk8sに適用される完全なマニフェスト（YAML）を生成します。

なお、記法は`go/template`になります。

https://pkg.go.dev/text/template

### Helm Chartを記述する
先述した「構成」を満たすHTTPサーバーのChartを作成していきます。

ルートディレクトリから`/k8s`を切って、以下のようにファイルを用意します。
```
k8s/charts/http-server
├── Chart.yaml
├── templates
│   ├── deployment.yaml
│   ├── hpa.yaml
│   └── service.yaml
└── values.yaml
```

このChartのメタデータ的情報を記述します。
::::details k8s/charts/http-server/Chart.yaml

```yaml:k8s/charts/http-server/Chart.yaml
name: http-server
description: A Helm chart for HTTP server with nginx reverse proxy
type: application
version: 0.1.0
appVersion: "0.1.0"

  - http-server
  - nginx

  - name: kakkky
```

リソースごとにファイルを分ける必要はありませんが、整理のため、リソースは分けて記述します。

以下はDeploymentリソースのテンプレートです。
`{{...}}`となっているところ以外は単なるk8sマニフェストの構造になっています。

::::details k8s/charts/http-server/templates/deployment.yaml
```yaml:k8s/charts/http-server/templates/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ .Release.Name }}-{{ .Chart.Name }}
  labels:
    app: {{ .Release.Name }}-{{ .Chart.Name }}
spec:
  replicas: {{ .Values.deployment.replicaCount }}
  strategy:
    type: {{ .Values.deployment.strategy.type }}
    {{- if eq .Values.deployment.strategy.type "RollingUpdate" }}
    rollingUpdate:
      maxSurge: {{ .Values.deployment.strategy.rollingUpdate.maxSurge }}
      maxUnavailable: {{ .Values.deployment.strategy.rollingUpdate.maxUnavailable }}
    {{- end }}
  selector:
    matchLabels:
      app: {{ .Release.Name }}-{{ .Chart.Name }}
  template:
    metadata:
      labels:
        app: {{ .Release.Name }}-{{ .Chart.Name }}
    spec:
      containers:
        - name: {{ .Chart.Name }}
          image: "{{ .Values.deployment.image.repository }}:{{ .Values.deployment.image.tag }}"
          ports:
            - containerPort: {{ .Values.deployment.containerPort }}
          resources:
            requests:
              cpu: {{ .Values.deployment.resources.requests.cpu }}
              memory: {{ .Values.deployment.resources.requests.memory }}
            limits:            
              cpu: {{ .Values.deployment.resources.limits.cpu }}
              memory: {{ .Values.deployment.resources.limits.memory }}
        - name: nginx
          image: nginx:1.25
          ports:
            - containerPort: 80
          volumeMounts:
            - name: nginx-conf
              mountPath: /etc/nginx/nginx.conf
              subPath: nginx.conf
          resources:
            requests:
              cpu: {{ .Values.deployment.nginx.resources.requests.cpu }}
              memory: {{ .Values.deployment.nginx.resources.requests.memory }}
            limits:
              cpu: {{ .Values.deployment.nginx.resources.limits.cpu }}
              memory: {{ .Values.deployment.nginx.resources.limits.memory }}
      volumes:
        - name: nginx-conf
          configMap:
            name: {{ .Release.Name }}-nginx-conf
            items:
              - key: nginx.conf
                path: nginx.conf

---
apiVersion: v1
kind: ConfigMap
metadata:
  name: {{ .Release.Name }}-nginx-conf
data:
  nginx.conf: |
    events {}
    http {
      server {
        listen 80;
        location / {
          proxy_pass http://localhost:{{ .Values.deployment.containerPort }};
          proxy_set_header Host $host;
          proxy_set_header X-Real-IP $remote_addr;
        }
      }
    }
```

`deployment.yaml`に含まれるConfigMapは、設定ファイルや環境変数などの非機密データを保存するリソースになります。Podから分離して設定を管理 (コンテナイメージに設定を埋め込まない)できます。

https://kubernetes.io/ja/docs/concepts/configuration/configmap/

`nginx.conf`というキーで定義しています。
```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: {{ .Release.Name }}-nginx-conf
data:
  nginx.conf: |
  ...
```

volume定義では、上のConfigMap(`{{ .Release.Name }}-nginx-conf`)の`nginx.conf`キーの値を`nginx.conf`というファイル名で置いています。
```yaml
volumes:
- name: nginx-conf
  configMap:
    name: {{ .Release.Name }}-nginx-conf # ConfigMap参照
    items:
      - key: nginx.conf # ConfigMapのkey
        path: nginx.conf # マウント時のファイル名
```

nginxコンテナの中で以下のようにvolumeをマウントする形で利用しています。
```yaml
containers:
  - name: nginx
    volumeMounts:
      - name: nginx-conf           # Volume名
        mountPath: /etc/nginx/nginx.conf  # コンテナ内のパス
        subPath: nginx.conf        # ファイル単位でマウント
```

```yaml: k8s/charts/http-server/templates/service.yaml
  selector:
    app: {{ .Release.Name }}-{{ .Chart.Name }}
  ports:
    - name: http
      port: 80
      targetPort: 80 # transfer to nginx container port
      {{- if eq .Values.service.type "NodePort" }}
      nodePort: {{ .Values.service.nodePort }}
      {{- end }}
```

## Helmfileを記述する
ここまでで、Helm Chart を使うことで 「構成は共通だが、環境ごとにパラメータを変えたい」という課題が解決されることがわかりました。

一方で、Helmだけで複数環境を運用しようとすると、以下のような不便さがあります。

- 環境ごとの状態を宣言的に定義できない
- 環境ごとのデプロイがコマンドベースなので再現性が低い

::::details helmコマンドでデプロイした場合の例
開発環境
```bash
helm upgrade --install http-server-dev ./k8s/charts/http-server \
  --namespace dev \
  --create-namespace \
  -f values.yaml \
  -f values-dev.yaml
```
本番環境
```bash
helm upgrade --install http-server-prod ./k8s/charts/http-server \
  --namespace prod \
  --create-namespace \
  -f values.yaml \
  -f values-prod.yaml
```
::::

そこで、Helmfileというツールを使い、この点を解決します。

https://cloudandbuild.jp/blog/article-20240916#%E3%81%AA%E3%81%9Chelmfile%E3%82%92%E4%BD%BF%E3%81%86%E3%81%AE%E3%81%8B

### Helmfileとは何か
Helmfileの特徴は以下のようなものがあります。

- 複数の Helm Chart をまとめて宣言的に管理できる
    - どのChartを、どのversionで、どのvaluesで、どのnamespaceにデプロイするかを1つのYAMLファイルに記述できる。
- 環境ごとの差分（dev / prod など）をコードとして明確に表現できる
    - values ファイルの切り替えや環境別設定をコマンドではなく設定ファイルで管理できる。
- `helmfile apply`だけで環境全体を再現でき、再現性と運用性が高い
    - 手順書に頼らず、CI/CDやGitOpsと相性の良い運用が可能。

### `helmfile.yaml`を記述する
以下のように`helmfile`を用意します。
なお、`go/template`を用いた条件分岐を記述したかったため、ここでは拡張子に`gotmpl`を指定します。
::::details k8s/helmfile.yaml.gotmpl
```yaml: k8s/helmfile.yaml.gotmpl
environments:
  development:
    kubeContext: kind-sandbox

  production:
    kubeContext: eks-sandbox 


repositories:
  - name: metrics-server
    url: https://kubernetes-sigs.github.io/metrics-server/

---
releases:
  - name: app
    namespace: "app-{{ .Environment.Name }}"
    chart: ./charts/http-server
    values:
      - values/{{ .Environment.Name }}/values.yaml
    installed: true
    atomic: false # Rollback on failure is disabled for learning purposes
 
  - name: metrics-server
    namespace: kube-system
    chart: metrics-server/metrics-server
    version: 3.12.1
    {{- if eq .Environment.Name "development" }}
    values:
      - args:
          - --kubelet-insecure-tls
    {{- end }}
```

#### enviroments
`enviroments`フィールドを使って、環境ごとに設定値を切り替えることができます。

以下では、`kubeContext`を切り替えるようにしています。
```yaml
environments:
  development:
    kubeContext: kind-sandbox

  production:
    kubeContext: eks-sandbox 
```

`kubeContext`は、k8sの`context`という概念に対応します。
https://helmfile.readthedocs.io/en/latest/builtin-objects/?utm_source=chatgpt.com#helmfile-template-built-in-objects:~:text=of%20the%20environment-,Environment.KubeContext%3A%20The%20kube%20context%20to%20be%20used%20by%20default%20for%20releases%20in%20the%20environment.,-Values%3A%20Values%20passed

contextとは、以下のような情報をひとまとめにした設定の単位です。
- 接続先のクラスタ
- 認証情報（ユーザー）
- デフォルトの namespace

`kubectl config use-context`で切り替えて`kubectl apply`することが多いです。
  
https://kubernetes.io/docs/concepts/configuration/organize-cluster-access-kubeconfig/?utm_source=chatgpt.com#context


#### releases
Helmのリリース単位（`helm install/upgrade`に相当）を定義します。

利用するChartと、適用する`values.yaml`を指定できます。
以下のように、環境ごとに利用する`values.yaml`のパスを変えるようにすることで、切り替えられるようにしています。
```yaml
releases:
  - name: app
    namespace: "app-{{ .Environment.Name }}"
    chart: ./charts/http-server
    values:
      - values/{{ .Environment.Name }}/values.yaml
    installed: true
    atomic: false # Rollback on failure is disabled for learning purposes
```

`envoriments`と`releases`の設定を踏まえて整理すると、
```bash
helmfile apply -e development
```
とコマンドを実行した場合、
- `kind-sandbox`のコンテキスト（= Kindクラスターに対して）で、
- `./charts/http-server`のChartを用いて、
- ` values/development/values.yaml`をvaluesとして展開して、

デプロイできるということになります。

#### metrics-server

```yaml:k8s/values/production/values.yaml
deployment:
  name: app
  replicaCount: 1
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 100%
      maxUnavailable: 25%
  image:
    repository: 846869429016.dkr.ecr.ap-northeast-1.amazonaws.com/eks-sandbox-ecr-repository
    tag: "20251206224539"
  containerPort: 8080
  resources:
    requests:
      cpu: "100m"
      memory: "128Mi"
    limits:
      cpu: "500m"
      memory: "512Mi"
  nginx:
    resources:
      requests:
        cpu: "10m"
        memory: "32Mi"
      limits:
        cpu: "100m"
        memory: "128Mi"
hpa:
  enabled: true
  minReplicas: 1
  maxReplicas: 3
  targetCpuUtilizationPercentage: 60
  targetMemoryUtilizationPercentage: 70
service:
  type: NodePort
  nodePort: 30080

```
::::


パッとみ、ポート番号とかがややこしそうなので以下にイメージ図を載せておきます。以下は本番でも開発環境でも同じです。

Worker Nodeの`:30080`番ポートへの通信を、Pod IPの`:80`ポート(nginxコンテナ)へ転送します。そして、そのnginxコンテナが`localhost:8080`へプロキシします。
