# はじめに
この章ではDockerfileを作成し、イメージをビルドしてアプリケーションをローカルマシンで起動させることをゴールとします。

docker imageは、アプリケーションとその依存関係をひとまとめにした“実行可能なパッケージ”であり、これを元にコンテナが作成されます。そしてこれは配布可能なものになっています。

このハンズオンにおける「デプロイ」とは、ビルドした docker imageを実行環境（ローカル／AWS）に参照させ、アプリケーションとして動かすことだといえます。

# コンテナイメージについて
そもそも、このハンズオンのゴールはEKS環境でアプリケーションが動くようにすることです。そこで、まずはじめにコンテナイメージを作ることから始めます。

そこで、コンテナイメージとは何か、そしてどう使われるのかを理解し、その必要性について知るところから始めます。
## コンテナイメージとは何か
コンテナイメージとは、ホストOS上で「コンテナ」を作成するための諸々がまとまったパッケージです。
::::message
まずは「仮想コンテナ」とは何かについて知る必要がありますが、なんとなくでいいので、以下のようにざっくり把握しておきましょう。
- コンテナとは、アプリケーションを実行するための軽量な仮想環境
- ホストOSのカーネルを共有しつつ、プロセス・ファイル・ネットワークを分離して動作する

![](https://storage.googleapis.com/zenn-user-upload/0cda2dd5f8e7-20251213.png)
*docker公式より引用（https://www.docker.com/ja-jp/resources/what-container/）*
::::

コンテナイメージを元に、「コンテナ」を実行する感じです。

### コンテナレジストリ
そして、コンテナイメージとは配布可能なものとも述べました。イメージは、コンテナレジストリという、「作成したコンテナイメージを管理する場所」を介することで配布または使用することが可能になっています。

代表的なコンテナレジストリ:
- [Docker Hub](https://hub.docker.com/)
- [Amazon ECR（Elastic Container Registry）](https://aws.amazon.com/jp/ecr/)
- [Google Artifact Registry](https://docs.cloud.google.com/artifact-registry/docs/overview?hl=ja)

コンテナイメージは、依存関係を含む複数のレイヤーによって構成されています。これらのレイヤーは、コンテナレジストリにイメージとして保存されており、そのイメージを Pull することでまとめて取得・利用できます。
今回作成するイメージはgoアプリケーションになりますが、ベースとなるgoのイメージをDocker HubからPullしてビルドする形になります。

Amazon ECRも後章で登場します。

ここでは一旦、「このようなコンテナレジストリにコンテナイメージを保存して、そこから取ってきて利用する」と認識しておきましょう。

## コンテナイメージはどう使われるのか
コンテナイメージは、「コンテナ」の起動に利用されると述べました。

イメージを用いてコンテナを起動する役割を果たしているのが、コンテナランタイムです。

### コンテナランタイム
コンテナランタイムは、いくつか代表的なものがあります。
- [containerd](https://github.com/containerd/containerd)
- [CRI-O](https://github.com/cri-o/cri-o)
- [Docker Engine（内部でcontainerdを利用）](https://www.docker.com/ja-jp/products/container-runtime/)
    - Docker Engineに関しては、このランタイムの並びにおいていいのか自信なかったのですが、[kubernetesのドキュメント](https://kubernetes.io/ja/docs/setup/production-environment/container-runtimes/#cri-o)に並立でおかれていたのでよしとします。

ちなみに、EKSで現在採用されているコンテナランタイムはcontainerdです。
https://docs.aws.amazon.com/ja_jp/eks/latest/userguide/eks-optimized-ami.html

正直、筆者はこのように疑問を感じました
「コンテナ実行といえばDockerだから、Docker Engine以外はなんなんだ？」
「手元で`docker build`したイメージが、Docker Engineではなくcontainerdで動く....?」

....などなど。

ここは整理しておきたいところなので、しっかり扱います。

#### OCI(Open Container Initiative)
コンテナを扱う上で登場した3つの要素について、以下のような仕様があります。
- the Image Specification (image-spec)
- the Distribution Specification (distribution-spec)
- the Runtime Specification (runtime-spec)
  
https://opencontainers.org/

image-specについては、コンテナイメージの仕様についてです。
`docker build`だけでなく、イメージの作成方法は様々あります。しかし、結果的に作成されるイメージがimage-specに沿っていればよく、image-specの仕様を解釈できる高レベル(※後述)コンテナランタイム上なら何製のイメージでも扱えるわけです。

> At a high-level an OCI implementation would download an OCI Image then unpack that image into an OCI Runtime filesystem bundle.
> 
> 訳：高レベルの OCI 実装は、OCI イメージをダウンロードし、そのイメージを OCI Runtime のファイルシステムバンドルに展開する、という流れになります。

https://github.com/opencontainers/image-spec?tab=readme-ov-file


distribution-specについては、コンテナレジストリの仕様についてです。
レジストリには、イメージをPushして保存しPullして取得するワークフローが定められています。
https://github.com/opencontainers/distribution-spec/blob/main/spec.md


runtime-specについては、コンテナをどう起動するかの仕様についてです。
コンテナを実行・制御するための操作のinterfaceについてなどが書いてあります。
- `create`/`start`/`kill`/`delete`/`state`

https://github.com/opencontainers/runtime-spec/blob/main/runtime.md#operations

また、以下の形式をもつFilesystem Bundleを元にコンテナは実行される仕様です。
```
bundle
├── config.json   ← 起動方法・権限・namespace・cgroup 設定
└── rootfs/       ← コンテナのルートファイルシステム
```

https://github.com/opencontainers/runtime-spec/blob/main/bundle.md

実は、runtime-specに準拠して、bundleを元にコンテナを実行するのは、先ほど挙げたコンテナランタイムらではありません。
以下のような、**コンテナを実際に起動する低レベルのコンテナランタイム**が直接的にコンテナの操作を担います。
- [runc](https://github.com/opencontainers/runc)
- [crun](https://github.com/containers/crun)
- [youki](https://github.com/youki-dev/youki)

先ほど挙げた、
- containerd
- CRI-O
- Docker Engine

らは、「runtime-specに準拠した低レベルのランタイムを利用する側」の存在です。
image-specに沿ったコンテナイメージから、runtime-specに沿った形式のbundleを用意して、低レベルのコンテナランタイムに渡すという役割を果たします。
そのため、これらは**高レベルのコンテナランタイム**と表せます。
先ほども引用した文章を再度示します。

> At a high-level an OCI implementation would download an OCI Image then unpack that image into an OCI Runtime filesystem bundle.
> 
> 訳：高レベルの OCI 実装は、OCI イメージをダウンロードし、そのイメージを OCI Runtime のファイルシステムバンドルに展開する、という流れになります。

なお、高レベルのランタイムが低レベルのランタイムを隠蔽しているため、開発者が普段runcなどについて意識することはないと思います。

ここまでの話を図解すると以下のように整理できます。
![](https://storage.googleapis.com/zenn-user-upload/cf4803228fc7-20251213.png)

コンテナイメージをビルドツールも、それを保管するレジストリも、それを実行するランタイムも様々ありますが、OCIで標準化されているからこそ、組み合わせは自由ということですね。

::::message
kubernetesの文脈で、高レベルのコンテナランタイムにも標準のインターフェースが定められています。
それが、CRI(Container Runtime Interface)です。
https://kubernetes.io/ja/docs/concepts/architecture/cri/

::::details main.go
```go
package main

import (
	"html/template"
	"log"
	"net/http"
	"sync"
)

// Todo represents a single todo item
type Todo struct {
	Title string
}

// In-memory storage for todo items
type TodoListStore struct {
	mu       sync.Mutex
	todoList []Todo
}

var todoListStore = &TodoListStore{
	todoList: []Todo{},
}

// Template for rendering the todo list
var tmpl = template.Must(template.ParseFiles("./index.html"))

// getTodoHandler handles GET requests to retrieve the todo list
func getTodoHandler(w http.ResponseWriter, r *http.Request) {
	tmpl.Execute(w, todoListStore.todoList)
}

// postTodoHandler handles POST requests to add a new todo item
func postTodoHandler(w http.ResponseWriter, r *http.Request) {
	if err := r.ParseForm(); err != nil {
		http.Error(w, "Failed to parse form", http.StatusBadRequest)
		return
	}
	title := r.FormValue("title")
	if title != "" {
		todoListStore.mu.Lock()
		todoListStore.todoList = append(todoListStore.todoList, Todo{Title: title})
		todoListStore.mu.Unlock()
	}

	http.Redirect(w, r, "/todos", http.StatusSeeOther)
}

// responseRecorder is a custom ResponseWriter to capture the status code
type responseRecorder struct {
	http.ResponseWriter
	status int
}

func (r *responseRecorder) WriteHeader(code int) {
	r.status = code
	r.ResponseWriter.WriteHeader(code)
}

// accessLogMiddleware logs each incoming HTTP request
func accessLogMiddleware(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		rec := &responseRecorder{ResponseWriter: w, status: 200}
		next.ServeHTTP(rec, r)
		log.Printf("%s %s %s %d", r.RemoteAddr, r.Method, r.URL, rec.status)
	})
}

func main() {
	mux := http.NewServeMux()

	mux.Handle("GET /todos", http.HandlerFunc(getTodoHandler))
	mux.Handle("POST /todos", http.HandlerFunc(postTodoHandler))
	mux.Handle("GET /healthz", http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		w.WriteHeader(http.StatusOK)
	}))

	http.ListenAndServe(":8080", accessLogMiddleware(mux))
}
```

### マルチステージビルド
今回扱っているのがgolangアプリケーションということで、「マルチステージビルド」の構成で記述していきます。

マルチステージの構成にすることで、最終的なイメージを軽量にすることができます。
https://docs.docker.jp/develop/develop-images/multistage-build.html

以下の図のように、「バイナリをコンパイル→実行」までをまとめたDockerfileをビルドすると、コンパイルの過程でのみ必要であったGoコンパイラ等々が不要に残ったイメージが生成されます。
一方、マルチステージでは、「バイナリのコンパイル」と「バイナリ実行」をステージで分けることで、「バイナリのコンパイル」で利用した諸々は捨てて、コンテナ実行に必要なLinuxのベース+バイナリのみを最終的なイメージに含めることができます。

![](https://storage.googleapis.com/zenn-user-upload/624302b1e409-20251214.png)

コンテナイメージは、依存関係や変更差分を「レイヤー」として積み重ねた構造を持ちます。
単一のステージでまとめた時と、マルチステージで記述したDockerfileでそれぞれコンテナイメージをビルドして比較したところ、以下のような差が出ました。

| 項目 | マルチステージ | シングルステージ | 差分 |
|------|---------------|-----------------|------|
| **レイヤー数** | 8層 | 19層 | +11層 |
| **イメージサイズ** | 109MB | 924MB | +815MB (約8.5倍) |

最終的なイメージから余計なレイヤーを省くことができ、その結果としてサイズも少なくすることができるんですね。

### 実行ステージ
先のビルドステージのコードの下に書いていきます。
```Dockerfile:Dockerfile
# existing codes

FROM debian:bookworm-slim

# Create non-root user
RUN useradd -m -u 1000 appuser

WORKDIR /app

# Copy binary from builder with correct ownership
COPY --from=builder --chown=appuser:appuser /src/app/todo-app .
```

押さえておきたいのは、
- debianの軽量ベースイメージの上でバイナリを実行している
- 非ルートユーザーを作成して実行を行っている

ことです。

1点目に関しては、以下の部分で、ビルドステージでコンパイルしたバイナリ（`todo-app`）とhtmlファイルをコピーしています。
```Dockerfile
COPY --from=builder --chown=appuser:appuser /src/app/todo-app .
COPY --from=builder --chown=appuser:appuser /src/app/index.html .
```

2点目に関しては、１つのトピックとして取り上げます。
#### コンテナをrootユーザーで実行すると何が問題か
まず、linuxにおける「rootユーザー」とは、システム上で最高の権限を持っているユーザを意味します。
つまり、ファイルのpermissionもほぼ無視しますし、基本的にコマンドの実行に制限を受けません。
そんな特権を持つrootユーザーは、`UID=0`であるユーザーを指します。

Dockerfileは以下のような仕様になっているようです。

>Dockerfile に USER を設定しない場合、ユーザーはデフォルトで root になることに注意してください。

https://www.docker.com/ja-jp/blog/understanding-the-docker-user-instruction/

つまり、以下のように`USER`を指定せずに実行した場合、このイメージはrootユーザーで実行されることになります。
```Dockerfile
FROM debian:bookworm-slim
WORKDIR /app
COPY --from=builder  /src/app/todo-app .
COPY --from=builder  /src/app/index.html .
EXPOSE 8080

# rootユーザーとしてアプリケーションを起動
CMD ["./todo-app"]
```

この状態で攻撃者によりコンテナへ侵入された場合、コンテナ内で特権を用いた操作が可能になってしまいます。
また、ここ理解しておくべきは、「コンテナ内のroot ユーザーは、ホストOSのカーネルに対して強い影響を及ぼし得る」と言うことです。

このカラクリについては、コンテナ仮想技術がどのようにして実現されていたかを知れば頭に入ってきやすいです。
もう一度以下の図を引用します。
![](https://storage.googleapis.com/zenn-user-upload/ab39f4ca783e-20251214.png)
*https://www.docker.com/ja-jp/blog/top-questions-for-getting-started-with-docker/*

コンテナはホストOSのLinuxカーネル上で動いています。
そもそもコンテナは、Linuxカーネルの既存機能である、namespace/cgroup等々を用いて隔離された「プロセス」にすぎません。「コンテナ」というワードだけに注目しているとそれ単体で独立している環境のように思えますが、コンテナとホストOSは密接に繋がっています。

namespaceで隔離されているので、通常、コンテナ内のrootユーザーとホストOSカーネルのrootユーザーは別物です。
しかし、何らかの脆弱性がカーネルまたはコンテナランタイムにあった場合、コンテナ内→ホストOSカーネルに対してrootレベルの操作ができてしまうケースがあるようです。

https://medium.com/@ayoubseddiki132/why-running-docker-containers-as-root-is-a-security-nightmare-and-how-to-fix-it-83a60509d9bf

脆弱性があったとしても、コンテナ内で特権（root権限）を持たせないことにより、ホストへの影響を大きく制限することができます。そのため、コンテナでは作業用のユーザーを作成し、その非rootユーザーを利用するようにするのが推奨されます。

そういうわけで、UID=1000のユーザーを作成し、実行前に切り替え、そのユーザーで実行するようにします。基本的にUID=0じゃなければ非rootユーザーです。

```Dockerfile
# UID=1000のユーザーをappuserという名前で作成
RUN useradd -m -u 1000 appuser

# ファイルの所有者をappuserにする（appuserで実行できるように）
COPY --from=builder --chown=appuser:appuser /src/app/todo-app .
COPY --from=builder --chown=appuser:appuser /src/app/index.html .

# ユーザーをappuserに設定
USER appuser

# appuserで実行
CMD ["./todo-app"]
```

### .dockerignore
Dockerfileにはソースコードをコピーする以下のような記述をしています。
```Dockerfile
COPY . .
```
ここで、アプリケーションのソースコード以外の無駄なファイルはコピーして欲しくないので、`.dockerignore`ファイルを追加しておきましょう。

https://docs.docker.jp/v20.10/engine/reference/builder.html#dockerignore-file

内容は以下のようにしてください。

# Dockerfileからコンテナイメージをビルド→起動する
Dockerfileが記述できたので、ビルドしましょう。
`-t`(tag)オプションを使って、`app`というイメージ名に`local`というタグをつけるようにしています、。
```
docker build -t app:local .
```

`load metadata for docker.io/library/golang:1.25-bookworm`や、`load metadata for docker.io/library/debian:bookworm-slim`のように、Docker HubからイメージをPullしている様子もありますね。

これでコンテナイメージができました。
以下のコマンドで、今作成したものがあるか確認してみます。
```
docker image ls
```

`app:local`というイメージがありますね。
```
REPOSITORY   TAG       IMAGE ID       CREATED       SIZE
app          local     10fcabb3f555   4 hours ago   109MB
```

`app:local`のコンテナイメージからコンテナを起動しましょう。
```
docker run -p 8080:8080 app:local
```
ここで、`-p`オプションによって、ホストのポート`:8080`をコンテナ内のポート(`:8080`)にマッピングしています。

https://docs.docker.jp/engine/reference/commandline/run.html#p-expose

コンテナ内で実行しているgolangアプリケーションは、`:8080`番でリッスンするように書いていました。
```go
http.ListenAndServe(":8080", accessLogMiddleware(mux))
```

起動できれば、ブラウザ上で`http://localhost:8080/todos`にアクセスしてみましょう。

![](https://storage.googleapis.com/zenn-user-upload/a76fda453242-20251214.png)

上のように表示されれば成功です。
