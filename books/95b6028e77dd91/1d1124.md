# ハンズオンの流れ
構成図を全体像として、それぞれの章でどの部分を扱い、構築していくかを説明します。

### 2章 docker imageをbuildする
この章ではDockerfileを作成し、イメージをビルドしてアプリケーションをローカルマシンで起動させることをゴールとします。

docker imageは、アプリケーションとその依存関係をひとまとめにした“実行可能なパッケージ”であり、これを元にコンテナが作成されます。そしてこれは配布可能なものになっています。

このハンズオンにおける「デプロイ」とは、ビルドした docker imageを実行環境（ローカル／AWS）に参照させ、アプリケーションとして動かすことだといえます。

構成図で言うと、以下の部分です。
![](https://storage.googleapis.com/zenn-user-upload/f431c3a0e6bb-20251208.png)


### 3章 helmfileでk8sのmanifestを管理する
Kubernetes（以降、k8s）という、コンテナ化されたアプリケーションを自動で配置・実行・管理するためのオーケストレーションプラットフォームがあります。

k8sではアプリケーションの状態や構成を manifest（マニフェスト） と呼ばれる YAML ファイルで定義します。このハンズオンでは、そのmanifestを効率的に整理・管理するためにhelmfileというツールを用います。

この章では、k8sの仕組みにも触れていきます。

構成図で言うと、以下の部分です（ここは微妙に表しにくいんですが、まあ大体で）。
![](https://storage.googleapis.com/zenn-user-upload/8294be768b99-20251208.png)

### 4章 kindクラスターでデプロイしてみる
3章で完成したmanifestをローカル環境で動作する軽量なk8sクラスタであるkind（Kubernetes in Docker）にデプロイしてみます。

kindを使えばお金もかからず、簡易的にローカルマシンでk8sの動作を確認できるため、まずはEKSにデプロイする前にお手軽ローカルで試してみましょうと言う章です。

ハンズオンのゴールからは若干それますが、構成図のEKS Clusterの部分をkindに置き換えて試してみると言う感じです。

雑ですが、構成図を改変して以下のようにあらわしてました（強引）。
![](https://storage.googleapis.com/zenn-user-upload/dc6534597d2b-20251209.png)


### 5章 terraformでEKS環境を構築する
3章で用意したk8s manifestを4章ではkindクラスターにデプロイしました。
この章では、manifestをEKSクラスターにデプロイする準備として、インフラ構築をしていきます。

そこで、terraformというIaC(Infrastructure as Code)を用います。

AWS上にリソースを構築する手法として、マネコンをポチポチして作っていくのも１つです。
しかし、企業だと「インフラリソースもコードで管理する」が主流と言っていいでしょう。

ここでは、terraformの構文にも触れながら進めつつ、主にはAWSリソースやネットワークについて取り上げます。EKS環境を用意すると言っても、「EKSだけ」用意するのではなく、必要最低限に周辺リソースも作っていきます。

5章を終えると、以下の構成図が完成します。
![](https://storage.googleapis.com/zenn-user-upload/c674cdebd7e9-20251208.png)

### 6章 EKSクラスターにデプロイする
5章で用意した環境にデプロイしていきます。
具体的には、構成図のECRにdocker imageをpushし、EKSクラスタにmanifestを適用させます。

概念的に表すと以下のようになります。
![](https://storage.googleapis.com/zenn-user-upload/4ee913c95896-20251211.png)

簡単のために、control plane（後述）にあるapi-serverをVPC内の「EKSクラスター」の中に書いています。実際はcontrol plane自体はAWS管理下にあり、このVPC内にはありません。その点も面白い部分でして、その辺の仕様に関しては、5章で改めて取り上げます。
