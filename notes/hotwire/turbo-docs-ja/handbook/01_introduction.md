# Introduction

Turbo は、JavaScript をほとんど使わずに、高速でモダンなプログレッシブ・エンハンスド Web アプリケーションを構築するためのいくつかの技術を束ねたものです。ロジックをすべてフロントエンドに置き、アプリのサーバーサイドを JSON API 程度のものに押し込めてしまう、いま主流のクライアントサイドフレームワークに対する、よりシンプルな代替手段を提供します。

Turbo を使うと、サーバーが HTML を直接届けられるようになります。つまり、権限チェックのロジック、ドメインモデルとのやり取り、その他アプリケーションのプログラミングに関わる一切合切を、ほぼすべて好きなプログラミング言語の中だけで扱えるということです。JSON という境界の両側にロジックをミラーリングする必要はもうありません。ロジックはすべてサーバーに置かれ、ブラウザは最終的な HTML だけを扱います。

この HTML-over-the-wire というアプローチの利点については、[Hotwire サイト](https://hotwired.dev/)でさらに詳しく読むことができます。以下では、これを可能にするために Turbo がもたらす技術を紹介していきます。

## Turbo Drive: 永続プロセス内でのナビゲーション

従来型の複数ページ構成に対して、シングルページアプリケーション (SPA) が魅力的だった大きな理由のひとつは、ナビゲーションの速さです。SPA が高速なのは、ページ遷移のたびにアプリケーションのプロセスを丸ごと破棄しては次のページで初期化し直す、ということをしないからです。

Turbo Drive は、同じ永続プロセスモデルを使ってその速度を実現します。しかも、アプリケーション全体をそのパラダイムに合わせて作り直す必要はありません。維持すべきクライアントサイドルーターも、注意深く管理すべき状態もありません。永続プロセスは Turbo が管理し、あなたはまるで 2000 年代初頭に戻ったかのようにサーバーサイドのコードを書けばよいのです。今日の SPA という怪物の複雑さから、幸せに切り離された状態で。

これは、同じドメインの `<a href>` リンクへのクリックをすべて横取りすることで実現されます。対象のリンクがクリックされると、Turbo Drive はブラウザがそれを辿るのを防ぎ、[History API](https://developer.mozilla.org/en-US/docs/Web/API/History) でブラウザの URL を書き換え、[`fetch`](https://developer.mozilla.org/en-US/docs/Web/API/fetch) で新しいページをリクエストし、返ってきた HTML をレンダリングします。

フォームでも同じことが起こります。送信は `fetch` リクエストへと変換され、Turbo Drive はリダイレクトを辿って HTML レスポンスをレンダリングします。

レンダリングの際、Turbo Drive は `<body>` 要素の中身を置き換え、`<head>` 要素の中身をマージします。JavaScript の window オブジェクト・document オブジェクト、および `<html>` 要素は、レンダリングをまたいで保持されます。

Turbo Drive を直接操作して visit の挙動を制御したり、リクエストのライフサイクルにフックしたりすることも可能ですが、多くの場合はいくつかの規約に沿うだけで、置き換えとして無料で速度を手に入れられるドロップイン置換として機能します。

## Turbo Frames: 複雑なページの分解

多くの Web アプリケーションは、複数の独立したセグメントを含むページを表示します。たとえば議論用のページなら、上部にナビゲーションバー、中央にメッセージ一覧、下部に新規メッセージ追加用のフォーム、サイドバーに関連トピック、といった具合です。このページを生成するには通常、各セグメントを順番に生成してから組み合わせ、単一の HTML レスポンスとしてブラウザに届けることになります。

Turbo Frames を使うと、こうした独立したセグメントを frame 要素の中に入れて、ナビゲーションのスコープを絞ったり、遅延ロードさせたりできます。スコープ付きナビゲーションとは、frame の中で発生するリンククリックやフォーム送信などのすべてのインタラクションが、その frame の中だけで完結するということです。ページの他の部分は変化も再ロードもしません。

独立したセグメントを自前のナビゲーションコンテキストに包むには、そのセグメントを `<turbo-frame>` タグで囲みます。たとえば以下のようにします。

```html
<turbo-frame id="new_message">
  <form action="/messages" method="post">
    ...
  </form>
</turbo-frame>
```

上のフォームを送信すると、Turbo はリダイレクト先の HTML レスポンスから対応する `<turbo-frame id="new_message">` 要素を抜き出し、その中身を既存の `new_message` frame にスワップします。ページの他の部分はそのままです。

frame はナビゲーションをスコープするだけでなく、中身の読み込みを遅延させることもできます。frame の読み込みを遅延させるには、`src` 属性に自動的にロードしたい URL を指定します。スコープ付きナビゲーションと同様、Turbo はレスポンスから対応する frame を見つけて抜き出し、その中身を差し替えます。

```html
<turbo-frame id="messages" src="/messages">
  <p>This message will be replaced by the response from /messages.</p>
</turbo-frame>
```

これは昔ながらの frame や `<iframe>` に似ているように聞こえるかもしれませんが、Turbo Frames は同じ DOM の一部です。したがって「本物の」 frame にまつわる奇妙さや妥協はありません。Turbo Frames は同じ CSS でスタイリングされ、同じ JavaScript コンテキストの一部となり、追加のコンテンツセキュリティ制約下に置かれることもありません。

セグメントを独立したコンテキストに変えるだけでなく、Turbo Frames は次のような恩恵をもたらしてくれます。

1. **効率的なキャッシュ。** 上の議論ページの例で言えば、関連トピックのサイドバーは新しい関連トピックが現れたときに expire する必要がありますが、中央のメッセージ一覧はその必要がありません。すべてが 1 ページになっていると、個々のセグメントのどれかが expire するとキャッシュ全体が expire してしまいます。frame を使えば、各セグメントは独立してキャッシュされるため、依存キーが少なく、より長寿命なキャッシュが得られます。
2. **並列実行。** 遅延ロードされる frame はそれぞれ独自の HTTP リクエスト/レスポンスで生成されるため、別プロセスで扱うことができます。これによりプロセスを手動で管理せずに並列実行ができるようになります。エンドツーエンドで 400ms かかる複雑な複合ページを frame に分割すると、最初のリクエストは 50ms で済み、3 つの遅延ロード frame もそれぞれ 50ms、というふうにできます。3 つの frame は逐次ではなく同時に走るため、ページ全体は 100ms で完了します。
3. **モバイル対応。** モバイルアプリでは、大きく複雑な複合ページを持てないのが普通です。それぞれのセグメントに専用の画面が必要になります。Turbo Frames で構築されたアプリケーションでは、複合ページをセグメントに分ける作業を既に済ませていることになります。これらのセグメントはそれぞれ独立した URL を持っているため、そのままネイティブなシートや画面に表示できます。

## Turbo Streams: ライブなページ変更を届ける

非同期アクションに応じてページを部分的に変更していくことで、アプリケーションは「生きている」ように感じられるようになります。Turbo Frames は単一の frame 内での直接的な操作への応答としてこうした更新を提供しますが、Turbo Streams は WebSocket 接続、SSE などのトランスポート越しに送られてくる更新に応じて、ページの任意の部分を変更できるようにします。（新しいメールが届いたら自動で更新される[imbox](http://itsnotatypo.com) を想像してください。）

Turbo Streams は `<turbo-stream>` 要素と、8 つの基本アクション—`append`、`prepend`、`replace`、`update`、`remove`、`before`、`after`、`refresh` を導入します。これらのアクションと、対象要素の ID を指定する `target` 属性を組み合わせれば、ページを更新するために必要な変更をすべてエンコードできます。1 つの stream メッセージに複数の stream 要素を組み合わせることもできます。挿入・置換したい HTML を [template タグ](https://developer.mozilla.org/en-US/docs/Web/HTML/Element/template) で包むだけで、あとは Turbo が処理します。

```html
<turbo-stream action="append" target="messages">
  <template>
    <div id="message_1">My new message!</div>
  </template>
</turbo-stream>
```

この stream 要素は、新しいメッセージ入りの `div` を取り出し、ID が `messages` のコンテナに追加します。既存要素の置換も同じくらい簡単です。

```html
<turbo-stream action="replace" target="message_1">
  <template>
    <div id="message_1">This changes the existing message!</div>
  </template>
</turbo-stream>
```

これは、Rails 界隈でかつて [RJS](https://weblog.rubyonrails.org/2006/3/28/rails-1-1-rjs-active-record-respond_to-integration-tests-and-500-other-things/) と呼ばれ、その後 [SJR](https://signalvnoise.com/posts/3697-server-generated-javascript-responses) と呼ばれていた考え方の概念的な延長です。ただし今回は JavaScript を必要としません。得られるメリットは変わりません。

1. **サーバーサイドテンプレートの再利用**: ライブなページ変更は、初回ロード時のページを作るのに使ったのと同じサーバーサイドテンプレートから生成されます。
2. **HTML over the wire**: 送るのは HTML だけなので、更新を処理するためのクライアントサイド JavaScript は（もちろん Turbo 自体を除けば）必要ありません。確かに HTML のペイロードは同等の JSON より少し大きくなるかもしれませんが、gzip をかければ差は無視できる程度になりますし、JSON を取得してから HTML に組み立てるクライアント側の労力もすべて省けます。
3. **シンプルな制御フロー**: WebSocket や SSE でメッセージが届いたとき、あるいはフォーム送信への応答で何が起こるのかが、非常に明確に追えます。ルーティングも、イベントバブリングも、その他の間接的な仕組みも要りません。変えたい HTML を、どう変えるかを示すたった 1 つのタグで包むだけです。

さて、RJS や SJR とは違い、Turbo Streams のアクションの一部としてカスタム JavaScript 関数を呼び出すことはできません。しかしこれはバグではなく、機能です。ああした技術は、レスポンスと一緒に大量の JavaScript を送りつけてしまうことで、簡単に絡まった混沌を生み出しがちだからです。Turbo は DOM を更新することだけに専念し、追加の振る舞いは [Stimulus](https://stimulus.hotwired.dev) のアクションやライフサイクルコールバックで繋ぎ込めばよい、という前提を置いています。

## Turbo Native: iOS & Android のためのハイブリッドアプリ

Turbo Native は iOS と Android 向けのハイブリッドアプリを作るのに最適です。既存のサーバーレンダリング HTML をそのまま使えば、アプリの機能を一通りネイティブラッパー越しにカバーできます。そこで節約できた時間はすべて、本当に高品質なネイティブコントロールが恩恵をもたらす少数の画面をさらに良くすることに使えます。

Basecamp のようなアプリケーションは、数百もの画面を持ちます。それらを全部書き直すのは、得られる効果に対してあまりに膨大な作業です。ネイティブの火力は、本当に最高の忠実度が求められる高頻度のインタラクションのために温存しておく方がよいのです。たとえば Basecamp の「New For You」inbox のような、スワイプ操作がしっくり来る必要のある画面などです。しかし単一メッセージを表示するようなほとんどのページは、完全にネイティブにしても大して良くはなりません。

ハイブリッドで行くことは開発プロセスを速めるだけでなく、遅くて面倒な App Store のリリース手続きを経ずにアプリをアップグレードする自由度も与えてくれます。HTML でできていることは Web アプリケーション側でいつでも変えられ、すぐに全ユーザーに反映されます。Big Tech の承認を待つ必要も、ユーザーがアップグレードするのを待つ必要もありません。

Turbo Native は、iOS と Android それぞれで推奨される開発プラクティスに沿っていることを前提にしています。ネイティブ API を隠蔽したり、ネイティブコードをプラットフォーム間で共有できるようにしたりするフレームワークではありません。共有できる部分はサーバー側でレンダリングされた HTML です。ネイティブコントロールは、推奨されるネイティブ API を使って書きます。

さらに詳しくは [Turbo Native: iOS](https://github.com/hotwired/turbo-ios) と [Turbo Native: Android](https://github.com/hotwired/turbo-android) のリポジトリを参照してください。Turbo で駆動するハイブリッドアプリがどれほど良く作れるかを実感するには、HEY のネイティブアプリ ([iOS](https://apps.apple.com/us/app/hey-email/id1506603805) / [Android](https://play.google.com/store/apps/details?id=com.basecamp.hey&hl=en_US&gl=US)) を見てみてください。

## バックエンドフレームワークとの統合

Turbo を使うのにバックエンドフレームワークは必須ではありません。すべての機能はさらなる抽象化なしで直接使えるように作られています。しかし、Turbo と統合されたバックエンドフレームワークを使えるなら、生活はぐっとシンプルになるはずです。[Ruby on Rails 向けにはリファレンス実装を作っています](https://github.com/hotwired/turbo-rails)。
