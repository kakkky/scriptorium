# The Origin of Stimulus

私たち [Basecamp](https://basecamp.com) では大量の JavaScript を書いていますが、それを現代的な意味での「JavaScript アプリケーション」を作るために使っているわけではありません。私たちのアプリケーションはすべてサーバーサイドでレンダリングされた HTML を核として持ち、そこに JavaScript をひとつまみ振りかけて、輝きを添えているに過ぎません。

これは [majestic monolith](https://signalvnoise.com/svn3/the-majestic-monolith/) の流儀です。Basecamp はネイティブモバイルアプリを含む半ダースほどのプラットフォームで動作していますが、Ruby on Rails を使って作った 1 セットの controller、view、model だけでそれらすべてを賄っています。共通のインターフェースを 1 箇所で更新できることこそが、多くのプラットフォームを抱えながらも少人数チームで戦い抜けるカギになっています。

これによって、私たちは昔のような生産性で盛り上がることができるのです。 1 人のプログラマが、抽象化の層や分散システムに阻まれることなく、貪欲に前へと進んでいけた時代への回帰です。JavaScript ベースのクライアントアプリケーションのために JSON を吐き出すことこそがサーバーサイドアプリケーションの聖杯だ、と誰もが信じるようになる前の時代、と言い換えてもよいでしょう。

こうしたアプローチにも、人によっては、あるいは場合によっては、価値があることを否定するつもりはありません。ただ、多くのアプリケーション、特に Basecamp のようなものにとっては、全体としての単純さや生産性という点で退行だ、と言いたいのです。

同時に、シングルページ JavaScript アプリケーションの隆盛が本物の恩恵をもたらしていないと言うつもりもありません。その最たるものは、フルページリフレッシュから解き放たれた、より高速で流動的なインターフェースです。

Basecamp にも、そうした感触を求めていました。まるで群衆に従ってクライアントサイドレンダリングに全面移行したり、モバイルではフルネイティブに舵を切ったりしたかのような感触です。

その願いから、私たちは 2 段構えの解へと辿り着きました。[Turbo](https://turbo.hotwired.dev) と Stimulus です。

### Turbo up high, Stimulus down low

私たちの新しい控えめな JavaScript フレームワーク、Stimulus の話に入る前に、Turbo が何を提案しているかを少し振り返らせてください。

Turbo は、GitHub で開発された [pjax](https://github.com/defunkt/jquery-pjax) と呼ばれるアプローチを源流に持ちます。基本的なコンセプトは今も同じです。フルページリフレッシュがしばしば遅く感じられるのは、サーバーから送られてきた大量の HTML をブラウザが処理しないといけないから、ではありません。ブラウザはそれをとても上手に、素早くこなします。そして多くの場合、HTML ペイロードが JSON ペイロードより大きくなりがちだという事実も (特に gzip 圧縮を効かせていれば) 大した問題にはなりません。原因は、CSS と JavaScript がページに対して再初期化・再適用されなければならないことにあります。ファイル自体がキャッシュされているかどうかとは無関係にです。相応の量の CSS と JavaScript があれば、この再初期化はかなり遅くなり得ます。

この再初期化を回避するために、Turbo はシングルページアプリケーションと同じように永続プロセスを維持します。ただし大部分は不可視のプロセスです。Turbo はリンクをインターセプトし、新しいページを Ajax 経由でロードします。サーバーは相変わらず完成された HTML ドキュメントを返し続けます。

この戦略だけでも、多くのアプリケーションにおける多くの操作は本当に高速に感じられるようになります (100〜200ms でサーバーレスポンスを返せれば、という条件付きですが、キャッシュを効かせれば十分に達成可能です)。Basecamp の場合、ページ間の遷移がおよそ 3 倍速くなりました。これによって、シングルページアプリケーションの魅力の大部分だった「反応の良さ」「なめらかさ」がアプリケーションに宿ります。

しかし Turbo だけでは話は半分にしかなりません。粗い粒度の話だけです。フルページの切り替えより下の粒度、すなわち 1 ページ内での細かなインタラクションの世界が広がっています。要素の表示・非表示を切り替える、コンテンツをクリップボードにコピーする、リストに新しい todo を追加する—そういった、現代の Web アプリケーションを構成する諸々のふるまいです。

Stimulus 以前の Basecamp では、これらのひとつまみを実現するために、多種多様なスタイルとパターンを混在させて使っていました。あるコードはただの jQuery のひとつまみ、別のコードは同じくらいのサイズの素の JavaScript、また別のコードはより大きなオブジェクト指向のサブシステム、といった具合です。これらは通常、`data-behavior` 属性にぶら下がる明示的なイベントハンドリングを介して動いていました。

このやり方で新しいコードを追加するのは簡単でしたが、包括的な解ではありませんでした。あまりにも多くの社内スタイルとパターンが共存してしまっていたのです。それゆえコードの再利用は難しく、新しく参加した開発者が一貫した書き方を身につけるのも難しくなっていました。

### The three core concepts in Stimulus

Stimulus は、これらのパターンの良いところをまとめ、たった 3 つの主要概念 — Controller、action、target — を軸にした、控えめで小さなフレームワークに仕立て直したものです。

Stimulus は、それが宛先とする HTML を見たときにプログレッシブ・エンハンスメントとして読めるように設計されています。テンプレートを 1 つ見れば、それにどんな振る舞いが乗っているかが分かるようにです。以下がその例です。

```html
<div data-controller="clipboard">
  PIN: <input data-clipboard-target="source" type="text" value="1234" readonly>
  <button data-action="clipboard#copy">Copy to Clipboard</button>
</div>
```

これを読めば、何が起きているかについてかなりよいイメージを持てるはずです。Stimulus について何も知らなくても、controller のコード自体を見ていなくても、です。ほとんど疑似コードのようなものです。外部の JavaScript ファイルからイベントハンドラが適用されるだけの HTML 片を読むのとは大違いです。それに、多くの現代的な JavaScript フレームワークで失われてしまった関心の分離も保たれています。

見ての通り、Stimulus は HTML を生成することに関与しません。むしろ、すでに存在する HTML ドキュメントに自分自身を接続します。HTML は多くの場合、ページロード時に (最初のヒットで、あるいは Turbo 経由で) サーバー側でレンダリングされるか、DOM を書き換える Ajax リクエストによってレンダリングされます。

Stimulus が関心を持つのは、この既存の HTML ドキュメントを操作することです。ときには要素を隠したりアニメーションさせたりハイライトしたりする CSS クラスの追加を意味し、ときには要素をグループごとに並び替えることを意味します。またときには、キャッシュ可能な UTC 時刻を表示可能なローカル時刻へと変換するように、要素の中身を操作することを意味します。

もちろん、Stimulus に新しい DOM 要素を生成させたい場面もあるでしょうし、それをやっても構いません。将来的にそれをもっと簡単にする糖衣構文が追加されるかもしれません。しかしそれは少数派のユースケースです。焦点は要素の生成ではなく操作にあります。

### How Stimulus differs from mainstream JavaScript frameworks

このため、Stimulus は現代の主流の JavaScript フレームワークの大多数とは大きく異なります。ほぼすべてのフレームワークは、なんらかのテンプレート言語を介して JSON を DOM 要素へと変換することに主眼を置いています。多くの場合、それらのフレームワークは空のページを産み落とすところから始まり、この JSON-to-テンプレートによるレンダリングでのみ生成された要素だけで、そこを埋めていきます。

Stimulus は状態の扱いという点でも異なります。ほとんどのフレームワークは、JavaScript オブジェクトの中で状態を保持し、その状態を元に HTML をレンダリングする仕組みを持ちます。Stimulus はその真逆です。状態は HTML に保存されるので、ページ遷移をまたいで controller は破棄されても、キャッシュされた HTML が再び現れたときに、以前と同じ状態として初期化し直すことができます。

これは本当に驚くほど異なるパラダイムです。現代的なフレームワークに慣れた歴戦の JavaScript 開発者の多くは、鼻で笑うでしょう。それでもいい、笑ってください。もし React + Redux のような渦の中でアプリケーションを維持することの複雑さと労力を良しとしているのなら、Turbo + Stimulus はあなたには魅力的に映らないはずです。

一方で、いま取り組んでいるものに、そうした現代的技法が要求する強烈な複雑さやアプリケーションの分離が本当に見合っているのかどうか、心のどこかでずっと引っかかっているのなら、私たちのアプローチに救いを見出せる可能性は高いでしょう。

### Stimulus and related ideas were extracted from the wild

Basecamp では、複数のバージョンの Basecamp や他のアプリケーションで、このアーキテクチャを何年も使い続けてきました。GitHub も似たアプローチで大きな成果を上げています。これは「モダン」な Web アプリケーションはこうあるべきだという主流の理解に対する、実行可能な代替案であるだけでなく、極めて説得力のある選択肢でもあります。

実際、[Ruby on Rails](https://rubyonrails.org/) を開発した頃に Basecamp で感じていた、あの秘伝のタレのような手応えがそこにはあります。現代の主流アプローチは無駄に入り組んでいて、はるかに少ない労力ではるかに多くのこと・速いことができる、という感覚です。

さらに言えば、選択を強いられるわけでもありません。Stimulus と Turbo は、他のより重量級のアプローチと組み合わせても十分にうまく機能します。アプリケーションの 80% にとって重機を持ち出す必要がないのであれば、その部分にはこの 2 発コンボを使いましょう。そして本当に重機が効果を発揮する部分にだけ、重機を投入すればよいのです。

Basecamp でも、必要な場面では、より重量級のアプローチをいくつも使っています。カレンダーはクライアントサイドレンダリングを使う傾向がありますし、テキストエディタは [Trix](https://trix-editor.org/) という、Stimulus controller のセットとして書くのは筋が悪い、完全な形をしたテキストプロセッサです。

この一連の代替フレームワークが目指しているのは、可能な限り重量物の運搬を避けることです。ごくシンプルなモデルで無理なくこなせる大量のインタラクションについては、リクエスト-レスポンスのパラダイムの中に留まる。そして、ピークの忠実度が要求される場面でだけ、高価な道具に手を伸ばす。

なによりも、これは、より労力のかかる主流アプローチに頼るずっと大きなチームと、忠実度とリーチで張り合っていきたい、小さなチームのためのツールキットなのです。
