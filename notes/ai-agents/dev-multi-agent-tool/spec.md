# トモダチコレクション風 CLI マルチエージェントゲーム 要求定義

## なぜ作るか

マルチ AI エージェント開発を学ぶための習作。題材として『トモダチコレクション』風の住民シミュレーションを選び、1 住民 = 1 エージェントとして扱う。

## 学びたいこと

- 複数エージェントの状態管理と相互作用 (goroutine + channel)
- LLM とルールベースの **使い分け** (どこを LLM に任せ、どこをルールで決めるか)
- **Orchestrator-Worker (Supervisor) パターン**: 個々のエージェントを俯瞰する上位エージェントを置き、LLM の構造化出力で「ゲーム世界そのものを操作」させる
- **A2A プロトコルの構造を借りる**: メッセージ・タスク・アーティファクトのデータモデル、タスク状態遷移 (submitted → working → input-required → completed/failed/canceled 等)、Agent Card 相当の能力公開、および JSON-RPC 2.0 の構造 (`jsonrpc` / `id` / `method` / `params` / `result` / `error`) を Go の struct で表現する
- LLM API を SDK 経由でなく `net/http` で直叩きしたときの肌感
- 永続化された記憶を持つエージェントの設計

## 作るもの (一文)

Go で書かれた CLI ゲーム。複数の住民エージェントが Tick ベースで生活し、ルールで行動を決め、発話の文面を LLM が生成する。さらに **Supervisor エージェント** が住民全体を俯瞰し、関係性が一定の条件に達したときなどに LLM の判断でライフイベント (結婚・喧嘩・引っ越し 等) を発火させる。プレイヤーは CLI から覗いたり話しかけたりできる。

## コア要求

- 住民は複数いて、それぞれ性格・気分・他住民への好感度を持つ
- 各住民は goroutine で動き、やり取りは channel 経由
  - メッセージは **A2A + JSON-RPC 2.0 の構造を持つ Go struct** で表現 (フィールド名・状態名は仕様の JSON 表現に揃える)
  - channel ではその struct をそのまま流す。JSON シリアライズはしない (将来 HTTP 化する余地は型レベルで残しておく)
- ゲームは Tick で進む。tick ごとに各住民の状態が更新され、行動が選ばれる
- 行動の選択 (誰に話す・移動する・休む 等) はルールベース
- 発話の **文面生成だけ** LLM が担当
- 同じ場所にいる住民同士で勝手に会話イベントが発生する
- **Supervisor エージェント** が住民全体の状態と関係性を入力に取り、LLM が構造化出力で「次に発火すべきライフイベント」を返す。プログラムはその出力を解釈してゲーム世界に作用させる
  - 例: `{"event": "propose_marriage", "actor": "Alice", "target": "Bob"}` → 状態遷移 + 発話イベント生成
  - つまり「LLM がプログラムを操作する」層を意図的に持つ
  - 候補イベント: 結婚・告白・喧嘩・仲直り・引っ越し・誕生日・ご近所トラブル など
  - Supervisor は毎 tick ではなく低頻度 (例: 数十 tick に 1 回) で起動
- プレイヤーは住民に話しかけられる (`talk <name> <text>` 程度)
- 状態を JSON で save / load できる
- LLM 呼び出しはレート制限を意識する (無料枠を超えない・失敗時はテンプレ発話にフォールバック)
- LLM SDK は使わない。HTTP クライアント直書き

## やらないこと (少なくとも初期は)

- 凝った TUI / アニメーション (最初は行ベース stdout でよい)
- マルチプロセス・分散
- A2A の HTTP / SSE / push-notification トランスポート層 (構造は借りるが in-memory channel で完結させる)
- 詳細な経済・育成・ミニゲーム要素
- 本格的なテストカバレッジ (作りながら必要に応じて)

## 大まかなフェーズ

設計詳細は作りながら決める前提で、ざっくり順序だけ:

1. Tick が回って、住民の状態がルールベースで変化するだけのもの (LLM なし)
2. LLM プロバイダを差し込んで、住民が発話するようになる
3. 住民同士の会話イベントが発生する
4. プレイヤーが話しかけられる + JSON 永続化
5. **Supervisor エージェント**: 住民全体のサマリを LLM に投げ、構造化出力でライフイベントを発火させる
6. 余裕があれば: 長期記憶の要約、関係性の長期変化、Supervisor の判断ログ表示等

## 動いたと言える基準

- `go run` 一発で起動し、Ctrl+C で終了する
- しばらく眺めていると住民が勝手に発話したり関係が変わったりする
- 同じ場所に居る 2 人が会話を始める瞬間が観測できる
- `talk` で話しかけると返事が返ってくる
- 関係が深まった住民同士で **Supervisor 経由のライフイベント (例: 結婚)** が発火するのを観測できる
- 終了 → 再起動で状態が引き継がれる

## 環境前提

- Go (バージョンは作るときに決める)
- LLM: **Google AI Studio - Gemini 2.5 Flash-Lite** 無料枠
  - 1,000 RPD / 15 RPM / 250K TPM / コンテキスト長 1M
  - 注意: 無料枠で送信したデータは Google のモデル学習に使われる (今回は商用しないため許容)
- `GEMINI_API_KEY` を環境変数で渡す
- プロジェクト置き場は作るときに決める (例: `~/projects/tomocolle`)
