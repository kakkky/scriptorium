### Function Calling

大体、MCPの話を知っていたので、理解はしていた(つもり)。

https://zenn.dev/yuta_kakiki/articles/caf139a2cf5f52

要は、LLMに対してTool呼び出しを通して外部APIなどを扱えるようにするためのもの。
LLMが呼び出すのではなく、LLMアプリケーション(クライアント)が悪魔で呼び出す。

- LLMクライアントが、LLMに対してToolの情報(使い方とか)を与える
- LLMはその情報を見てJsonRPC形式(例だけど一般的だと思う)でTool呼び出しの意思表示をレスポンスとして返す
- LLMクライアントがそのレスポンスをparseして実際にTool呼び出しを実行
- LLMクライアントがそのTool呼び出しの結果をLLMに渡す

みたいなかんじ。
MCPは、そのLLMクライアント - Toolの間のやり取りを標準化しようとしたプロトコル。

### RAG
Retrieval Augmented Generationの略。
要は、LLMにContextを与えるための仕組み。

ユーザーからのinputに対して、LLMが必要とする情報を外部から検索してきて、それをContextとしてLLMに渡す。
その検索の部分を、Retrieverと読んでいるっぽい。
Retrieverの具体をあげると色々あるが見てる感じ
- ベクトルDB
- Web Search

からとってくるのが多いのかなと思った。

大体の流れは、

```
[Input] →　Retriever → Prompt構築 → LLM → [Output]
```

という感じ。RetrieverからContextとなる情報をとってきてPromptに付加する感じ。

ちなみに、Vector DBに関してはめちゃくちゃ理解しているわけではない。セマンティックな値を高次元の数値で表現している = ベクトルとやんわり理解。

### Advanced RAG
精度をよりあげるための発展系。

上の大体のRAGの流れの中のところどころに工夫を挟む感じ。


- ベクトルDBのindexing
  - わからんけど、大体はDBのindexと同じだろう。。。検索を早くするためのあれこれ。


つまりこれで、Inputを元にしてRetrieveする部分を効率化できる。

```
[Input] → Retriever(indexing済みVector DB) → Prompt構築 → LLM → [Output]
```

- 検索クエリの工夫としてのHyDE
  - シンプルなRAGだと、Input(=質問)をそのままRetrieverに渡して埋め込みベクトルの類似度で検索する感じらしい。
  - HyDEは、InputをまずそのままLLMにわたし、仮説的に解答させる。
  - その仮説的な解答をRetrieverに渡して、ベクトルDBから検索する。
  - つまり、InputをそのままRetrieverに渡すのではなく、LLMに仮説的な解答をさせてからRetrieverに渡す感じ。

ユーザーの質問よりもLLMの仮説的な答えの方がベクトルの類似度検索に適しているという前提に基づくやつ。LLMが推論しやすいものなのなら、この手法は有用。

```
[Input] → LLM(仮説的な解答) → Retriever(HyDE) → Prompt構築 → LLM → [Output]
```


- 検索後の工夫としてのRAG-Fusion
  - まず、InputをLLMに渡して、複数の検索クエリを生成し、それぞれ並列にRetrieverになげ、複数のContextをとってくるようにする。
  - それらの結果を、RRFという複数検索結果の順位を融合して並べるためのアルゴリズムで評価し、上位のものをPromptに付加する感じ。


```
[Input] → LLM(複数の検索クエリ生成) → Retriever(複数のContext取得) → RRF(順位付け) → Prompt構築 → LLM → [Output]
```

- 複数のRetrieverを使う工夫としてのRouting
  - Inputを元に、どのRetrieverを使うかをLLMに判断させる感じ。
  - ハイブリッドに複数を利用し、後で組み合わせるというのもある。

```
[Input] → LLM(どのRetrieverを使うか判断) → Retriever(複数のContext取得) → Prompt構築 → LLM → [Output]
```

また、ベクトルにはいくつか手法があり、
  - 密ベクトル (Dense Vector): 埋め込みベクトル
    - Embeddingモデルが生成する数百〜数千次元の連続値ベクトル
    - 各次元に意味的な情報が分散して詰まっている
    - ほぼ全次元が非ゼロ値
  - 疎ベクトル (Sparse Vector): BM25/TF-IDF 
    - 語彙数 (数万〜数十万) と同じ次元を持つベクトル
    - 文書に出現する単語の次元だけ値が入り、他は 0
    - 単語が一致しないと類似度が出ない (語彙ミスマッチに弱い)

これらのベクトル検索を組み合わせていい感じにするのがハイブリッドの強み。

### LLMアプリケーション評価
この書籍ではLangChainを主に使っていたのでLangSmithというやつを紹介していた。

とりあえず汎用的なのとして、評価には２種あり、
- オフライン評価
  - 事前に用意したテストセットで評価。
- オンライン評価
  - ユーザーからのFBを元に評価する


Ragasというのがオフライン評価のフレームワークとしてあり、LLM as a Judge主義。
基本的にアウトプットをLLMに評価させる。
- 生成 (Generation) 側
  - Faithfulness: 回答が取得した文脈に忠実か (ハルシネーション検出)
  - Answer Relevancy: 回答が質問に対して適切か
  - Answer Correctness: 正解と比較した正しさ
- 検索 (Retrieval) 側
  - Context Precision: 取得した文脈にノイズがどれだけ少ないか
  - Context Recall: 正解の根拠となる情報を漏れなく取得できたか
  - Context Relevancy: 取得文脈の質問への関連度

また、LangfuseとかLangSmithはこのRagasを実装しつつも、独自にルールベースの評価ロジックも設定できるようになっている。
