# はじめに
golangにはgoroutineというGoランタイムレベルでの軽量スレッドが実装されています。
Goランタイムは、以下の二つを`go`文の記述によって簡単に実現します。
- 優秀なスケジューリングにより1つのマシンスレッド上でgoroutineを高速に切り替えて実行する **並行処理**
- 複数マシンスレッド上でgoroutineを実行する **並列処理**

https://zenn.dev/yuta_kakiki/articles/1267c116bf69b8

`go`文は、非同期処理的な側面で使われることが多いかと思います。

同期的に処理が進行しているmain goroutineから、`go`文の宣言によって一部の処理が別goroutineに移譲され、main goroutineはそのgoroutineの完了を待たずに進行します。

![](/images/structured-conc/main-goroutine.png)
*処理を別goroutineに移し、main goroutineは進行する*

とても便利な`go`文ですが、使い方を誤ると**goroutine leak**を誘発してしまう可能性があります。

> A leaked goroutine is a goroutine blocked on some concurrency primitive (channels, sync.Mutex, sync.Cond, etc) that cannot possibly become unblocked.
>
> https://go.dev/doc/go1.26 より

goroutine leakとはつまり、**goroutineが終了できずに残り続け、メモリを占有し続ける状態**を指します。
goroutineはプログラムが終了するまで解放されないため、じわじわとこれが問題になり、OOMの原因になり得ます。

個人的な考えですが、goroutine leakを起こしてしまうような書き方をしてしまう理由の一つとして

- 実行するgoroutineのライフタイムを開発者が認知できていない

というのが大きいのではないかなと思っていました。

そこで、このような問題への解決策として **structured concurrency(構造的並行処理)** という概念があることを知りました。

この記事では、構造的並行処理についてと、これをGoで表現するために筆者が作成した`scope`というpackageについて紹介します。

https://github.com/kakkky/scope


# 構造的並行処理について
構造化プログラミングの文脈から、いかにして構造的並行処理という概念の必要性が謳われるようになったのかを簡単に説明していきます。

## 並行処理は構造化プログラミングを破っている？

構造的並行処理は、「構造化プログラミング(structured programming)」の概念を並行処理にも適用させたものになっています。

「構造化プログラミング」は、決められた制御構造の組み合わせだけでプログラムを組み立てる手法です。

制御構造というと、逐次的な実行である**順次**(sequential)、`if-else`による**選択**(selection)、`while`や`for`による**繰り返し**(repetition)の基本的な３つの要素でプログラムの流れを明確にしようというものですね。

上の3つの要素は、すべて「入口が1つ、出口が1つ」のブロックです。ブロックを抜けたということは、ブロック内の処理は完了しているということになります。

これにより、プログラムの処理の流れが上→下に固定されます。つまり、とても読みやすくなるんですね。

しかし、並行処理/非同期処理の呼び出しは「構造化プログラミング」による「制御フローの抽象化」を破壊しているのではないかというのです。

![](/images/structured-conc/structure-example.png)
*並行処理は上から下に流れる制御フローから外れている*

以下のコードを見てください。`hoge`関数を実行した後、`fuga()`関数を`go`文で実行しています。
```go
func foo() {
  hoge()
  go fuga()  // 制御フローが横に飛び出す
  // ...
  return     // fuga はまだ生きているかもしれない
}
```
この場合、`foo()`がreturnして終了したとしても、並行処理としている`fuga()`が完了したかどうかわかりません。もしかしたら終了しているかもしれないし、まだ処理中かもしれません。

`foo()`の呼び出しもとは、`foo()`が完了した時点で`foo()`ブロック内の処理は完了していると考え、後続の処理を続けるでしょう。しかし、`go`による並行タスク実行によってそれが保証されない。関数呼び出しという一種の「抽象化」が破られています。
これは、goroutineのメモリリーク、共有リソース操作の競合、goroutine内のエラーの握り潰しなど、バグの温床になります。

これを解決するための一種の並行処理/非同期処理のパラダイムとして提唱されているのが **構造的並行処理(structured concurrency)** です。


## 構造的並行処理

構造的並行処理は以下3つのルールに集約されると言えます。

- 子スレッドのライフタイムは親スレッドのライフタイムに束縛される
- 子→親スレッドへエラーが伝播される
- タスクグループ内においてキャンセルが伝播される

### 子スレッドのライフタイムは親スレッドのライフタイムに束縛される
構造化プログラミングが目指すところである、「処理の流れを上から下に読めるようにする」ために重要なことは、処理の始点と終点を明確にすることにあると思います。
`if`や`while`は、ブロックの開き括弧が始点、閉じ括弧が終点です。

構造的並行処理は、「並行タスクのライフサイクルを１つのブロックスコープ内に終始させる」ことでこれを実現します。このブロックスコープは、タスクグループとも呼ばれるようです。

図解で以下のように示せます。子スレッド（= 並行タスク）のライフタイムは、親スレッドによって明確に管理されます。

![](/images/structured-conc/structured-conc-concept.png)
*タスクグループを抜けた時点で子スレッドの完了が保証される*

並行処理として呼び出した子スレッドは、タスクグループのブロックスコープ内で実行され、終了します。よって、その子スレッドの始点と終点が明確になっているんですね。

これにより構造化プログラミングの規約が満たされ、結果的に並行タスクのライフタイムが明確になります。

### 子→親スレッドへエラーが伝播される
普通、関数呼び出しはコールスタックという形式でツリー上につながっています。
しかし、並行処理が子スレッドとして起動されると、そのコールスタックからは外れてしまいます。

以下のプログラムを実行してみます。
```go
func main() {
  hoge()
  fmt.Println("main completed")
}

func hoge() {
  go panicTask()
  time.Sleep(time.Second)
}

func panicTask() {
  panic("something went wrong")
}
```
出力が以下のようになりました。

```bash
❯ go run main.go
panic: something went wrong

goroutine 7 [running]:
main.panicTask()
	workspace/main.go:19 +0x2c
created by main.hoge in goroutine 1
	workspace/main.go:14 +0x24
exit status 2
```

「`panicTask()`が`hoge()`にて作成された」というところから始まっています。

直感的には`main()`→`hoge()`→`panicTask()`というようにコールスタックが記録されているかと想像しますが、そうではないようです。

つまり、`panicTask()`のpanicは`goroutine 7`の中で完結しており、`hoge()`や`main()`のスタックには届きません。`hoge()`は子の失敗を知る術がありません。

コールスタックから外れるということは、エラーを伝播する経路そのものが存在しないということになります。

構造的並行処理では、エラーの伝播を保証します。

![](/images/structured-conc/err-propagation.png)
*親スレッド上でタスクグループ内タスクのエラーを補足できる*


### タスクグループ内においてキャンセルが伝播される
タスクグループ内のタスクが失敗した場合、同タスクグループ内の他タスクの実行はキャンセルされます。

まず、一般的な関数のエラーハンドリングを見てみましょう。
`hoge()`内で呼び出している`foo`がエラーを返す、もしくはpanicを引き起こした時、`fuga()`は実行されないように記述するのが自然です。
```go
func hoge() error {
  if err := foo(); err!=nil{
    return err // 後続の処理は行わずreturnする。panicが起きた場合はプログラムがクラッシュするので後続の処理には進まない。
  }
  fuga()
  // ...
  return nil
}
```

これと考えは同じで、タスクグループ内のいずれかのタスクが異常終了した場合は、他のタスクを続行するべきではありません。

![](/images/structured-conc/cancel-propagation.png)
*fuga()の異常終了により、hoge()の実行がキャンセルされる*

------

このように、構造的並行処理は「並行処理を一般的な構造化プログラミングとして扱えるようにしよう」という試みであるということがわかります。


## Goには言語仕様的に組み込まれていない
並行処理の実行のためのAPIとして`go`文が提供されているGoですが、構造的並行処理が言語仕様に組み込まれているわけではありません。
しかし他言語に目を向けてみると、いくつかの言語では対応がされていました。

| 年 | 言語 | バージョン | 機能 | 参考 |
|---|---|---|---|---|
| 2018 | Kotlin | kotlinx.coroutines 1.0 | `CoroutineScope` | [kotlinx.coroutines](https://github.com/Kotlin/kotlinx.coroutines) |
| 2021 | Swift | Swift 5.5 | `withTaskGroup`（SE-0304） | [Swift 5.5 Released](https://www.swift.org/blog/swift-5.5-released/) |
| 2022 | Python | Python 3.11 | `asyncio.TaskGroup` | [asyncio docs](https://docs.python.org/3/library/asyncio-task.html#task-groups) |
| 2023 | Java | Java 21 (Preview) | `StructuredTaskScope`（JEP 453） | [JEP 453](https://openjdk.org/jeps/453) |

Goにはそれがありませんが、過去のissueを見ると、議論がなされていたことが垣間見えます。

内容は、Goの2系から構造的並行処理を言語仕様として導入することの提案です。

https://github.com/golang/go/issues/29011

結果的に以下の理由でこの提案は棄却されています。
- 既存のコードをほぼ全て壊すため採用できない
- 準標準packageである`golang.org/x/sync/errgroup`と、標準の`context.Context`の終了シグナルにより大体は実現可能なので具体的な言語変更は不要

提案自体には否定的な姿勢を示すだけではなく、一部賛同している部分もありそうでした。そのため、Goメンテナ側はさらなる議論が必要としています。
その後この話題が進展している様子はwatchできていません。

## Goで構造的並行処理を実現する選択肢

言語自体に組み込まれてはいないものの、標準/準標準/3rd party packageを利用すればある程度は実現することはできます。
筆者が把握している範囲に限ってですが、以下のpackageについて簡単に機能性を整理します。

- `golang.org/x/sync/errgroup`
- `sourcegraph/conc`
- `arunsworld/nursery`

それぞれを構造的並行処理の3要件（ライフタイム束縛・エラー伝播・キャンセル伝播）の観点で整理してみました。

| 観点 | `errgroup` | `conc` | `nursery` |
|---|---|---|---|
| ライフタイム束縛 | △ `Wait()`を呼べば待てる（呼び忘れ可能） | △ `Wait()`を呼べば待てる（呼び忘れ可能） | ◯ `RunConcurrently`内で完結 |
| エラー伝播 | ◯ `Wait()`の戻り値で取得 | ◯ `pool.ErrorPool`等で取得／panicも再raise | ◯ `RunConcurrently`の戻り値で取得 |
| キャンセル伝播 | △ `WithContext`＋各goroutineで`ctx.Done()`を見る前提 | △ `pool.ContextPool`等で対応可（同上） | ◯ いずれかのerrorで共有contextが自動キャンセル |

各packageへのリンクは以下です。

- `errgroup` : https://pkg.go.dev/golang.org/x/sync/errgroup
- `conc` : https://pkg.go.dev/github.com/sourcegraph/conc
- `nursery` : https://pkg.go.dev/github.com/arunsworld/nursery

`errgroup`/`conc`は3要件を概ね満たせるものの、`Wait()`の呼び忘れを構文レベルで防ぐことはできません。
また、`errgroup.Group`のインスタンスを宣言→`Group`からgoroutineを実行→`Wait()`で合流待機といった、ある種**「手続的な」書き方がgoroutineのライフタイムをわかりにくくしている原因なのではないか**なと個人的に考えています。
```go
func main() {
  var g errgroup.Group

  g.Go(func() error {
    // ...
    return nil
  })
  g.Go(func() error {
    // ...
    return nil
  })

  if err := g.Wait(); err != nil {
    fmt.Println("error:", err)
  }
}
```
手続き的という特性には、その記述スタイルにある程度の自由性が付与されていると考えることができます。例えば、以下のように書くことも可能です。
```go
func main() {
  var g errgroup.Group
  spawnTasks(&g)

  // 何らかの処理...

  if err := g.Wait(); err != nil {
    fmt.Println("error:", err)
  }
}

func spawnTasks(g *errgroup.Group) {
  g.Go(func() error {
    // ...
    return nil
  })
  g.Go(func() error {
    // ...
    return nil
  })
}
```
`Go()`でgoroutineを起動する場所と`Wait()`で合流する場所をいくらでも分離できる訳ですね。
このようにコーディングされた場合、コードを全体的に見渡さないと実行されているgoroutineがいつまで生き続けるのかを把握しづらくなります。


そこで、上のコード中に何らかの実装追加を以下のように行ったとします。
```go
func main() {
  var g errgroup.Group
  spawnTasks(&g)

  // ⭐︎ コード追加
  if err := somethingCheck(); err != nil {
    log.Println("error:", err)
    return // ← g.Wait()を通らない。task A/Bは走りっぱなしのまま終了
  }

  // 何らかの処理...

  if err := g.Wait(); err != nil {
    fmt.Println("error:", err)
  }
}
```

この時点で、`spawnTasks()`内で起動したgoroutineを待機するチェックポイントは通過しないルートが出てきてしまいました。
goroutineでファイル/ネットワーク通信処理が行われていた場合、`main()`の終了とともにgoroutineは強制終了となります(プログラムとして終了するため)。

また、これがHTTPハンドラー関数だとすると、goroutine leakの温床になります。
`handleRequest()`が`return`してもサーバープロセスは生き続けるので、goroutineは孤児として残り続ける可能性があります。
```go
func handleRequest(w http.ResponseWriter, r *http.Request) {
  var g errgroup.Group
  spawnTasks(&g)

  // ⭐︎ コード追加
  if err := somethingCheck(); err != nil {
    log.Println("error:", err)
    return // ← g.Wait()を通らない。task A/Bは走りっぱなしのまま終了
  }

  // 何らかの処理...

  if err := g.Wait(); err != nil {
    log.Println("error:", err)
  }
}
```

`arunsworld/nursery`はその点、タスクグループを構文として強制している点が良く、構造的並行処理の3つの要件を満たします。

`arunsworld/nursery`はPythonのtrioライブラリの一機能である`nursery`から着想をそのまま得ているものと思われます。
trioの`nursery`は["Notes on structured concurrency, or: Go statement considered harmful"](https://vorpus.org/blog/notes-on-structured-concurrency-or-go-statement-considered-harmful/)という構造的並行処理に関して強い影響力を与えたブログの著者であるNathaniel J. Smith氏が開発したものです。

`arunsworld/nursery`は、他言語に提供されている機能性と比べると、ミニマムなものとなっています。


Kotlin coroutines / Swift Structured Concurrency / Python `asyncio.TaskGroup` / Java `StructuredTaskScope` などで一般的に提供されている機能には、以下のようなものがあります。

- **panic / 例外回収**
  - タスクの異常終了を補足して親に伝播
  - 例: Kotlin（コルーチンの例外は親 `CoroutineScope` に自動伝播）/ Swift `withThrowingTaskGroup` / Python `TaskGroup` (`ExceptionGroup` として再送出) / Java `scope.throwIfFailed()`
- **動的タスク追加**
  - スコープ内で実行中のコードから新たなタスクを追加できる
  - 例: Kotlin `launch` / Swift `TaskGroup.addTask` / Python `TaskGroup.create_task` / Java `scope.fork`
- **Timeout / Deadline**
  - スコープ全体に時間制限を設ける
  - 例: Kotlin `withTimeout` / Python `asyncio.timeout` / Java `joinUntil` (Swift はコアAPI無し、`Task.sleep` + `group.cancelAll()` で自作が慣用)
- **ネスト子スコープ**
  - 親スコープから子スコープを派生させる明示API
  - 例: Kotlin nested `coroutineScope` / Swift nested `withTaskGroup` / Python nested `asyncio.TaskGroup` / Java nested `StructuredTaskScope`
- **型付き結果取得**
  - タスクの戻り値を型安全に受け取る
  - 例: Kotlin `Deferred<T>` / Swift `async let` / Python `asyncio.Task[T].result()` / Java `Subtask<T>.get()`
- **エラー集約**
  - 全タスクのエラーをまとめて取得
  - 例: Python `ExceptionGroup` (PEP 654) / Java カスタムポリシー
- **Supervisor mode**: 一部のタスクが失敗しても他のタスクをキャンセルしない
  - 例: Kotlin `supervisorScope` / `SupervisorJob` (Java は JEP 505 以降の `Joiner.awaitAll()` で同等のことが可能)
- **最初の成功で他をキャンセル**
  - いずれかが成功した時点で他のタスクを打ち切る
  - 例: Java `StructuredTaskScope.ShutdownOnSuccess`



そこで、**構造的並行処理の概念に忠実**であり、かつ**一定の機能性を兼ね備えた**packageを目指して筆者が実装したのが、次に紹介する`scope`packageになります。

# `scope` packageの紹介

コンセプト / 機能性の観点から簡単に紹介します。

https://github.com/kakkky/scope

## コンセプト
最も基本的な設計コンセプトは、

- goroutineのライフタイムをレキシカルスコープによって「宣言的に」束縛する

です。

その点は、他言語の構造的並行処理の実装と比べると特異点はありませんし、`arunsworld/nursery`と志向は同じです。


![](/images/structured-conc/scope-concept.png)
*goroutineはscopeを超えて存続しない*


`scope`では、タスクグループを`scope.Run`という一つの関数呼び出しで表現します。
`scope.Run`の`body`（第二引数のコールバック）の中だけが「並行処理を起動して良いスコープ」であり、`scope.Run`がreturnする時点で、その内側で起動したgoroutineは**必ず完了またはキャンセル済み**であることが保証されます。

`errgroup`で挙げた例を`scope`で書き直すと以下のようになります。

```go
func main() {
    err := scope.Run(context.Background(), func(s *scope.Scope) error {
        s.Go(func(ctx context.Context) error {
            // ...
            return nil
        })
        s.Go(func(ctx context.Context) error {
            // ...
            return nil
        })
        return nil
    })
    if err != nil {
        fmt.Println("error:", err)
    }
}
```

`scope.Run`のbodyの開き括弧がタスクグループの始点、閉じ括弧が終点です。`Wait()`に相当する明示的な合流処理は存在せず、`scope.Run`がreturnする時点で合流が完了します。

これにより、

- 「`Wait()`の呼び忘れ」を構文レベルで不可能にする
- 起動と合流の場所が分離されない（`Scope`インスタンスが`scope.Run`の外に漏れない）
- `body`の途中で`return`しても、起動済みのgoroutineは`scope.Run`で待機・回収される

といった効果が得られます。

## 機能性

他言語の構造的並行処理に実装された一般的な機能性に倣う形で、`scope`では以下を提供しています。

### panic / 例外回収
`scope.Run`配下で起動されたgoroutine内のpanicは自動でrecoverされ、`scope: panic recovered: ...`という形式のerrorに変換されて`scope.Run`の戻り値として返ります。プロセスは落ちません。

```go
err := scope.Run(ctx, func(s *scope.Scope) error {
    s.Go(func(ctx context.Context) error {
        panic("something bad")
    })
    return nil
})
// err: scope: panic recovered: something bad (+ stack trace)
```

### 動的タスク追加
`Scope.Go`はbody内に限らず、**既に起動済みのgoroutine内からも呼び出せます**。事前にタスクを配列で列挙しておく必要はありません。

```go
scope.Run(ctx, func(s *scope.Scope) error {
    s.Go(func(ctx context.Context) error {
        for _, item := range fetchItems(ctx) {
            s.Go(func(ctx context.Context) error {
                return process(ctx, item)
            })
        }
        return nil
    })
    return nil
})
```

### Timeout / Deadline
`scope.WithTimeout(d)`オプションでスコープ全体に時間制限を設けられます。期限超過時はスコープのcontextがキャンセルされ、`context.DeadlineExceeded`が返ります。

```go
err := scope.Run(ctx, func(s *scope.Scope) error {
    s.Go(func(ctx context.Context) error {
        <-ctx.Done()
        return ctx.Err()
    })
    return nil
}, scope.WithTimeout(10*time.Millisecond))
```

### ネスト子スコープ
`Scope.Scope`で子スコープを派生できます。子スコープのcontextは親のcontextから派生しており、子スコープ内のgoroutineは子スコープを抜ける時点で完了が保証されます。

```go
scope.Run(ctx, func(s *scope.Scope) error {
    s.Scope(func(child *scope.Scope) error {
        child.Go(func(ctx context.Context) error {
            // child scope 内のタスク
            return nil
        })
        return nil
    })
    // ここに到達した時点で child scope の全タスクは完了済み
    return nil
})
```

### 型付き結果取得
`scope.GoFuture[T]`でジェネリックな結果を返すgoroutineを起動でき、`Future[T].Wait()`で型安全に値を取り出せます。`chan T`を別途用意したりクロージャで外部変数に書き込んだりせずに、戻り値として直接受け取れます。タスク間に依存がある場面（DAG的なフロー）で有用です。

```go
scope.Run(ctx, func(s *scope.Scope) error {
    aF := scope.GoFuture(s, func(ctx context.Context) (int, error) {
        return 9, nil
    })
    bF := scope.GoFuture(s, func(ctx context.Context) (int, error) {
        a, err := aF.Wait()
        if err != nil {
            return 0, err
        }
        return a + 1, nil
    })
    s.Go(func(ctx context.Context) error {
        v, _ := bF.Wait()
        fmt.Println(v) // 10
        return nil
    })
    return nil
})
```

### エラー集約
デフォルトは「最初のerrorのみを返す（first-error-wins）」挙動ですが、`scope.WithErrAggregation()`を渡すと全goroutineのerrorを`errors.Join`でまとめて返します。

```go
err := scope.Run(ctx, func(s *scope.Scope) error {
    s.Go(func(ctx context.Context) error { return errA })
    s.Go(func(ctx context.Context) error { return errB })
    return nil
}, scope.WithErrAggregation())
// errors.Is(err, errA) && errors.Is(err, errB)
```

### Supervisor mode
`scope.WithSupervisor()`を渡すと、同スコープ内のgoroutineの失敗が他の兄弟goroutineのcontextをキャンセルしなくなります。「片方が落ちても他は走らせ続けたい」というケース向けです。

```go
scope.Run(ctx, func(s *scope.Scope) error {
    s.Go(func(ctx context.Context) error {
        return errors.New("task failed")
    })
    s.Go(func(ctx context.Context) error {
        // ctx はキャンセルされない
        return doWork(ctx)
    })
    return nil
}, scope.WithSupervisor())
```

### 最初の成功で他をキャンセル
`scope.WithCancelOnSuccess()`を渡すと、いずれかのgoroutineが`nil` errorで返った時点でスコープのcontextをキャンセルします。ヘッジリクエスト（同じ問い合わせを複数経路に投げて速い方を採用する）パターンに利用できます。

```go
err := scope.Run(ctx, func(s *scope.Scope) error {
    s.Go(func(ctx context.Context) error { return queryA(ctx) })
    s.Go(func(ctx context.Context) error { return queryB(ctx) })
    return nil
}, scope.WithCancelOnSuccess())
```

### 最大並行数の制限
これは構造的並行処理に必須の機能ではないですが、実用的な機能として`scope.WithMaxConcurrency(n)`を提供しています。スコープ内で同時に走るgoroutineの数を制限でき、上限に達した状態での`Scope.Go`は空きが出るまで待機します。
外部API呼び出しのレートリミット対策や、リソース消費の抑制に使えます。

```go
scope.Run(ctx, func(s *scope.Scope) error {
    for _, item := range items {
        s.Go(func(ctx context.Context) error {
            return process(ctx, item)
        })
    }
    return nil
}, scope.WithMaxConcurrency(3))
```

:::message
### goroutineは外側からキャンセルできない

goroutine自体をキャンセルするということはGoの言語機能として不可能です。

よって、`scope`はスコープ内goroutineへ渡しているcontextに対してキャンセル通知を送るだけです。

つまり、実際にgoroutineがキャンセルされるためには、goroutine内でcontextのキャンセル通知(`context.Done()`)を監視しておく必要があります。その部分については開発者の責務になります。
```go
s.Go(func(ctx context.Context) error {
    for _, item := range items {
        select {
        case <-ctx.Done():
            return ctx.Err() // キャンセル通知を受けて早期終了
        default:
        }
        // itemに対する処理
        process(item)
    }
    return nil
})
```

ただ、`scope`を使っている場合、何がなんでもそれを書かないといけないのかというと別にそうでもないかなと思います。
例えば、HTTPリクエストやDB呼び出しを行う場合に利用するAPIは、内部実装としてcontextを受け取ってキャンセル通知を監視し、検知したら終了するようにケアされていることが多いと思うからです。
また、長寿命処理にならないことが明確な場合は、タスクは自然に完了して`scope.Run`へ合流するので、わざわざキャンセル監視を書く必要もないでしょう。

そのため、自分で`<-ctx.Done()`を書くのは、contextを直接見るのが必要な長時間ループ等の場合のみで良いだろうと考えています。
:::
