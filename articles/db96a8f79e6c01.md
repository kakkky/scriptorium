# はじめに


# GC(Garbage Collection)とは
Garbage Collectionとは、プログラムが使用しなくなったヒープ領域のメモリを自動的に回収する仕組みのことです。これにより、開発者はメモリ管理を意識せずにコードを書くことができます。

ざっと、コンテナでGoプログラムを起動させた時のメモリの勢力図を以下に記してみました。
![](/images/gc/mem-structure.png)

それぞれ、以降で利用するメトリクスの値でラベリングしています。それぞれの値は以下のように説明できます。
| メトリクス | 説明 |
| --- | --- |
| [`MemStats.Sys`](https://github.com/golang/go/blob/f4d1304904aadf0fa5281b1ede5274a238824762/src/runtime/mstats.go#L78) | Go ランタイムが OS から借りた仮想アドレス領域の総量。heap / stack / 内部メタデータの合計 |
| [`HeapSys`](https://github.com/golang/go/blob/f4d1304904aadf0fa5281b1ede5274a238824762/src/runtime/mstats.go#L138) | そのうち heap 用に借りた仮想領域。`HeapInuse + HeapIdle` |
| [`HeapInuse`](https://github.com/golang/go/blob/f4d1304904aadf0fa5281b1ede5274a238824762/src/runtime/mstats.go#L166) | 使用中の span(=ページ単位のバイト塊) の合計。中に 1 個以上オブジェクトがある span |
| [`HeapAlloc`](https://github.com/golang/go/blob/f4d1304904aadf0fa5281b1ede5274a238824762/src/runtime/mstats.go#L125) | 実際に allocated されたオブジェクトのバイト数。中でも参照されているものを live heapと呼ぶ。 |
| [`HeapIdle`](https://github.com/golang/go/blob/f4d1304904aadf0fa5281b1ede5274a238824762/src/runtime/mstats.go#L153) | 中身が空の span の合計。次のアロケーションで再利用される空き |
| [`StackSys`](https://github.com/golang/go/blob/f4d1304904aadf0fa5281b1ede5274a238824762/src/runtime/mstats.go#L210) | goroutine スタック用に OS から借りた領域。各 goroutine のローカル変数や呼び出しフレームが置かれる。 |
| `バイナリ由来` (Sys 外) | 実行コード (Text)、グローバル変数 (Data / BSS)。Sys には含まれない |

この勢力図の中で、GCが対象とするのはヒープ(`HeapSys`)領域のメモリとなります。

::::message
### ヒープ/スタック
これら二つのメモリ割り当て領域はGolangに関わらず登場します。
それぞれ以下のように整理できます。

#### ヒープ
動的メモリ割り当て領域。
変数の寿命や参照関係がコンパイル時に分からないため、いつ解放するかをランタイムが判断する必要がある。

例：
- nが変数で実行時にしかサイズがわからない
```go
make([]byte, n)
```

- 変数の寿命が関数スコープを超える
```go
func hoge() *Local{
  local := ...

  return &local
}
```

#### スタック
静的メモリ割り当て領域。
コンパイル時に変数等の寿命が判断できるため、関数を抜ければ機械的に解放できる。

例：

- 関数の中で使われるローカル変数
```go
func hoge() int {
      x := 42
      return x
  }
```
::::

つまり、動的に増え続ける分、使われなくなったメモリを解放し、再利用可能な状態にする仕組みが必要であり、それがGCであるわけです。

そして、「動的に増える」というのは、つまり`HeapAlloc`としてメモリ割り当てが発生するということになります。
![](/images/gc/mem-alloc.png)

メモリは基本的には`HeapIdle`から取ると考えましょう。(ローカルキャッシュとか詳細にはもう少し手段はあります)

では、`HeapIdle`に確保された空きメモリでは足りなくなった場合はどうなるでしょうか。

その場合、`syscall`経由でOSからメモリを借りることになります。

::::details OSからメモリを拝借しているコード部分
```go:runtime/mheap.go

// runtime/mheap.go
// 
// allocSpan allocates an mspan which owns npages worth of memory.
//go:systemstack
func (h *mheap) allocSpan(npages uintptr, typ spanAllocType, spanclass spanClass) (s *mspan) {
	// ...
	if base == 0 {
		// Try to acquire a base address.
		base, scav = h.pages.alloc(npages)
		if base == 0 { // HeapIdleから取れなかった場合
			var ok bool
			growth, ok = h.grow(npages) // OS からメモリを借りて HeapIdle を増やす
			if !ok {
				unlock(&h.lock)
				return nil
			}
			base, scav = h.pages.alloc(npages) // 改めて HeapIdle から取り直す
			if base == 0 {
				throw("grew heap, but no adequate free space found")
			}
		}
	}
  // ...	
}

// runtime/mheap.go
// 
// Try to add at least npage pages of memory to the heap,
// returning how much the heap grew by and whether it worked.
//
// h.lock must be held.
func (h *mheap) grow(npage uintptr) (uintptr, bool) {
	// ...
	if nBase > h.curArena.end || /* overflow */ end < h.curArena.base {
		// Not enough room in the current arena. Allocate more
		// arena space. This may not be contiguous with the
		// current arena, so we have to request the full ask.
		av, asize := h.sysAlloc(ask, &h.arenaHints, &h.heapArenas) // メモリをOSから予約
		// ...
	}
	// Transition the space we're going to use from Reserved to Prepared.
	//
	// The allocation is always aligned to the heap arena
	// size which is always > physPageSize, so its safe to
	// just add directly to heapReleased.
	sysMap(unsafe.Pointer(v), nBase-v, &gcController.heapReleased, "heap") // OSから予約したメモリを利用可能状態にする

	// ...
	return totalGrowth, true
}
```
::::

コンテナの場合、コンテナの cgroup memory limit の枠から物理メモリが割り当てられ、その分`HeapSys`が増える感じです。
![](/images/gc/mem-alloc-bollow-from-os.png)

では、ランタイムが物理メモリの上限を超えてメモリを要求した場合にどうなるでしょうか。

OSカーネルのOOM Killerがコンテナ内のプロセスを強制終了します。いわゆる、OOM(Out Of Memory)です。
![](/images/gc/mem-alloc-oom.png)

こうならないために、GCが`HeapAlloc`から「参照されていないオブジェクト」を判断して`HeapIdle`に戻します。
![](/images/gc/mem-gc.png)

このような処理をGoランタイムが自動でやってくれるのは非常に便利です。
開発者にとってのノイズを一つ減らしてくれます。



しかしながら、このGC処理は常時回っているわけではなく、発火するタイミングがあります。
これを知らずにコードを書いた場合、GCがうまく働かずにOOMを引き起こしてしまう可能性があります。

本記事のゴールは、いくつかあるGCタイミングを理解することです。
GCタイミングを意識できれば、コードから漂うOOMの匂いに気づき、チューニングを行うことも可能でしょう。

次節以降では、OOMを引き起こす可能性のあるサンプルコードを例に進めます。GCタイミングを意図的に操作してOOMを回避できるようにしてみることで、理解を深めていきます。

# サンプルコードで考える
memory limitを設定しやすいので、コンテナとして実行してみます。

さて、以下のコードをmemory limit = 512MBのコンテナで実行した場合、正常に終了するでしょうか。
内容としては、各ループで指定のサイズのバイトスライスを確保する感じです。それに加えて計測用のコードがあるくらいです。
```go
package main

import (
	"crypto/rand"
	"fmt"
	"runtime"
)

const MiB = 1024 * 1024

func main() {
	sizes := []int{
		200 * MiB,
		180 * MiB,
		175 * MiB,
		140 * MiB,
		60 * MiB,
		170 * MiB,
		40 * MiB,
		120 * MiB,
		80 * MiB,
		150 * MiB,
	}

	for iter, size := range sizes {
		// 指定のサイズのランダムなバイト列を生成
		buf := make([]byte, size)
		_, _ = rand.Read(buf)

		// 計測
		var m runtime.MemStats
		runtime.ReadMemStats(&m)

		fmt.Printf(
			"iter %d HeapAlloc=%dMiB NextGC=%dMiB NumGC=%d\n",
			iter+1,
			m.HeapAlloc/MiB,
			m.NextGC/MiB,
			m.NumGC,
		)
	}
}

```
```Dockerfile:Dockerfile
FROM golang:1.25-alpine AS build
WORKDIR /src
COPY main.go .
RUN go build -o main main.go

FROM alpine:3.20
COPY --from=build /src/main /main
CMD ["/main"]
```


ループ毎に以下のメトリクスを出力します。
| メトリクス | 説明 |
| --- | --- |
| `HeapAlloc` | 現在ヒープに allocated されているバイト数。参照されているもの (live) と 参照が切れているもの (dead) の合計 |
| `NextGC` | 次の GC が発火するヒープサイズの閾値 (target heap memory)。`Live heap × (1 + GOGC/100)` で計算される。この辺に関しては後述する。 |
| `NumGC` | プログラム起動からの累計 GC 回数。前のループから増えていればその間に GC が走った証拠 |

これを、512Mをlimitとしたコンテナで実行してみます。
```bash
docker build -t gc . // ビルド
docker run --name gc-sample --memory=512m --memory-swap=512m gc // swap　しないようにして実行
```

結果を見る前に、直感的にはどう動くと考えられるでしょうか。

ループごとに処理するバイトサイズはどれも512Mib以下です。
ぱっと見、各ループごとに`buf`は参照が切れますから、GCによってメモリが解放され、10回のループを完遂するように思えませんか？
筆者なら以下のようなheapの推移を想起します。
１回目のループで200Mib分、`HeapAlloc`が膨れ上がったのち、2回目のループに差し掛かる時点で参照が切れてGCにより解放される。
また`HeapAlloc`が0の状態から始まり、180Mibまで膨れ上がる.....。

::::message
直感的に考えても、前回のdead heap分のGCの完了が遅延して２ループ目ではピーク時380Mibまでは残っていてもおかしくない気はしますよね。
まあそれでも3ループ目では1回目の分は流石に解放されていると考えれば、3ループ目のピーク時のヒープメモリサイズは355Mibほどと考えるのが自然な気がします。
::::

![](/images/gc/sample-heap-intuitive.png)



すると、以下のようにしてコンテナが終了してしまいました。

# GCタイミング
GCタイミングは主に以下の4つであると考えられます。

1. "Target heap memory"への到達時
2. `GOMEMLIMIT`への到達時
3. `runtime.GC()`の実行時
4. 最後のGCから2分経過時

これらのタイミングを理解していれば、サンプルコードのOOMを回避させることができます。
詳細とともにそのタイミングを用いた改善策を見ていきましょう。

# 各GCタイミングを理解してOOMを回避させてみる
順に見ていきます。

## 1. "Target heap memory"への到達時
1GCサイクル後にターゲットヒープサイズを決定し、そのターゲットヒープサイズに達したタイミングを次回のGCタイミングとするというものです。

以下にそのターゲットヒープサイズを決める数式を示します。

$$ Target heap memory = Live heap + (Live heap + GC roots) * GOGC / 100 $$

| 値 | 説明 |
| --- | --- |
| `Target heap memory` | 次の GC が発火するヒープサイズの閾値。|
| `Live heap` | 直近の GC完了時点で生存（reachable）と判定されたオブジェクトの合計サイズ。参照が残っているヒープ上のデータ |
| `GC roots` | GC がトレースを開始する起点。goroutine のスタック、グローバル変数などを指す|
| `GOGC` | GC の発火頻度を決めるチューニングパラメータ 。デフォルトは100。|

`GC roots`はいわゆるスタックメモリ(`StackSys`)であり、全体を大きく占めるものではありません。数式上の変数としては存在しているものの。微々たるものとしてここでは無視したいと思います。

今回、`GOGC`パラメータは特にいじっていません。デフォルトは100になっています。
この値を操作することで、`Target heap memory`を上下させることができます。つまり、GC頻度を操作できるようになるということです。

https://github.com/golang/go/blob/d00c67f297ef6f2cb2cd0e9aae59fa3936bb7eca/src/runtime/extern.go#L17

サンプルコードを実行したとき、この数式に照らし合わせるとどう`Target heap memory`が設定されていたかを考えてみます。
```bash
iter 1 HeapAlloc=200MiB NextGC=400MiB NumGC=1
iter 2 HeapAlloc=380MiB NextGC=400MiB NumGC=1
```

### 1ループ目の様子
まず、`iter 1`(ループ1回目)でGCが一度起きていますね。
起動時点では、もっともミニマムな`Target heap memory`として、`NextGC=4MiB`に設定されています。以下のバイトスライス初期化時点で200Mibが確保され、その時にGCが発火したものと考えられます。
```go
buf := make([]byte, size) // size = 200Mib
```
しかし、`buf`はまだ参照が残っているLive heapでした。そのため回収できるヒープメモリはなかったと考えられます。
次回のGCタイミングが決定されました。数式に当てこんで考えます。

$$ Target heap memory = 200 + (200 + 0) * 100 / 100 $$

`Target heap memory`は400になります。前述の通り、`GC Roots`は無視しています(0にしました)。
机上の計算と出力は合致しています。
```
iter 1 HeapAlloc=200MiB NextGC=400MiB NumGC=1
```

### 2ループ目の様子
そして、2ループ目に差し掛かります。
2ループ目開始時点で、1ループ目の`buf`変数は参照が切れたためdead heapとなります。
- `Live Heap` = 0
- `HeapAlloc` = 200

そして以下に差し掛かり、180Mib分のメモリがLive heapとなります。
```go
buf := make([]byte, size) // size = 180
_, _ = rand.Read(buf)
```
- `Live Heap` = 180
- `HeapAlloc` = 380

dead heapはまだ回収されません。Live Heapが`Target heap memory`である400Mibに達していないからです。
雲行きが怪しくなってきました。

### ３ループ目の様子
3ループ目に差し掛かります。
2ループ目開始時点で、2ループ目の`buf`変数は参照が切れたためdead heapとなります。
- `Live Heap` = 0
- `HeapAlloc` = 300

そして以下に差し掛かり、175Mib分のメモリがLive heapとなります。
```go
buf := make([]byte, size) // size = 175
_, _ = rand.Read(buf)
```
- `Live Heap` = 175
- `HeapAlloc` = 555 (計算上)

この時点でGoランタイムが要求するメモリがコンテナ上の物理メモリの上限である512Mbを超過しました.....!
つまりOOMです。

このため、プログラムを実行した時の出力が2ループ目までで止まっていたのですね。

つまり、実際は以下のようにしてヒープメモリが推移しようとしていたのです。

![](/images/gc/sample-heap-actual.png)

### `GOGC`パラメータを調整してGC頻度を上げてみる
このパラメータ操作によって得られる結果は以下のように整理できます。
- `GOGC`を下げる→`Target heap memory`が下がる→GC頻度が上がる
- `GOGC`を上げる→`Target heap memory`が上がる→GC頻度が下がる

GCはある程度コストを伴うものです。頻度を調整することはつまり、メモリとCPUのトレードオフを追うことであると言えます。
GCの頻度を上げればピーク時のメモリ使用量を下げられますが、その分計算量が増えてCPUのオーバーヘッドが発生します。アプリケーションの性能が落ち、レイテンシが悪化するなどが考えられます。
一方、GCの頻度を下げれば、CPU使用率は下げられますが、その分メモリのオーバーヘッドが発生します。これこそOOMを誘発する原因にもなりかねません。

実際、GOGC を 2 倍にする(=GC頻度を下げる)とGCのCPUコストはおよそ半分になるとも述べられています。

> doubling GOGC will double heap memory overheads and roughly halve GC CPU cost
> 
> 引用：https://go.dev/doc/gc-guide

この`GOGC`の操作方針の推奨として、以下のように述べられています。

> - Don't set a memory limit to avoid out-of-memory conditions when a program is already close to its environment's memory limits.
> 
>This effectively replaces an out-of-memory risk with a risk of severe application slowdown, which is often not a favorable trade, even with the efforts Go makes to mitigate thrashing. In such a case, it would be much more effective to either increase the environment's memory limits (and then potentially set a memory limit) or decrease GOGC (which provides a much cleaner trade-off than thrashing-mitigation does).

「プログラムがすでに環境のメモリ上限ぎりぎりで動いている状況で、OOM を回避する目的で（`GOMEMLIMIT`による）メモリ制限を設定してはいけない。」と述べられています。(`GOMEMLIMIT`については次節で取り上げます)
また、その場合は以下の二択が効果的とされています。
- 環境側のメモリ上限を上げる
- `GOGC`を下げる

今回は`GOGC`を半分の50にしてみましょう。

```bash
❯ docker run --rm --name gc-sample --memory=512m --memory-swap=512m -e GOGC=50 gc
iter 1 HeapAlloc=200MiB NextGC=300MiB NumGC=1
iter 2 HeapAlloc=180MiB NextGC=270MiB NumGC=2
iter 3 HeapAlloc=175MiB NextGC=262MiB NumGC=3
iter 4 HeapAlloc=140MiB NextGC=210MiB NumGC=4
iter 5 HeapAlloc=200MiB NextGC=210MiB NumGC=4
iter 6 HeapAlloc=170MiB NextGC=255MiB NumGC=5
iter 7 HeapAlloc=210MiB NextGC=255MiB NumGC=5
iter 8 HeapAlloc=120MiB NextGC=180MiB NumGC=6
iter 9 HeapAlloc=80MiB NextGC=120MiB NumGC=7
iter 10 HeapAlloc=150MiB NextGC=225MiB NumGC=8
```

OOMを回避してプログラムを完遂しました！
1~3ループ目を抜粋します。
```bash
iter 1 HeapAlloc=200MiB NextGC=300MiB NumGC=1
iter 2 HeapAlloc=180MiB NextGC=270MiB NumGC=2
iter 3 HeapAlloc=175MiB NextGC=262MiB NumGC=3
```

#### GOGC=50の時の1ループ目の様子

１回目のループ時のGC完了時、`Target heap memory`が以下のように設定されたようです。

$$ Target heap memory = 200 + (200 + 0) * 50 / 100 $$

つまりLive heapの1.5倍が`Target heap memory`と設定されます。

#### GOGC=50の時の2ループ目の様子
2ループ目に差し掛かります。
2ループ目開始時点で、1ループ目の`buf`変数は参照が切れたためdead heapとなります。
- `Live Heap` = 0
- `HeapAlloc` = 200

そして以下に差し掛かり、180Mib分のメモリがLive heapとなります。
```go
buf := make([]byte, size) // size = 180
_, _ = rand.Read(buf)
```
- `Live Heap` = 180
- `HeapAlloc` = 380

ここで`HeapAlloc`(live heap + dead heap)の値が`Target heap memory`を迎えました。
この瞬間にGCが発火したと考えられます。
- `Live Heap` = 180
- `HeapAlloc` = 180

そして、Live heapの1.5倍である270Mibが次回のGCタイミングとして設定されます。

#### GOGC=50の時の2ループ目の様子
3ループ目に差し掛かります。
3ループ目開始時点で、2ループ目の`buf`変数は参照が切れたためdead heapとなります。
- `Live Heap` = 0
- `HeapAlloc` = 180

そして以下に差し掛かり、175Mib分のメモリがLive heapとなります。
```go
buf := make([]byte, size) // size = 175
_, _ = rand.Read(buf)
```
- `Live Heap` = 175
- `HeapAlloc` = 355

ここで`HeapAlloc`(live heap + dead heap)の値が前回設定した`Target heap memory`(=270Mib)を迎えました。
この瞬間にもまたGCが発火したと考えられます。
- `Live Heap` = 175
- `HeapAlloc` = 175

--------

このように、`Target heap memory`というベースラインを`GOGC`パラメータによって「下げる」ことでGC頻度を上げることができました。
そして、OOMを引き起こすことなくプログラムの実行に成功できたというわけです。

## 2. `GOMEMLIMIT`への到達時
続いて、`GOMEMLIMIT`パラメータ操作によるGCタイミングの調整について紹介します。
これは、先ほどの`Target heap memory`を決定する数式に加えてGCタイミングを調整することができるものになっています。

`GOGC`は、Live heapに対する比率で`Target heap memoruy`を決める「相対指標」でした。
対して、`GOMEMLIMIT`は「Goランタイムが使用するメモリの総量（ヒープ + 非ヒープ）がこの上限を超えないように`Target heap memoruy`を引き下げる」という絶対指標です。
つまり、Live heap がどれだけ大きくなっても、`Target heap memoruy`はこの上限から非ヒープ分を引いた値以下に抑え込まれます。
`GOMEMLIMIT`はデフォルトで上限なしです。

https://github.com/golang/go/blob/d00c67f297ef6f2cb2cd0e9aae59fa3936bb7eca/src/runtime/debug/garbage.go#L223


このパラメータの設定における推奨の方針が以下にあります。

> - Do take advantage of the memory limit when the execution environment of your Go program is entirely within your control, and the Go program is the only program with access to some set of resources (i.e. some kind of memory reservation, like a container memory limit).
>
>A good example is the deployment of a web service into containers with a fixed amount of available memory.
>
>In this case, a good rule of thumb is to leave an additional 5-10% of headroom to account for memory sources the Go runtime is unaware of.
